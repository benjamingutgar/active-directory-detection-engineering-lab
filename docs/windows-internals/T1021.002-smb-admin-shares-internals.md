# T1021.002 — SMB / Windows Admin Shares Internals

## 1. Purpose

This document explains what happens internally in Windows during the SMB / Windows Admin Shares remote-execution scenario reproduced in the laboratory.

The objective is not only to describe that an SMB connection or a remote service was observed.

The objective is to understand the complete Windows architecture that makes the operation possible:

```text
remote client
      ↓
TCP connection
      ↓
SMB protocol negotiation
      ↓
SMB session establishment
      ↓
authentication
      ↓
Windows network logon
      ↓
security token
      ↓
authorization
      ↓
administrative shares
      ↓
IPC$
      ↓
Named Pipes
      ↓
DCE/RPC
      ↓
SCMR
      ↓
Service Control Manager
      ↓
service creation
      ↓
services.exe
      ↓
process execution
      ↓
Windows telemetry
      ↓
Wazuh detection
```

The technique does not require SMB itself to be vulnerable.

It uses legitimate Windows functionality intended for authenticated remote administration.

The security problem appears when an attacker controls an identity with enough privileges to use those mechanisms remotely.

In the laboratory:

```text
Kali-ATK01

      │
      │ SMB / TCP 445
      ▼

      │

      │

cmd.exe
      │
      ▼

      │
      ▼
NT AUTHORITY\SYSTEM
```

# 2. SMB Before the Attack: What Windows Provides

SMB means:

```text
Server Message Block
```

It is a native Windows network protocol used for access to resources such as:

- files;
- directories;
- shared folders;
- printers;
- named pipes;
- remote-administration interfaces.

SMB therefore provides considerably more than ordinary file sharing.

Conceptually:

```text
SMB
 │
 ├── file access
 ├── directory access
 ├── administrative shares
 ├── printer sharing
 ├── named pipes
 └── transport for some RPC interfaces
```

This last capability is particularly important for the laboratory.

The attack does not simply:

```text
connect to a folder
```

It uses the authenticated SMB relationship to reach Windows remote-management infrastructure.

The complete concept is:

```text
SMB
 ↓
authenticated session
 ↓
IPC$
 ↓
Named Pipe
 ↓
RPC
 ↓
Windows management API
```

---

# 3. SMB Is Not Remote Execution by Itself

SMB itself does not mean:

```text
execute this command
```

SMB first provides communication and access to remote resources.

Remote execution occurs because other Windows components can be reached through that authenticated relationship.

Therefore:

```text
SMB
    ≠
Service Control Manager
```

and:

```text
SMB
    ≠
remote process execution
```

Instead:

```text
SMB
      ↓
provides authenticated remote communication
      ↓
IPC$
      ↓
Named Pipe
      ↓
DCE/RPC
      ↓
Service Control Manager
      ↓
remote service
      ↓
process execution
```

This separation is fundamental to understanding the technique.

# 5. Windows SMB Server

The Windows service normally associated with file and printer sharing is:

```text
Server
```

with service name:

```text
LanmanServer
```

This service provides server-side SMB functionality.

Conceptually:

```text
remote SMB client
       ↓
network
       ↓
Windows SMB server functionality
       ↓
LanmanServer
       ↓
shared Windows resources
```

On modern Windows systems, SMB server processing also involves kernel-mode networking and SMB server components.

The important architectural distinction is that `LanmanServer` represents the Windows service controlling server-side file and resource sharing, while lower-level Windows networking components handle substantial parts of actual SMB protocol processing.

For detection purposes, this can be simplified to:

```text
network stack
     ↓
Windows SMB server
     ↓
LanmanServer / SMB infrastructure
```

# 6. TCP Port 445

Modern direct-hosted SMB normally uses:

```text
TCP/445
```

The laboratory path is:

```text
Kali-ATK01
192.168.56.40
      │
      │ TCP/445
      ▼
DC01
192.168.56.20
```

The initial network operation is conceptually:

```text
Kali
  │
  │ SYN
  ▼
DC01:445
  │
  │ SYN/ACK
  ▼
Kali
  │
  │ ACK
  ▼
TCP connection
```

At this point:

```text
TCP connection established
```

does not mean:

```text
SMB authentication succeeded
```

and it certainly does not mean:

```text
remote command execution succeeded
```

Several additional Windows security boundaries still need to be crossed.

# 7. SMB Protocol Negotiation

Once the TCP connection exists, the client and server negotiate SMB capabilities.

Modern Windows uses SMB2/SMB3 protocol families.

A simplified sequence is:

```text
TCP connection
      ↓
SMB NEGOTIATE
      ↓
SMB dialect selected
      ↓
SESSION_SETUP
      ↓
authentication
      ↓
SMB session
      ↓
TREE_CONNECT
      ↓
specific share
```

The negotiation phase determines capabilities such as:

- supported SMB dialects;
- security capabilities;
- signing support;
- encryption capabilities;
- message sizes;
- credit handling;
- other SMB features.

Conceptually:

```text
Client supported dialects
        ↓
SMB NEGOTIATE
        ↓
Server supported dialects
        ↓
common dialect selected
```

For example, modern systems can support dialects from the SMB 2.x and SMB 3.x families.

The repository should not claim that a specific SMB dialect was observed unless packet capture or equivalent evidence confirms it.

---

# 8. SMB2/SMB3 Command Model

Modern SMB is organized around commands.

Important commands include:

```text
NEGOTIATE
SESSION_SETUP
TREE_CONNECT
CREATE
READ
WRITE
CLOSE
IOCTL
QUERY_INFO
SET_INFO
LOGOFF
```

They perform different functions.

Conceptually:

```text
NEGOTIATE
    ↓
choose SMB capabilities

SESSION_SETUP
    ↓
authenticate and create session

TREE_CONNECT
    ↓
connect session to a share

CREATE
    ↓
open/create file, directory or Named Pipe

READ / WRITE
    ↓
exchange data

CLOSE
    ↓
close opened object
```

The word:

```text
CREATE
```

can be misleading.

An SMB `CREATE` operation does not necessarily mean creating a new file.

It is also the SMB operation used to open existing objects.

For example, a named pipe can be opened through an SMB `CREATE` request.

This becomes important later when:

```text
\pipe\svcctl
```

is opened.

---

# 9. SMB NEGOTIATE

The first SMB-specific phase is protocol negotiation.

Conceptually:

```text
Kali-ATK01
      │
      │ SMB NEGOTIATE
      ▼
DC01
      │
      │ supported protocol/capabilities
      ▼
Kali-ATK01
```

The server and client establish a mutually supported SMB dialect.

This does not yet authenticate the user.

Therefore:

```text
NEGOTIATE
      ↓
protocol established
```

but not:

```text
identity authenticated
```

---

# 10. SMB SESSION_SETUP

Authentication is principally associated with the SMB:

```text
SESSION_SETUP
```

phase.

Conceptually:

```text
SMB NEGOTIATE complete
        ↓
SESSION_SETUP
        ↓
authentication exchange
        ↓
successful identity validation
        ↓
SMB SessionId
```

The resulting session associates the SMB connection with an authenticated security identity.

This distinction is important.

SMB maintains internal identifiers for different objects.

Conceptually:

```text
Connection
    ↓
SessionId
    ↓
TreeId
    ↓
FileId / object handle
```

They represent different levels of state.

---

# 11. Authentication Data Inside SESSION_SETUP

The SMB client does not simply send:

```text
username
password
```

as plaintext fields to the remote Windows server.

The `SESSION_SETUP` exchange carries security information used by the authentication mechanism.

Conceptually:

```text
SESSION_SETUP
       ↓
security token / authentication blob
       ↓
authentication protocol
       ↓
Windows authentication subsystem
```

Depending on the environment and client configuration, SMB authentication can involve:

```text
Kerberos
NTLM
```

often negotiated using mechanisms such as SPNEGO/Negotiate.

---

# 12. Important Difference: Kali Does Not Use Windows SSPI

The client in this laboratory is:

```text
Kali-ATK01
```

and the SMB tooling is based on:

```text
CrackMapExec / Impacket
```

Therefore, the client is not a Windows process invoking Windows SSPI.

Instead, the client tooling implements the SMB and authentication protocols itself.

Conceptually:

```text
Kali
 │
 └── Impacket / CrackMapExec
          │
          ├── SMB protocol implementation
          └── NTLM protocol implementation
```

On the Windows side:

```text
DC01
 │
 └── Windows SMB server
          ↓
     Windows authentication subsystem
          ↓
      LSA / LSASS
```

This distinction is important.

It would be inaccurate to draw:

```text
Kali
 ↓
Windows SSPI
```

because Kali is not running the Windows SSPI stack.

Instead:

```text
Impacket generates protocol messages
             ↓
network
             ↓
Windows receives and processes them
```

# 13. Kerberos and NTLM

SMB can use different authentication mechanisms.

In a normal Windows domain environment, Kerberos is generally preferred when all required conditions are available, including an appropriate service identity/SPN.

For SMB, the service principal is commonly associated with:

```text
cifs/<server-name>
```

If Kerberos cannot be used, NTLM may be used when allowed.

Conceptually:

```text
SMB authentication
      ↓
Can Kerberos be used?
      │
      ├── yes
      │    ↓
      │ Kerberos
      │
      └── no
           ↓
          NTLM
```

The exact behavior depends on the client implementation and authentication configuration.

---

# 14. Authentication Observed in This Laboratory

The laboratory evidence confirms:

```text
AuthenticationPackageName = NTLM
```

for the SMB network logon.

Therefore the scenario should be documented as:

```text
SMB
 ↓
NTLM
```

because that is what Windows actually recorded.

The test connects directly to:

```text
192.168.56.20
```

and the tooling used does not operate with a Kerberos ticket workflow in the documented execution.

It is therefore safer to state:

```text
NTLM was observed in this laboratory
```

than to make the universal statement:

```text
connecting to an IP address always forces NTLM
```

because Kerberos behavior can vary with client implementation and configuration.

---

# 15. NTLM Challenge-Response

NTLM is based on a challenge-response model.

At a high level:

```text
Kali-ATK01
      │
      │ authentication negotiation
      ▼
DC01
      │
      │ server challenge
      ▼
Kali-ATK01
      │
      │ calculated NTLM response
      ▼
DC01
      │
      ▼
validate response
```

The plaintext password is not simply transmitted to DC01.

Instead, cryptographic credential material is used to create the response required by the authentication exchange.

The detailed NTLM cryptographic internals are documented separately in the Pass-the-Hash internals document.

For the SMB scenario, the key concept is:

```text
valid credentials
       ↓
valid NTLM response
       ↓
Windows accepts identity
```

---

# 16. LSA and LSASS on DC01

Windows centralizes important authentication operations around:

```text
Local Security Authority
LSA
```

The associated user-mode process is:

```text
C:\Windows\System32\lsass.exe
```

When SMB presents authentication material to Windows, Windows authentication infrastructure validates the identity.

Conceptually:

```text
SMB SESSION_SETUP
        ↓
authentication data
        ↓
Windows security subsystem
        ↓
LSA / LSASS
        ↓
NTLM authentication package
        ↓
identity validation
```

Because the target is:

```text
DC01
```

the same system is also the Domain Controller containing Active Directory domain identity data.

The conceptual architecture is:

```text
Kali-ATK01
      │
      │ NTLM
      ▼
DC01
      │
      ├── SMB Server
      ├── LSASS
      └── Active Directory
```

This is different from an SMB connection to a member server, where the member server can need to communicate with a Domain Controller for domain credential validation.

# 17. Authentication Creates a Network Logon

Successful SMB authentication results in a Windows network logon.

The relevant Windows logon type is:

```text
Logon Type 3
```

which means:

```text
Network
```

The main Security event is:

```text
4624
```

Therefore:

```text
SMB SESSION_SETUP
       ↓
NTLM authentication succeeds
       ↓
Windows network logon
       ↓
4624
       ↓
LogonType = 3
```

This is very different from the RDP scenario:

```text
RDP
 ↓
4624
 ↓
Logon Type 10
 ↓
RemoteInteractive
```

versus:

```text
SMB
 ↓
4624
 ↓
Logon Type 3
 ↓
Network
```

This difference reflects the internal Windows logon model.

---

# 18. Logon Session

Successful authentication causes Windows to create a security logon session representing the remote identity.

Conceptually:

```text
remote credentials
      ↓
authentication
      ↓
identity established
      ↓
network logon session
```

Windows assigns the logon session an identifier commonly exposed as:

```text
Logon ID
```

This identifier can later help analysts correlate related activity.

The important point is that Windows has now transformed:

```text
remote network credentials
```

into:

```text
a Windows security context
```

---

# 19. Access Token

Windows uses access tokens to represent authenticated security identities.

Conceptually:

```text
authenticated account
       ↓
logon session
       ↓
access token
       │
       ├── User SID
       ├── Group SIDs
       ├── privileges
       └── security attributes
```

Windows later uses this information to decide whether the remote identity can:

```text
access ADMIN$
access C$
access IPC$
open SCM
create services
```

Authentication therefore establishes identity.

Authorization still needs to occur for every protected resource.

---

# 20. Authentication Does Not Mean Administrative Access

This distinction is fundamental:

```text
successful authentication
        ≠
administrator
```

An ordinary user may successfully establish an SMB session but still receive:

```text
ACCESS_DENIED
```

when attempting to access an administrative share or create a service.

Conceptually:

```text
authentication succeeds
        ↓
network logon exists
        ↓
Windows evaluates permissions
        │
        ├── insufficient
        │      ↓
        │ ACCESS_DENIED
        │
        └── sufficient
               ↓
        operation allowed
```

This explains why remote-service execution requires more than valid credentials.

---

# 21. Privileged Account and Event ID 4672

The account used in the laboratory has administrative privileges.

Windows can therefore assign sensitive privileges to the associated logon session.

This produces:

```text
Event ID 4672
```

with meaning:

```text
Special privileges assigned to new logon
```

The laboratory observed privileges including examples such as:

```text
SeImpersonatePrivilege
SeBackupPrivilege
SeRestorePrivilege
SeSecurityPrivilege
```

The conceptual sequence is:

```text
4624 / Logon Type 3
        ↓
privileged account
        ↓
special privileges assigned
        ↓
4672
```

Event `4672` is useful context.

However:

```text
4672 alone
```

does not prove PsExec, smbexec, or malicious SMB activity.

It indicates that the logon received sensitive privileges.

---

# 22. SMB Session vs Share Connection

Once authenticated, the client has an SMB session.

It still does not automatically have a connection to every share.

Conceptually:

```text
SMB connection
      ↓
SessionId
      ↓
authenticated identity
```

To access a particular share the client performs:

```text
TREE_CONNECT
```

For example:

```text
\\DC01\ADMIN$
```

or:

```text
\\DC01\IPC$
```

Conceptually:

```text
SessionId
     ↓
TREE_CONNECT
     ↓
specific share
     ↓
TreeId
```

The `TreeId` identifies the connection to that share within the SMB session.

---

# 23. SMB TREE_CONNECT

The conceptual operation is:

```text
authenticated SMB session
        ↓
TREE_CONNECT
        ↓
\\DC01\ADMIN$
```

Windows then evaluates whether the authenticated security context is allowed to connect to the requested share.

If allowed, the server creates a tree connection and returns a:

```text
TreeId
```

Therefore:

```text
SessionId
```

represents the authenticated SMB session, while:

```text
TreeId
```

represents access to a particular share.

This distinction is useful when understanding packet captures and SMB internals.

---

# 24. Administrative Shares

Windows automatically creates administrative shares on many Windows systems.

The most relevant to this technique are:

```text
ADMIN$
C$
IPC$
```

The `$` suffix normally marks the share as hidden from ordinary browsing.

Hidden does not mean protected by secrecy.

Access is still controlled through Windows security mechanisms.

---

# 25. ADMIN$

`ADMIN$` refers to the Windows system directory.

Usually:

```text
%SystemRoot%
```

and on a standard installation:

```text
C:\Windows
```

Therefore:

```text
\\DC01\ADMIN$
```

typically corresponds to:

```text
C:\Windows
```

on DC01.

It exists to support remote administration.

The important mapping is:

```text
\\DC01\ADMIN$
        ↓
DC01
        ↓
%SystemRoot%
        ↓
C:\Windows
```

---

# 26. C$

`C$` refers to the root of the `C:` volume.

Correct mapping:

```text
\\DC01\C$
       ↓
C:\
```

It does **not** mean:

```text
C:\Windows
```

Other drives can have equivalent administrative shares:

```text
D$
E$
...
```

depending on the system.

---

# 27. IPC$

`IPC$` means:

```text
Inter-Process Communication
```

It is fundamentally different from `ADMIN$` and `C$`.

It is not primarily a file-storage share.

Instead, it is used to access communication endpoints such as:

```text
Named Pipes
```

Conceptually:

```text
\\DC01\IPC$
       ↓
Named Pipe namespace
       ↓
remote IPC
```

This is why `IPC$` becomes critical to the remote-service part of the scenario.

---

# 28. Disk Share vs Pipe Share

SMB distinguishes different share types.

Conceptually:

```text
ADMIN$
C$
 ↓
Disk Share
```

while:

```text
IPC$
 ↓
Named Pipe / IPC-oriented share
```

This difference explains why operations against `IPC$` may involve paths such as:

```text
\pipe\svcctl
```

rather than normal disk files.

---

# 29. Share Authorization

Connecting to a share requires authorization.

Windows evaluates the authenticated identity against share-level access controls.

Conceptually:

```text
access token
     ↓
share security descriptor
     ↓
access check
     │
     ├── deny
     └── allow
```

Therefore:

```text
knowing that ADMIN$ exists
```

does not imply:

```text
being allowed to use ADMIN$
```

---

# 30. NTFS Authorization

For disk-backed shares such as:

```text
ADMIN$
C$
```

access can also involve NTFS filesystem authorization.

Conceptually:

```text
authenticated user
        ↓
share access check
        ↓
NTFS access check
        ↓
file/directory access
```

This means a remote filesystem operation can be constrained by more than one security layer.

The account used in the laboratory possesses sufficient administrative privileges for the relevant operations.

---

# 31. Event ID 5145

With the appropriate Detailed File Share auditing enabled, Windows can record:

```text
Event ID 5145
```

The event represents:

```text
a network share object was checked
to determine whether the client
could be granted the requested access
```

Relevant fields can include:

```text
SubjectUserName
SubjectDomainName
IpAddress
ShareName
ShareLocalPath
RelativeTargetName
AccessMask
AccessList
```

Therefore:

```text
5145
```

does not simply mean:

```text
malicious ADMIN$ access
```

It records a share-access authorization operation.

Its value comes from context.

# 33. Named Pipes

A Named Pipe is an operating-system inter-process communication mechanism.

Conceptually:

```text
Process A
    │
    │ Named Pipe
    ▼
Process B
```

Named Pipes can also be exposed remotely through SMB.

The remote form is conceptually represented as:

```text
\\server\pipe\name
```

For example:

```text
\\DC01\pipe\svcctl
```

This allows a remote authenticated client to communicate with a Windows service that exposes an RPC interface through a Named Pipe.

---

# 34. Opening a Named Pipe Through SMB

After connecting to:

```text
IPC$
```

the client can open a named pipe.

At the SMB2 level, opening the object can use:

```text
SMB2 CREATE
```

Conceptually:

```text
SMB session
      ↓
TREE_CONNECT IPC$
      ↓
SMB CREATE
      ↓
svcctl Named Pipe
      ↓
pipe handle
```

Again:

```text
CREATE
```

does not necessarily mean:

```text
create a new pipe
```

It is the SMB operation used to open the existing endpoint.

---

# 35. The svcctl Named Pipe

The critical pipe for this execution path is:

```text
\pipe\svcctl
```

This endpoint provides access to the:

```text
Service Control Manager Remote Protocol
```

The architectural chain is:

```text
SMB
 ↓
IPC$
 ↓
Named Pipe
 ↓
\pipe\svcctl
 ↓
DCE/RPC
 ↓
SCMR
 ↓
Service Control Manager
```

The pipe itself does not execute the command.

It transports RPC communication to the Windows service-control infrastructure.

---

# 36. SMB Is Acting as a Transport for RPC

This is one of the most important internal concepts.

At this stage there are two protocols layered together.

Conceptually:

```text
DCE/RPC messages
      ↓
Named Pipe
      ↓
SMB
      ↓
TCP/445
```

Therefore the network stack looks like:

```text
SCMR
 ↓
DCE/RPC
 ↓
Named Pipe
 ↓
SMB
 ↓
TCP
```

The remote client communicates with the Service Control Manager using RPC semantics.

SMB provides the remote Named Pipe transport.

---

# 37. DCE/RPC

DCE/RPC provides a framework for invoking procedures on remote services.

Instead of sending a textual command such as:

```text
CREATE_SERVICE
```

as an arbitrary string, the client communicates with a defined RPC interface.

Conceptually:

```text
client
  ↓
RPC bind
  ↓
specific interface
  ↓
remote procedure call
  ↓
server-side implementation
```

For the service-management path:

```text
DCE/RPC
   ↓
SCMR interface
```

---

# 38. RPC Binding

After the Named Pipe has been opened, the client binds to the SCMR RPC interface.

Conceptually:

```text
\pipe\svcctl opened
        ↓
DCE/RPC BIND
        ↓
SCMR interface selected
        ↓
RPC calls available
```

At this point, the client can request operations exposed by the Service Control Manager Remote Protocol.

This still does not mean every operation is authorized.

Windows performs security checks when protected SCM operations are requested.

---

# 39. SCMR

SCMR means:

```text
Service Control Manager Remote Protocol
```

# 45. smbexec-Style Execution

The laboratory uses:

```text
CrackMapExec
--exec-method smbexec
```

The smbexec execution model differs from classic PsExec.

Classic PsExec-style execution typically relies on a dedicated service executable being placed on the target and registered as a Windows service.

smbexec-style execution can instead configure a temporary Windows service whose command line invokes the Windows command processor.

Conceptually:

```text
SCM
 ↓
temporary service
 ↓
ImagePath
 ↓
cmd.exe /c ...
```

The important distinction is:

```text
classic PsExec
      ↓
dedicated service executable
```

versus:

```text
smbexec-style
      ↓
service command invoking cmd.exe
```

---

# 46. smbexec Does Not Mean Zero File Activity

It would be inaccurate to describe smbexec as:

```text
completely fileless
```

The important property is that it does not require the same dedicated remote-service executable used by classic PsExec.

Depending on implementation and version, smbexec-style tooling can still use:

- temporary command files;
- temporary batch files;
- temporary output files;
- writable administrative shares.

Therefore:

```text
no dedicated PsExec service binary
```

does not mean:

```text
no filesystem activity
```

The exact temporary paths and filenames should not be described as laboratory evidence unless they were actually preserved.

# 47. The Service ImagePath

Normally, a legitimate service might contain something like:

```text
  ↓
```

This difference is highly valuable for detection.

# 55. Why the Remote User Becomes SYSTEM

The remote user itself does not literally transform into:

```text

```


Then:



```text

      ↓

      ↓

```

This distinction is extremely important.

```text

```

# 91. Why This Matters Defensively

The internal model explains that the attacker never directly creates a Windows process through the network.

The real chain is:

```text
remote request
      ↓
Windows receives request
      ↓
Windows authenticates identity
      ↓
Windows authorizes resource access
      ↓
Windows accepts RPC operation
      ↓
Windows SCM creates service
      ↓
Windows services.exe creates process
```

Therefore:

```text
Windows itself performs the final execution
```

because the remote caller has successfully convinced legitimate Windows administration mechanisms to do so.

This is exactly why the attack can blend with legitimate administration.
