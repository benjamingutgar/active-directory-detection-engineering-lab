# T1021.001 — Remote Desktop Protocol Internals

## 1. Purpose

This document explains what happens internally in Windows during the Remote Desktop Protocol scenario reproduced in the laboratory.

The objective is not only to describe that an RDP connection occurred, but to understand the complete internal chain that makes that connection possible:

```text
Remote client
      ↓
network connection
      ↓
RDP protocol
      ↓
Remote Desktop Services
      ↓
security negotiation
      ↓
authentication
      ↓
domain identity validation
      ↓
Windows logon session
      ↓
access token
      ↓
RemoteInteractive authorization
      ↓
RDP user session
      ↓
interactive desktop
      ↓
process creation
      ↓
Windows telemetry
      ↓
Wazuh detection
```

Understanding this chain is important because RDP is not malicious functionality.

It is a legitimate Windows remote-access mechanism.

The offensive behavior appears when an attacker who controls valid credentials uses that legitimate mechanism to obtain an interactive session on another system.

In the laboratory:

```text
Kali-ATK01
192.168.56.40
      │
      │ RDP
      ▼
WS01
192.168.56.30
      │
      ▼
LAB domain user
      │
      ▼
remote interactive session
      │
      ▼
cmd.exe
      │
      ├── whoami.exe
      ├── HOSTNAME.EXE
      └── ipconfig.exe
```

# 2. RDP Before the Attack: What Windows Provides

Before examining the laboratory execution, it is necessary to understand what Remote Desktop Services normally does.

Remote Desktop Protocol is a legitimate Windows protocol designed to provide remote graphical access to applications and desktops running on another Windows system.

The critical architectural concept is:

```text
applications execute on the remote Windows host
```

not on the RDP client.

The client mainly performs two functions:

```text
Server → Client
graphical/display information

Client → Server
keyboard/mouse/user input
```

Therefore, when a user remotely opens:

```text
cmd.exe
```

the executable is not running on Kali.

It is running on `WS01`.

The same is true for:

```text
whoami.exe
HOSTNAME.EXE
ipconfig.exe
explorer.exe
powershell.exe
```

and any other application started from that RDP session.

Conceptually:

```text
Kali-ATK01
     │
     │ keyboard / mouse
     ▼
WS01
     │
     │ executes applications locally
     ▼
Windows processes
     │
     │ graphical output
     ▼
Kali-ATK01
```

This is the first fundamental concept required to understand RDP telemetry.

Windows events describing process creation appear on `WS01` because that is where the processes actually exist.

# 4. Remote Desktop Services and TermService

Windows implements Remote Desktop functionality through Remote Desktop Services.

The principal Windows service associated with this functionality is:

```text
Remote Desktop Services
Service name: TermService
```

Its purpose is to provide the Windows infrastructure required for remote interactive sessions.

The service participates in accepting and managing Remote Desktop connections and integrating those connections with Windows session management.

Conceptually:

```text
network
   ↓
RDP connection
   ↓
Remote Desktop Services
   ↓
Windows session infrastructure
```

The remote user is therefore not connecting directly to:

```text
explorer.exe
```

or:

```text
cmd.exe
```

The user first reaches the Remote Desktop infrastructure.

That infrastructure eventually produces the Windows user session in which those applications can execute.

# 5. RDP Listener and Network Transport

The laboratory connection originates from:

```text
Kali-ATK01
192.168.56.40
```

and targets:

```text
WS01
192.168.56.30
```

The standard RDP endpoint is:

```text
TCP/3389
```

The simplified initial network flow is:

```text
192.168.56.40
      │
      │ TCP SYN
      ▼
192.168.56.30:3389
      │
      │ TCP SYN/ACK
      ▼
192.168.56.40
      │
      │ ACK
      ▼
TCP connection established
```

At this point:

```text
RDP session ≠ established Windows logon
```

Only the underlying network communication has been established.

This distinction is important.

A client being able to reach:

```text
TCP/3389
```

only proves that network communication with the RDP listener is possible.

Windows has not yet necessarily authenticated the user or created an interactive session.

Modern RDP implementations can also use UDP in some circumstances to improve transport performance, but the laboratory documentation should not assume UDP usage unless it was actually captured.

The relevant confirmed laboratory path remains:

```text
Kali-ATK01
      ↓
TCP/3389
      ↓
WS01
```

# 6. RDP Protocol Negotiation

Once the underlying connection exists, the client and server begin negotiating the Remote Desktop connection.

At protocol level, RDP contains several layers and connection phases.

A simplified representation is:

```text
TCP connection
      ↓
RDP connection initiation
      ↓
security protocol negotiation
      ↓
basic settings exchange
      ↓
channel establishment
      ↓
authentication
      ↓
session establishment
      ↓
capability exchange
      ↓
graphical/input communication
```

The client and server need to agree on characteristics of the session such as:

- security mechanism;
- display capabilities;
- screen dimensions;
- graphics functionality;
- compression capabilities;
- input capabilities;
- virtual channels;
- device-redirection capabilities;
- clipboard functionality;
- audio capabilities;
- other RDP features.

RDP is therefore not a single stream containing only graphical pixels.

It is a multi-channel remote presentation protocol.

Conceptually:

```text
RDP connection
      │
      ├── graphics
      ├── keyboard
      ├── mouse
      ├── clipboard
      ├── device redirection
      ├── drive redirection
      ├── printer redirection
      ├── audio
      └── other virtual channels
```

Not every channel must be enabled.

Their availability depends on client configuration, server policy, and negotiated capabilities.

---

# 7. RDP Security Negotiation

Before Windows creates the user session, the client and server also negotiate how the connection will be protected.

Modern Windows RDP commonly relies on Enhanced RDP Security.

Security can involve mechanisms such as:

```text
TLS
CredSSP
Network Level Authentication
```

The important distinction is:

```text
RDP
```

is the remote-desktop protocol, while:

```text
TLS
CredSSP
Kerberos
NTLM
```

are security or authentication mechanisms that can participate in establishing that session.

They should not be treated as synonyms.

For example:

```text
RDP ≠ NTLM
RDP ≠ Kerberos
RDP ≠ CredSSP
```

Instead:

```text
RDP
  │
  └── can use CredSSP
           │
           └── uses authentication mechanisms
                   │
                   ├── Kerberos
                   └── NTLM
```

---

# 8. Network Level Authentication

When Network Level Authentication, or NLA, is enabled, Windows requires authentication before creating the full remote interactive desktop.

Conceptually:

```text
without authentication
        ↓
no complete Windows desktop session yet
```

The sequence becomes:

```text
RDP connection
      ↓
security channel
      ↓
user authentication
      ↓
authorization
      ↓
only then
      ↓
full Remote Desktop session
```

This is important architecturally because Windows does not need to allocate the complete interactive desktop environment to an unauthenticated remote client.

NLA normally uses:

```text
CredSSP
```

to perform this pre-session authentication.

---

# 9. CredSSP

CredSSP means:

```text
Credential Security Support Provider
```

It is a Windows Security Support Provider implemented through SSPI.

In the RDP architecture its function is to securely perform remote authentication and credential delegation before the full Remote Desktop session is created.

A simplified CredSSP flow is:

```text
RDP client
      ↓
CredSSP begins
      ↓
TLS channel established
      ↓
SPNEGO / Negotiate
      ↓
Kerberos or NTLM
      ↓
client/server authentication
      ↓
credential delegation
      ↓
remote Windows logon
```

The first important stage is the establishment of:

```text
TLS
```

This creates an encrypted channel between client and server.

Inside that protected relationship, CredSSP uses authentication mechanisms negotiated through Windows security infrastructure.

Conceptually:

```text
CredSSP
   │
   ├── TLS
   │
   └── SPNEGO
          │
          ├── Kerberos
          └── NTLM
```

This is why CredSSP should not itself be described simply as "the RDP authentication protocol."

It is a composite mechanism that coordinates other security protocols.

---

# 10. SSPI

SSPI means:

```text
Security Support Provider Interface
```

Applications in Windows generally do not need to implement the full Kerberos or NTLM logic themselves.

Instead they can use SSPI.

Conceptually:

```text
application
     ↓
SSPI
     ↓
Security Support Provider
     ↓
authentication protocol
```

Examples of Security Support Providers include:

```text
Negotiate
Kerberos
NTLM
CredSSP
Schannel
```

In this architecture:

```text
RDP / CredSSP
      ↓
SSPI
      ↓
Negotiate
      ↓
Kerberos or NTLM
```

SSPI therefore provides an abstraction layer between the application and the authentication protocol.

---

# 11. Negotiate

The Windows:

```text
Negotiate
```

security package allows Windows to select an appropriate authentication mechanism.

Conceptually:

```text
application asks for authentication
        ↓
Negotiate
        ↓
Can Kerberos be used?
        │
        ├── Yes
        │     ↓
        │  Kerberos
        │
        └── No
              ↓
             NTLM
```

The exact mechanism used depends on factors such as:

- domain membership;
- target identity;
- hostname/SPN availability;
- client configuration;
- Kerberos availability;
- credentials;
- network connectivity to the domain infrastructure;
- policies;
- the capabilities of the client.

Therefore, the generic RDP architecture should be represented as:

```text
CredSSP
   ↓
Negotiate
   ↓
Kerberos OR NTLM
```

rather than claiming that every RDP connection necessarily uses one specific package.

```text
LAB\usuario.dominio
```

`WS01` is joined to:

```text
lab.local
```

and the Domain Controller is:


```text
Kali-ATK01
192.168.56.40

      │ RDP credentials
      ▼
WS01
192.168.56.30

      ├── RDP infrastructure
```

# 13. LSA and LSASS

Windows centralizes important authentication and security operations around the:

```text
Local Security Authority
LSA
```

The user-mode process associated with this subsystem is:

```text
C:\Windows\System32\lsass.exe
```

LSASS participates in functions including:

- authentication;
- security-policy enforcement;
- interaction with authentication packages;
- creation of logon security contexts;
- management of authentication material for active sessions;
- interaction with domain authentication mechanisms.

Conceptually:

```text
remote credentials
      ↓
Windows authentication stack
      ↓
LSA / LSASS
      ↓
authentication package
      ↓
identity validated or rejected
```

This does **not** mean that RDP traffic itself is processed entirely by `lsass.exe`.

RDP and authentication are separate layers.

The Remote Desktop infrastructure handles the RDP connection.

LSASS participates when Windows needs to authenticate and establish the user's security context.

---

# 14. Kerberos Branch

If Kerberos is selected, the domain authentication architecture conceptually involves:

```text
RDP client
     ↓
CredSSP / SPNEGO
     ↓
Kerberos
     ↓
domain Kerberos infrastructure
     ↓
DC01 / KDC
     ↓
Kerberos authentication
```

The Domain Controller provides the domain's Kerberos Key Distribution Center functionality.

The important idea here is not to reproduce the complete Kerberos protocol — that is documented separately for the Kerberos-focused scenarios — but to understand where it fits into RDP.

RDP does not validate a domain user's Kerberos identity by itself.

It relies on Windows authentication infrastructure.

---

# 15. NTLM Branch

If Kerberos cannot be used and NTLM is available, Windows can use NTLM instead.

Conceptually:

```text
RDP / CredSSP
      ↓
SPNEGO / Negotiate
      ↓
NTLM
      ↓
challenge-response authentication
      ↓
domain identity validation
```

Again:

```text
RDP ≠ NTLM
```

NTLM is only the authentication mechanism used inside the wider remote-session establishment process.

The exact authentication package used in a particular laboratory execution should be confirmed from the corresponding Windows event fields or network evidence before being stated as observed fact.

---

# 16. Authentication Is Not Authorization

A critical Windows security concept is the difference between:

```text
authentication
```

and:

```text
authorization
```

Authentication answers:

```text
Who are you?
```

Authorization answers:

```text
What are you allowed to do?
```

A valid domain account does not automatically have permission to open an RDP session.

Conceptually:

```text
valid credentials
      ↓
authentication succeeds
      ↓
account identity established
      ↓
Windows checks remote-logon rights
      ↓
allowed OR denied
```

This is why an attacker can possess a correct password and still receive an RDP access-denied error.

---

# 17. RemoteInteractive Logon Right

For an RDP session, the account must be authorized for a remote interactive logon.

Relevant Windows configuration includes the user right:

```text
Allow log on through Remote Desktop Services
```

Conceptually:

```text
authenticated account
        ↓
group membership / user rights
        ↓
RemoteInteractive logon check
        │
        ├── denied
        │      ↓
        │   no RDP session
        │
        └── allowed
               ↓
         create logon session
```

Membership in groups such as:

```text
Remote Desktop Users
Administrators
```

can be relevant depending on the system configuration and policy.

There are also deny policies capable of overriding allowed access.

Therefore:

```text
valid credentials
        ≠
guaranteed RDP access
```

# 18. Windows Logon Type 10

When the Remote Desktop authentication and authorization complete successfully, Windows creates a:

```text
RemoteInteractive
```

logon.

Windows represents this using:

```text
Logon Type 10
```

The associated successful-logon event is:

```text
Event ID 4624
```

Therefore:

```text
4624
+
LogonType = 10
      ↓
successful RemoteInteractive logon
```

This distinction is important because Event ID `4624` alone does not mean RDP.

For example:

```text
4624 / Logon Type 3
```

is normally associated with:

```text
Network
```

whereas:

```text
4624 / Logon Type 10
```

means:

```text
RemoteInteractive
```

Conceptually:

```text
RDP
      ↓
4624
      ↓
Logon Type 10
      ↓
RemoteInteractive
```

This is one of the most useful Windows fields for identifying an RDP logon.

# 19. Creation of the Windows Logon Session

Successful authentication causes Windows to establish a logon session for the user.

This is more than simply recording:

```text
password correct
```

Windows creates an internal security context representing the authenticated identity.

Conceptually:

```text
credentials
     ↓
authentication
     ↓
identity established
     ↓
logon session created
```

The logon session receives an identifier commonly represented in Windows events as:

```text
Logon ID
```

That identifier can be useful for correlating activity belonging to the same security context.

The important concept is:

```text
user identity
      ↓
logon session
      ↓
security context
```

---

# 20. Access Token Creation

A fundamental part of Windows security is the:

```text
access token
```

After authentication, Windows creates a security context associated with the account.

The token can contain information such as:

```text
User SID
Group SIDs
Privileges
Integrity information
Other security attributes
```

Conceptually:

```text
LAB\usuario.dominio
        ↓
authentication
        ↓
logon session
        ↓
access token
        │
        ├── User SID
        ├── Group SIDs
        ├── privileges
        └── security attributes
```

Windows later uses this token to determine what processes running under that identity are allowed to do.

This explains an important fact:

```text
RDP does not bypass Windows permissions
```

Commands executed through RDP normally operate with the same effective permissions that the authenticated user has in that Windows security context.

---

# 21. Why the Access Token Matters

Suppose the RDP user starts:

```text
cmd.exe
```

The process receives a token associated with that user.

If `cmd.exe` then launches:

```text
whoami.exe
```

the child process normally inherits the relevant security context.

Conceptually:

```text
logon session
      ↓
user access token
      ↓
cmd.exe
      ↓
whoami.exe
```

Therefore `whoami.exe` can identify the account under which the process is executing.

The same relationship applies to:

```text
HOSTNAME.EXE
ipconfig.exe
```

Those programs execute in the security context available to the RDP user.

---

# 22. Creation of the Remote Desktop Session

Authentication and Windows logon are not yet the whole graphical-session story.

Remote Desktop Services creates or associates the user with an RDP session.

Each Remote Desktop session has its own:

```text
Session ID
```

Conceptually:

```text
authenticated identity
        ↓
Windows logon session
        ↓
RDP session
        ↓
Session ID
```

This allows Windows to maintain multiple interactive sessions separately.

A remote session is therefore not simply:

```text
one TCP connection = one desktop process
```

Windows maintains an actual operating-system session boundary.

---

# 23. Windows Sessions

Windows separates interactive users through sessions.

Conceptually:

```text
Windows
 │
 ├── Session A
 │      └── User A
 │
 ├── Session B
 │      └── User B
 │
 └── Session C
        └── User C
```

Each RDP logon receives its own session identity.

Resources such as graphical desktops and session-scoped processes can therefore be separated from other interactive sessions.

This architecture explains why multiple users can interact with the same Windows host while maintaining different session environments.

---

# 24. WinSta0

Each Remote Desktop session is associated with an interactive:

```text
Window Station
```

The interactive window station is called:

```text
WinSta0
```

Conceptually:

```text
RDP Session ID
      ↓
WinSta0
      ↓
desktop objects
```

A Window Station is a Windows object containing resources related to interactive graphical operation.

It includes concepts such as:

- clipboard;
- desktop objects;
- graphical interaction infrastructure;
- input association.

Each RDP session receives its own interactive `WinSta0`.

Therefore the name:

```text
WinSta0
```

can exist in more than one Windows session because each instance belongs to a different session namespace.

---

# 25. Desktops Inside WinSta0

Windows Window Stations can contain multiple desktop objects.

For an interactive Window Station, standard desktops include concepts such as:

```text
Winlogon desktop
Screen-saver desktop
Interactive desktop
```

Conceptually:

```text
RDP Session
     ↓
WinSta0
     │
     ├── Winlogon desktop
     ├── screen-saver desktop
     └── interactive desktop
```

The user normally interacts with the:

```text
interactive desktop
```

after logon.

This is the graphical environment in which normal user applications appear.

---

# 26. Winlogon

Windows also uses:

```text
winlogon.exe
```

as an important component of interactive logon and session management.

At a high level, Winlogon participates in the transition from authenticated identity to usable interactive Windows environment.

The simplified relationship is:

```text
authentication succeeds
        ↓
LSA / LSASS
        ↓
Windows logon
        ↓
Winlogon
        ↓
interactive user environment
```

The exact implementation contains more components than this diagram shows, but from a detection-engineering perspective the important distinction is:

```text
authentication infrastructure
```

establishes identity and security context, while:

```text
interactive-logon infrastructure
```

creates the environment in which the user can actually work.

---

# 27. User Profile and Shell

After Windows creates the interactive logon environment, the user's profile and shell can be initialized.

A conventional Windows desktop logon ultimately results in the user shell being started.

Typical components include:

```text
userinit.exe
explorer.exe
```

The conceptual sequence is:

```text
successful logon
      ↓
user profile
      ↓
user initialization
      ↓
user shell
      ↓
desktop environment
```

The exact shell can be changed through system configuration, but the normal Windows desktop shell is:

```text
explorer.exe
```

At this point the remote user sees a functional Windows desktop.

# 28. What the RDP Client Actually Receives

It is important to understand what is and is not happening between the two machines.

The client does **not** receive:

```text
explorer.exe
cmd.exe
whoami.exe
```

for local execution.

Instead:

```text
WS01 executes process
       ↓
Windows renders application/desktop state
       ↓
RDP encodes/remotes presentation data
       ↓
network
       ↓
xfreerdp displays it
```

Input travels in the opposite direction:

```text
keyboard / mouse
      ↓
xfreerdp
      ↓
RDP
      ↓
WS01
      ↓
target interactive session
```

The complete conceptual relationship is:

```text
                GRAPHICS
WS01 ─────────────────────────► Kali-ATK01

                INPUT
WS01 ◄───────────────────────── Kali-ATK01
```

The computational work is primarily performed by the Windows endpoint.

# 29. RDP Virtual Channels

These can carry different kinds of information.

Examples include:

```text
display data
keyboard input
mouse input
clipboard redirection
drive redirection
printer redirection
audio
device redirection
```

Conceptually:

```text
RDP connection
 │
 ├── graphics channel
 ├── input
 ├── clipboard
 ├── device redirection
 ├── drive redirection
 └── other virtual channels
```

From a defensive perspective, these capabilities matter because an RDP session can provide more than graphical access.

Depending on policy and client configuration, the user may also be able to expose local resources to the remote session.

This document does not assume that every redirection feature was enabled in the laboratory.

They are described here because they are part of the RDP architecture.

# 31. Creation of cmd.exe

The user opened a Windows command shell:

```text
C:\Windows\System32\cmd.exe
```

Windows therefore created a new process.

Conceptually:

```text
RDP interactive desktop
        ↓
user action
        ↓
CreateProcess
        ↓
cmd.exe
        ↓
user access token
```

The resulting `cmd.exe` process executes under the security context of the RDP user.

Windows process auditing can observe this creation through:

```text
Event ID 4688
```

Sysmon, when configured and ingested, can provide additional process information using:

```text
Sysmon Event ID 1
```

# 32. Execution of whoami.exe

Inside `cmd.exe`, the laboratory executes:

```text
whoami
```

The Windows command processor resolves and starts:

```text
C:\Windows\System32\whoami.exe
```

The process relationship observed in the laboratory is:

```text
cmd.exe
   ↓
whoami.exe
```

Conceptually:

```text
RDP user token
      ↓
cmd.exe
      ↓
CreateProcess
      ↓
whoami.exe
      ↓
same user security context
```

`whoami.exe` queries the identity associated with the process token.

That is why the output identifies the account executing inside the remote Windows session.

Again:

```text
whoami.exe
```

executes locally on `WS01`.

# 33. Execution of HOSTNAME.EXE

The laboratory then executes:

```text
hostname
```

which creates:

```text
C:\Windows\System32\HOSTNAME.EXE
```

The process relationship is:

```text
cmd.exe
   ↓
HOSTNAME.EXE
```

Windows can therefore generate another process-creation event.

The program queries the local computer identity and returns the hostname of the system on which it is actually executing.

# 47. Disconnect and Reconnect Telemetry

An RDP session can be:

```text

disconnected
reconnected
logged off
```

A disconnected session is not necessarily destroyed.

The Windows session can continue to exist even though the RDP client is no longer actively attached to it.

This distinction is important.

Conceptually:

```text

      ↓

      ↓
user reconnects later
      ↓

```

Windows Security can provide additional events such as:

```text

```

These can help reconstruct the complete session lifecycle.

They are not required for the primary detection hypothesis used in this laboratory.

# 48. Logoff Telemetry

Windows can also record events associated with termination of a logon session.

Logoff events instead help answer:

Therefore their absence from the primary detection chain is an intentional scope decision rather than evidence that Windows does not generate session-termination telemetry.

# 53. Why Correlation Is Required

RDP is a legitimate administrative protocol.

A real administrator may produce:

```text

cmd.exe
whoami.exe
ipconfig.exe
```

without performing malicious activity.

Therefore detection should not be based on the assumption:

```text

```

The meaningful hypothesis is contextual.

For the laboratory:

```text

        +
RemoteInteractive logon
        +
known destination
        +
expected account
        +
post-access command execution
```

creates a high-confidence reconstruction of the test.

In a production environment, equivalent detection would require additional context such as:

- approved administration sources;
- expected users;
- normal login hours;
- asset criticality;
- geolocation;
- VPN context;
- jump-host usage;
- historical behavior;
- process execution after access.

# 54. Why RDP Is Useful for Lateral Movement

RDP does not need a software exploit to provide lateral movement.

The attack can rely entirely on legitimate functionality:

```text
valid identity
      ↓
legitimate RDP service
      ↓
legitimate authentication
      ↓
legitimate authorization
      ↓
legitimate Windows session
      ↓
legitimate processes
```

The malicious aspect is the attacker's control over the identity and the intent behind the session.

That is what makes RDP particularly relevant to detection engineering.

The operating system can behave exactly as designed while the overall activity is malicious.

# 59. Detection Engineering Interpretation

The main detection-engineering lesson is:

```text

      ↓

      ↓
Windows authorization
      ↓
RemoteInteractive logon
      ↓
Windows session
      ↓

      ↓
Windows events
      ↓

```

The SIEM sees the consequences of Windows performing these operations.

It does not see an abstract concept called:

```text

```

Windows produces lower-level facts such as:


The analyst and the detection logic then interpret those facts in context.

# 60. Why This Matters Defensively

Without understanding Windows internals, an analyst might memorize:

```text
4624 = login
4688 = process
```

but would not understand why those events are connected.

The internal model provides the causal chain:

```text
RDP reaches TermService
        ↓
authentication establishes identity
        ↓
LSASS creates security context
        ↓
authorization permits RemoteInteractive logon
        ↓
Windows creates the user session
        ↓
the session receives an access token
        ↓
Windows creates an interactive desktop
        ↓
the user launches cmd.exe
        ↓
cmd.exe launches child processes
        ↓
Windows records process creation
```

This allows the analyst to understand not only:

```text
what event occurred
```

but:

```text
which Windows component caused it
why Windows generated it
what security decision preceded it
what should occur next
what would be abnormal
```

That is the purpose of the Windows Internals section of this repository.
