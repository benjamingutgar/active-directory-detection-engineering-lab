# T1558.004 — AS-REP Roasting Internals

## Purpose

This document explains what happens inside Windows and Active Directory during the controlled AS-REP Roasting scenario.

The objective is to connect:

```text
Kerberos request
      ↓
Domain Controller / KDC processing
      ↓
Windows Security Event ID 4768
      ↓
Wazuh decoding
      ↓
custom detection rules
```

---

## Laboratory Context

| Component | Value |
| --------- | ----- |
| Kerberos client | `Kali-ATK01` |
| Client address | `192.168.56.40` |
| Domain Controller | `DC01.lab.local` |
| Domain Controller address | `192.168.56.20` |
| Domain | `LAB.LOCAL` |
| Target account | `svc_asrep_lab` |
| Kerberos service | `krbtgt` |
| Windows event | `4768` |

## Kerberos Authentication Service

Active Directory uses the Kerberos Key Distribution Center on the Domain Controller.

The KDC contains two logical services:

```text
Authentication Service
      ↓
issues TGT-related responses

Ticket Granting Service
      ↓
issues service tickets
```

AS-REP Roasting is associated with the Authentication Service and TGT-request stage.

Kerberoasting is associated with the Ticket Granting Service and service-ticket stage.

| Technique | Kerberos stage | Main Windows event |
| --------- | -------------- | ----------------- |
| AS-REP Roasting | TGT request | `4768` |
| Kerberoasting | Service-ticket request | `4769` |

---

## Normal Pre-Authentication

During normal Kerberos authentication, the client must provide pre-authentication data demonstrating knowledge associated with the account before the KDC returns the authentication response.

Simplified flow:

```text
client requests authentication
        ↓
KDC requires pre-authentication
        ↓
client supplies pre-authentication data
        ↓
KDC validates the request
        ↓
TGT-related response
```

---

## Observed No-Pre-Authentication Condition

The controlled account generated the following event field:

```text
preAuthType = 0
```

The observed flow was:

```text
request for svc_asrep_lab
        ↓
DC01 processes the request
        ↓
no pre-authentication recorded
        ↓
successful Kerberos response
        ↓
Event ID 4768
```

This creates the observable condition used by the detection.

---

## Event ID 4768

Windows describes Event ID `4768` as:

```text
A Kerberos authentication ticket (TGT) was requested
```

The event is generated on `DC01` because the Domain Controller processes the Kerberos request.

### Account fields

```text
targetUserName = svc_asrep_lab
targetDomainName = LAB.LOCAL
serviceName = krbtgt
```

These fields identify the requested account, domain and Kerberos TGT service.

### Network fields

```text
ipAddress = ::ffff:192.168.56.40
ipPort = client ephemeral port
```

The address identifies the controlled source.

### Kerberos result fields

```text
preAuthType = 0
status = 0x0
ticketEncryptionType = 0x17
ticketOptions = 0x50800000
```

Interpretation:

| Field | Meaning in this experiment |
| ----- | -------------------------- |
| `preAuthType=0` | No Kerberos pre-authentication recorded |
| `status=0x0` | Successful request |
| `ticketEncryptionType=0x17` | RC4-HMAC |
| `ticketOptions=0x50800000` | Kerberos ticket options stored by Windows |

## Wazuh Processing

The Wazuh alert records show:

```text
location = EventChannel
decoder.name = windows_eventchannel
agent.name = DC01
manager.name = wazuh-manager
```

The processing chain is:

```text
Windows Security Event 4768
        ↓
Wazuh Agent on DC01
        ↓
windows_eventchannel decoder
        ↓
native Windows rule context
        ↓
custom rule 100050
        ↓
custom rule 100051
        ↓
frequency rule 100052
```

### Rule 100050

Rule `100050` requires:

```text
Event ID 4768
+
preAuthType = 0
+
target is not krbtgt
+
target is not a machine account
```

This creates the initial AS-REP Roasting-compatible signal.

### Rule 100051

Rule `100051` adds:

```text
ticketEncryptionType = 0x17
```

This adds RC4-HMAC context to the no-pre-authentication request.

### Rule 100052

Rule `100052` requires:

```text
three rule 100051 matches
+
same source address
+
60-second window
```

This adds behavioral repetition.

---

## Detection Confidence

A single Event ID `4768` is common in Active Directory and should not be treated as malicious by itself.

Detection confidence increases as more context is added:

```text
4768
  ↓
successful request
  ↓
preAuthType 0
  ↓
named non-machine account
  ↓
RC4-HMAC
  ↓
repeated requests from the same source
```

The frequency correlation is the strongest signal demonstrated in the experiment.

---

## Visibility Boundary

Windows and Wazuh can observe:

- the TGT request;
- the target account;
- the source address;
- the request result;
- the pre-authentication type;
- the encryption type;
- repeated requests.

Windows and Wazuh do not directly observe:

- every offline password candidate;
- successful offline password recovery;
- later use of a recovered password unless it produces additional authentication telemetry.

The correct interpretation is:

```text
activity compatible with AS-REP Roasting
```

not:

```text
proof that the password was recovered
```

---

## Defensive Considerations

Defensive priorities include:

- inventory accounts with Kerberos pre-authentication disabled;
- restore pre-authentication where it is not required;
- use long, random and unique passwords;
- reduce unnecessary RC4 compatibility;
- monitor Event ID `4768` with `preAuthType=0`;
- review requests from unusual sources;
- correlate repeated requests;
- review later authentication involving the target account;
- minimize account privileges and remote logon rights.
