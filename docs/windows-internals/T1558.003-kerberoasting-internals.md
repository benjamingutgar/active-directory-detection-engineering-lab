# T1558.003 — Kerberoasting Internals

## 1. Purpose

This document explains what happens internally in Windows and Active Directory during the Kerberoasting scenario reproduced in the laboratory.

The objective is not only to describe that a Kerberos service ticket was requested.

The objective is to understand:

- how normal Kerberos authentication works;
- how Windows and Active Directory represent services;
- what a Service Principal Name is;
- how the KDC finds the account associated with a service;
- how a Ticket Granting Ticket is used;
- what happens during a TGS request;
- which cryptographic keys protect the different parts of a TGS response;
- why a legitimate user can obtain service-ticket material;
- why that material can become an offline password-verification target;
- why the Domain Controller cannot observe the later password-testing loop;
- why Kerberoasting detection is intrinsically difficult;
- why service-account hardening is as important as SIEM detection;
- how Windows Event ID `4769` relates to the internal KDC operation;
- how the laboratory Wazuh rules interpret that telemetry;
- and which defensive practices reduce the actual Kerberoasting risk.

The central architectural chain is:

```text
Authenticated domain identity
        ↓
Kerberos authentication
        ↓
Ticket Granting Ticket
        ↓
Service Principal Name
        ↓
TGS request
        ↓
Domain Controller / KDC
        ↓
Active Directory service account
        ↓
service-account Kerberos key
        ↓
service ticket
        ↓
Event ID 4769
        ↓
ticket returned to client
        ↓
        ├── legitimate service authentication
        │
        └── Kerberoasting
                ↓
        offline password testing
```

Kerberoasting is unusual from a defensive perspective because the attacker does not necessarily need to:

```text
exploit a vulnerability
bypass authentication
create a remote process
generate repeated password failures
lock an account
send malformed Kerberos traffic
```

Instead, the attacker can use a legitimate feature of Kerberos:

```text
request a service ticket
```

The KDC may therefore behave exactly as designed.

The security problem appears because the encrypted service ticket contains material protected using a long-term key associated with the service identity.

If that identity uses a weak password, the attacker can test password candidates offline.

# 5. Kerberos in Active Directory

Kerberos is a principal authentication protocol in Active Directory domains.

Its purpose is to allow identities to authenticate securely to network services without sending the plaintext password to every service.

A simplified Windows model is:

```text
User
 ↓
Windows security subsystem
 ↓
Kerberos
 ↓
Domain Controller
 ↓
KDC
 ↓
Active Directory
```

The resulting architecture provides Single Sign-On.

Conceptually:

```text
user authenticates once
        ↓
obtains Kerberos credentials
        ↓
requests tickets for services
        ↓
accesses multiple Kerberos-aware services
```

The password therefore does not need to be repeatedly supplied to each application.

---

# 6. Windows Kerberos Architecture

On a normal Windows domain client, an application can interact with the Windows authentication stack through:

```text
SSPI
```

meaning:

```text
Security Support Provider Interface
```

A simplified Windows architecture is:

```text
Application
    ↓
SSPI
    ↓
Negotiate
    ↓
Kerberos Security Support Provider
    ↓
LSA / LSASS
    ↓
Kerberos protocol
    ↓
Domain Controller
    ↓
KDC
```

The application normally does not implement every Kerberos message itself.

Windows authentication infrastructure performs that work.

# 8. The Key Distribution Center

The Kerberos:

```text
Key Distribution Center
```

or:

```text
KDC
```

is provided by the Domain Controller.

In this laboratory:

```text
DC01
```

acts as the KDC for:

```text
lab.local
```

The KDC relies on Active Directory identity information.

Conceptually:

```text
KDC
 ↓
Active Directory
 │
 ├── users
 ├── computer accounts
 ├── service accounts
 ├── SPNs
 ├── group information
 └── Kerberos key material
```

# 9. Two Logical Functions of the KDC

Kerberos defines two principal KDC exchanges.

The first is the:

```text
Authentication Service
AS
```

The second is the:

```text
Ticket Granting Service
TGS
```

Their responsibilities are different.

```text
Authentication Service
        ↓
issues a Ticket Granting Ticket

Ticket Granting Service
        ↓
issues tickets for individual services
```

Kerberoasting primarily abuses the second stage.

---

# 10. Normal Kerberos Flow

A simplified Kerberos V5 flow is:

```text
Client
   ↓
AS-REQ
   ↓
KDC
   ↓
AS-REP
   ↓
TGT
   ↓
client wants a service
   ↓
TGS-REQ
   ↓
KDC
   ↓
TGS-REP
   ↓
service ticket
   ↓
AP-REQ
   ↓
target service
```

Kerberoasting focuses on:

```text
TGS-REQ
   ↓
TGS-REP
```

rather than the initial authentication exchange.

The protocol architecture described here follows Kerberos V5 as defined by RFC 4120 and the Windows-specific Kerberos extensions documented by Microsoft in [MS-KILE].

---

# 11. Initial Authentication — AS-REQ

The client initially requests a Ticket Granting Ticket using:

```text
KRB_AS_REQ
```

commonly called:

```text
AS-REQ
```

Conceptually:

```text
Client
   │
   │ AS-REQ
   ▼
KDC Authentication Service
```

The request identifies the client principal and requests credentials that can later be used with the Ticket Granting Service.

---

# 12. Kerberos Preauthentication

Normal Active Directory user accounts usually require Kerberos preauthentication.

The client must demonstrate possession of appropriate credential-derived key material.

Conceptually:

```text
client credential
        ↓
Kerberos key
        ↓
preauthentication data
        ↓
KDC validates proof
```

Only after successful validation can the normal authentication exchange continue.

The configuration where preauthentication is disabled is central to:

```text
T1558.004 — AS-REP Roasting
```

which is documented separately.

---

# 13. AS-REP

If the KDC accepts the authentication request, it returns:

```text
KRB_AS_REP
```

or:

```text
AS-REP
```

The response gives the client:

```text
Ticket Granting Ticket
```

and information required to establish the client/TGS security context.

Conceptually:

```text
AS-REQ
   ↓
KDC validates client
   ↓
AS-REP
   ↓
TGT
+
client/TGS session key
```

---

# 14. The Ticket Granting Ticket

The:

```text
TGT
```

does not authenticate the user directly to an application such as SQL Server or a file server.

Its purpose is to allow the client to obtain additional tickets.

Conceptually:

```text
domain authentication
       ↓
TGT
       ↓
ability to request
service tickets
```

This is a key part of Kerberos Single Sign-On.

---

# 15. The krbtgt Account

In Active Directory, the special account:

```text
krbtgt
```

is associated with the Kerberos Ticket Granting Service.

The protected portion of a TGT is secured using KDC-controlled key material associated with this identity.

Conceptually:

```text
KDC
 ↓
krbtgt key material
 ↓
TGT protection
```

The client can possess the TGT without being able to arbitrarily modify its protected contents.

---

# 16. Ticket Cache on Windows

On a Windows client, Kerberos tickets are associated with the Windows logon session and cached by the Kerberos security subsystem.

Conceptually:

```text
Windows logon
      ↓
TGT obtained
      ↓
ticket cache
      ↓
service tickets obtained later
```

This matters defensively because:

```text
service access
```

does not always imply:

```text
new TGS request
```

If a valid service ticket is already cached, the client may reuse it without asking the KDC for another one.

Therefore:

```text
absence of a new 4769
```

does not necessarily mean:

```text
service was not accessed
```

---

# 17. Services Need Kerberos Identities

When a client accesses a Kerberos-aware service, the KDC needs to know:

```text
which identity represents that service
```

Kerberos solves this using:

```text
Service Principal Names
```

or:

```text
SPNs
```

---

# 18. What an SPN Is

An SPN is a unique identifier for a service instance.

Conceptually:

```text
service class
+
host
+
optional port / service instance
```

An illustrative example is:

```text
MSSQLSvc/sql01.lab.local:1433
```

This is only an example of SPN structure.

The public repository uses:

```text
<SERVICE_SPN>
```

for the actual controlled laboratory value.

---

# 19. SPN Structure

A typical SPN follows a structure conceptually similar to:

```text
serviceclass/host:port
```

Examples include:

```text
HTTP/web01.lab.local

CIFS/files01.lab.local

MSSQLSvc/sql01.lab.local:1433
```

The exact syntax depends on the service.

The SPN allows Kerberos to map:

```text
requested network service
```

to:

```text
Active Directory security principal
```

---

# 20. SPN-to-Account Mapping

An SPN is stored in Active Directory in the:

```text
servicePrincipalName
```

attribute of an account object.

Conceptually:

```text
<SERVICE_SPN>
      ↓
Active Directory search
      ↓
account object
      ↓
<SERVICE_ACCOUNT>
```

Kerberos uses this relationship to determine which long-term service key must protect the ticket.

---

# 21. Why SPN Uniqueness Matters

A given SPN should identify one service identity.

If multiple objects incorrectly contain the same SPN, Kerberos cannot reliably determine which identity represents the service.

Therefore:

```text
SPN
 ↓
one service-account mapping
```

is an important directory-integrity requirement.

SPN hygiene is therefore both:

```text
an operational requirement
```

and:

```text
a security requirement
```

---

# 22. The Service Does Not Need to Be Running for Ticket Issuance

An important point in the laboratory is that:

```text
the service represented by the SPN
does not need to be operational
for the KDC to issue the ticket
```

The KDC is interested in:

```text
Does the SPN exist?
Which account owns it?
Can a ticket be generated for that principal?
```

It does not need to verify:

```text
Is SQL Server currently listening on TCP/1433?
```

before issuing the service ticket.

Conceptually:

```text
TGS-REQ
      ↓
SPN exists in AD
      ↓
service account found
      ↓
ticket issued
```

The application itself may later be unavailable, but that does not prevent the ticket-request phase.

This property is particularly relevant to Kerberoasting.

---

# 23. How the Laboratory Finds SPNs

The first stage performed by:

```text
impacket-GetUserSPNs
```

is service-account discovery.

The repository's controlled execution performs an authenticated:

```text
LDAP query
```

against Active Directory.

Conceptually:

```text
Kali-ATK01
      ↓
valid domain credentials
      ↓
LDAP
      ↓
DC01 / Active Directory
      ↓
search account objects
      ↓
servicePrincipalName attribute
      ↓
accounts with SPNs
```

This is not yet the Kerberos ticket-request stage.

---

# 24. LDAP Enumeration Is Not a 4769

The SPN-discovery operation and the TGS request are separate operations.

Conceptually:

```text
LDAP
 ↓
discover SPN/account
```

followed later by:

```text
Kerberos
 ↓
request service ticket
```

Therefore:

```text
SPN enumeration
```

does not by itself mean that:

```text
Event ID 4769
```

must already have been generated for the target service.

The `4769` becomes relevant when the KDC processes the actual service-ticket request.

---

# 25. Why Enumeration Is Difficult to Treat as Malicious

Reading directory attributes is normal Active Directory behavior.

Applications, administrators, management tools and domain clients query LDAP constantly.

Therefore:

```text
LDAP query for SPN
```

is not proof of:

```text
Kerberoasting
```

The value appears when LDAP enumeration is correlated with later ticket-request behavior.

---

# 26. Traditional User-Based Service Accounts

A service can run under a normal domain user account configured as a service identity.

Conceptually:

```text
domain user account
      ↓
servicePrincipalName
      ↓
service identity
```

These traditional service accounts are historically important to Kerberoasting because their credentials are frequently:

```text
human-managed
```

and sometimes configured with:

```text
PasswordNeverExpires
```

---

# 27. Computer Accounts and Service Accounts Are Different Risk Profiles

Computer accounts can also own SPNs.

However, their credentials are normally managed automatically by Windows and are high entropy.

Traditional user-based service accounts may instead use manually selected passwords.

Therefore:

```text
SPN on account
```

does not automatically mean:

```text
equally valuable Kerberoasting target
```

The actual risk depends heavily on the credential quality and privilege level of the account behind the SPN.

---

# 28. Long-Term Kerberos Keys

A Kerberos service requires long-term cryptographic key material.

For a traditional user-based service account, those keys are ultimately derived from the account's password.

Conceptually:

```text
service-account password
        ↓
Kerberos string-to-key processing
        ↓
long-term Kerberos key
```

Different encryption types produce different long-term keys.

Examples include:

```text
RC4-HMAC
AES128
AES256
```

---

# 29. Why the Service Account Password Is Security-Critical

The KDC must create a ticket that:

```text
the client can carry
```

but:

```text
the target service can decrypt
```

Therefore:

```text
KDC
 ↓
service-account long-term key
 ↓
encrypt ticket
 ↓
client receives ticket
 ↓
client presents ticket to service
 ↓
service uses its own key
 ↓
ticket decrypted
```

The requesting client does not need to know the service account's password.

That is a normal and necessary property of Kerberos.

But it also means that the client obtains ciphertext protected with key material derived from that service account.

---

# 30. TGS-REQ

When the client wants a ticket for a service, it sends:

```text
KRB_TGS_REQ
```

or:

```text
TGS-REQ
```

The request conceptually contains:

```text
TGT
+
Authenticator
+
requested service principal
```

The flow is:

```text
Client
   │
   │ TGS-REQ
   ▼
KDC Ticket Granting Service
```

---

# 31. What the TGS-REQ Proves

The client is effectively telling the KDC:

```text
I possess valid Kerberos credentials
and I want a ticket for this service.
```

The KDC then evaluates the supplied Kerberos material.

This is important because Kerberoasting does not necessarily involve an unauthenticated requester.

The requester can be:

```text
a perfectly valid low-privileged domain user
```

---

# 32. The Authenticator

The TGS request includes a Kerberos Authenticator.

The Authenticator is protected using the security context associated with the TGT.

Conceptually:

```text
TGT
+
fresh Authenticator
      ↓
KDC
      ↓
validate requesting client
```

This helps provide freshness and prevents a simple copied ticket from being sufficient by itself for arbitrary replay of protocol messages.

---

# 33. KDC Validates the TGT

When the TGS request arrives, the KDC:

```text
receives TGS-REQ
      ↓
identifies the TGT
      ↓
decrypts / validates TGT
      ↓
validates ticket lifetime
      ↓
validates Authenticator
      ↓
identifies requesting principal
```

If these checks succeed, the KDC can proceed with the service-ticket request.

---

# 34. KDC Resolves the Requested SPN

The request identifies the target service.

The KDC then resolves that identity through Active Directory.

Conceptually:

```text
requested SPN
      ↓
Active Directory
      ↓
servicePrincipalName search
      ↓
account object
      ↓
<SERVICE_ACCOUNT>
```

The account object provides the security identity and Kerberos-key context required for the service ticket.

---

# 35. TGS Encryption-Type Selection

The KDC must select a Kerberos encryption type that is compatible with the relevant participants and policy.

The exact selection process depends on:

```text
client-advertised encryption types
service-account supported encryption types
keys actually available for the service account
Domain Controller capabilities
domain/KDC policy
explicit account configuration
```

Conceptually:

```text
client capabilities
        +
service capabilities
        +
available service keys
        +
KDC policy
        ↓
compatible encryption type selected
```

This is much more precise than saying:

```text
the client simply chooses RC4
```

---

# 36. Supported Encryption Types in Active Directory

Active Directory uses the attribute:

```text
msDS-SupportedEncryptionTypes
```

to represent supported Kerberos encryption types for an account.

This attribute is a:

```text
bitmask
```

Relevant values include:

```text
0x4
RC4-HMAC

0x8
AES128

0x10
AES256
```

Combinations are produced by adding the relevant bits.

For example:

```text
0x18
=
0x8 + 0x10
=
AES128 + AES256
```

---

# 37. Important: msDS-SupportedEncryptionTypes Is Not TicketEncryptionType

Two sets of values must not be confused.

## Active Directory bitmask

```text
msDS-SupportedEncryptionTypes
```

uses capability bits such as:

```text
0x4  → RC4
0x8  → AES128
0x10 → AES256
```

## Kerberos ticket encryption type

Event ID `4769` records a protocol encryption-type identifier.

Relevant values include:

```text
0x17 → RC4-HMAC

0x11 → AES128-CTS-HMAC-SHA1-96

0x12 → AES256-CTS-HMAC-SHA1-96
```

Therefore:

```text
msDS-SupportedEncryptionTypes = 4
```

and:

```text
TicketEncryptionType = 0x17
```

both relate to RC4, but they are:

```text
different fields
using different numbering systems
```

This distinction is important when reading laboratory evidence.

---

# 38. Deliberately Vulnerable RC4 Configuration in the Laboratory

The controlled laboratory temporarily configures the service account to support RC4.

Conceptually:

```text
<SERVICE_ACCOUNT>
      ↓
msDS-SupportedEncryptionTypes
      ↓
RC4 enabled for controlled test
```

This configuration is deliberately insecure.

It exists only to make the RC4 Kerberoasting behavior observable.

It is not a production recommendation.

---

# 39. Modern Windows RC4 Context

RC4 is legacy Kerberos encryption.

Current Windows security hardening increasingly expects:

```text
AES
```

for supported configurations.

As of the July 2026 Windows security-update enforcement phase, Windows Domain Controllers apply stronger restrictions to RC4-based Kerberos service-ticket issuance.

Therefore the laboratory RC4 configuration should be understood as:

```text
explicit controlled legacy configuration
```

created for:

```text
detection testing
```

and not as a normal recommended Active Directory configuration.

After evidence collection, the safer state is restored.

---

# 40. TGS-REP

After the KDC validates the requester, resolves the SPN and selects the required cryptographic context, it returns:

```text
KRB_TGS_REP
```

or:

```text
TGS-REP
```

Conceptually:

```text
TGS-REQ
   ↓
KDC validates request
   ↓
service identity resolved
   ↓
service ticket generated
   ↓
TGS-REP
   ↓
client
```

The response contains:

```text
new service ticket
+
client-visible encrypted reply information
```

These two protected components must not be confused.

---

# 41. Two Different Cryptographic Protections Inside TGS-REP

A `TGS-REP` contains conceptually different cryptographic relationships.

```text
KRB_TGS_REP
 │
 ├── Ticket
 │      ↓
 │   encrypted for the
 │   target service
 │
 └── EncTGSRepPart
        ↓
     encrypted for the client
```

They use different keys.

---

# 42. The Client-Side Encrypted Part

The:

```text
EncTGSRepPart
```

contains information required by the requesting client, including the newly issued client/service session-key information.

According to Kerberos V5, this encrypted reply portion is protected using:

```text
the sub-session key from the
TGS Authenticator
```

if the client supplied one.

Otherwise, it is protected using:

```text
the session key from the TGT
```

Conceptually:

```text
TGS Authenticator sub-session key
             │
             │ if present
             ▼
       EncTGSRepPart

otherwise:

TGT session key
      ↓
EncTGSRepPart
```

This portion is intended to be usable by the client.

---

# 43. The Service Ticket Uses a Different Key

The actual service ticket is different.

In the normal service-ticket case relevant to Kerberoasting, its protected portion is encrypted using long-term key material associated with the requested service principal.

Conceptually:

```text
requested SPN
      ↓
Active Directory
      ↓
service account
      ↓
service long-term Kerberos key
      ↓
Ticket.enc-part
```

Therefore:

```text
EncTGSRepPart
        ≠
service-ticket encrypted part
```

The client must be able to use the first.

The target service must be able to decrypt the second.

---

# 44. Why This Distinction Matters for Kerberoasting

Kerberoasting targets the cryptographic relationship:

```text
service account
      ↓
long-term Kerberos key
      ↓
encrypted service ticket
```

It does not depend on breaking the temporary client/TGS session-key protection around:

```text
EncTGSRepPart
```

This is why understanding the internal structure of `TGS-REP` matters.

---

# 45. The Client Normally Cannot Decrypt the Service Ticket

The service ticket is intended for:

```text
the target service
```

Conceptually:

```text
KDC
 ↓
service key
 ↓
encrypted ticket
 ↓
client
 ↓
transport only
 ↓
service
 ↓
service key
 ↓
decrypt ticket
```

The client does not need the service account's long-term key.

It only needs to carry the ticket to the service.

---

# 46. Session Key Between Client and Service

The ticket contains a session key generated for communication between:

```text
client
```

and:

```text
service
```

The KDC provides the necessary session-key information to both parties through differently protected structures.

Conceptually:

```text
                    KDC
                     │
            client/service session key
                ┌────┴────┐
                │         │
                ▼         ▼
       client-visible   service ticket
        encrypted part      │
                │           │
                ▼           ▼
             client       service
```

The long-term service password/key is therefore not used to encrypt every application message.

It protects the Kerberos ticket that securely conveys the session information to the service.

---

# 47. Client Presents the Ticket to the Service

Normal Kerberos authentication continues using:

```text
KRB_AP_REQ
```

or:

```text
AP-REQ
```

Conceptually:

```text
client
   ↓
service ticket
+
Authenticator
   ↓
AP-REQ
   ↓
service
```

The service uses its long-term Kerberos key to decrypt the service ticket.

---

# 48. Service Decrypts the Ticket

The service conceptually performs:

```text
receive AP-REQ
      ↓
extract service ticket
      ↓
decrypt ticket
using service key
      ↓
obtain client/service session key
      ↓
validate Authenticator
      ↓
identify client
```

The service can then build the authenticated security context required by the application.

---

# 49. PAC and Windows Authorization Information

Windows Kerberos tickets commonly contain authorization information in a:

```text
Privilege Attribute Certificate
PAC
```

The PAC can contain information associated with the authenticated domain identity.

Conceptually:

```text
Active Directory identity
        ↓
authorization information
        ↓
PAC
        ↓
Kerberos ticket
```

This can include information that Windows services use when creating an authorization context.

Kerberoasting does not primarily target the PAC.

Its primary target is the cryptographic protection associated with the service account's long-term key.

---

# 50. Authentication Is Not Authorization

Possessing a valid service ticket proves an authenticated relationship.

It does not necessarily grant:

```text
unrestricted access
```

The target application still performs authorization.

Conceptually:

```text
Kerberos authentication
        ↓
identity established
        ↓
application authorization
        ↓
allowed or denied action
```

This explains why being able to request a service ticket does not mean that the requesting user is allowed to perform every operation provided by the service.

---

# 51. The Point Where Kerberoasting Diverges From Normal Use

Normal behavior is:

```text
authenticated user
      ↓
valid TGT
      ↓
TGS-REQ
      ↓
service ticket
      ↓
AP-REQ
      ↓
use service
```

Kerberoasting changes what happens after ticket acquisition:

```text
authenticated user
      ↓
valid TGT
      ↓
TGS-REQ
      ↓
service ticket
      ↓
retain encrypted ticket material
      ↓
offline password testing
```

The KDC part can be identical.

---

# 52. Kerberoasting Does Not Require a KDC Vulnerability

The KDC can receive:

```text
valid TGT
valid Authenticator
valid requested SPN
```

and produce:

```text
valid service ticket
```

This is expected behavior.

Therefore the attack does not require:

```text
malformed protocol messages
```

or:

```text
KDC exploitation
```

The weakness is the exposure of password-derived ticket material combined with a recoverable service-account secret.

---

# 53. A Low-Privileged User Can Be Enough

A normal authenticated domain account can generally request service tickets for service principals it needs to authenticate to.

Therefore the ticket-request stage does not necessarily require:

```text
Domain Admin
```

Conceptually:

```text
ordinary domain user
      ↓
valid TGT
      ↓
TGS request for existing SPN
      ↓
KDC issues service ticket
```

This is why the service account's credential strength must not depend on the assumption:

```text
only privileged users can obtain its ticket
```

---

# 54. What the Attacker Actually Obtains

The attacker obtains:

```text
encrypted Kerberos service-ticket material
```

The attacker does **not** initially obtain:

```text
plaintext service password
```

and does not necessarily obtain:

```text
service-account long-term key directly
```

Instead:

```text
ciphertext
+
known Kerberos structure
```

provides a target against which candidate keys can be tested.

---

# 55. RC4-HMAC and the NT Hash

For Kerberos encryption type:

```text
etype 23
```

represented in Windows Event ID `4769` as:

```text
0x17
```

the service's RC4-HMAC long-term key is closely tied to the Windows:

```text
NT hash
```

of the account password.

Conceptually:

```text
service-account password
        ↓
NT hash
        ↓
RC4 Kerberos long-term key
        ↓
service-ticket encryption
```

This is one reason RC4 service tickets have historically been attractive Kerberoasting targets.

---

# 56. Hashcat Representation

The controlled laboratory exports the ticket material in a representation compatible with password-testing tools.

For RC4-HMAC service tickets, the output begins conceptually with:

```text
$krb5tgs$23$...
```

The number:

```text
23
```

is the decimal Kerberos etype number corresponding to:

```text
0x17
```

in Windows Event ID `4769`.

Therefore:

```text
Hashcat-style format:
23
```

and:

```text
Windows event:
0x17
```

refer to the same Kerberos encryption type.

---

# 57. Offline Password Testing

After the ticket is obtained, password candidates can be tested locally.

Conceptually:

```text
password candidate
      ↓
derive candidate service key
      ↓
test candidate against
ticket cryptographic material
      │
      ├── invalid
      │      ↓
      │ next candidate
      │
      └── valid
             ↓
       password recovered
```

This is:

```text
offline
```

because DC01 is no longer required for each candidate.

---

# 58. Hashcat and Wazuh Visibility

The laboratory uses:

```text
Hashcat
```

on:

```text
Kali-ATK01
```

after the service ticket has already been retrieved.

Conceptually:

```text
DC01
 ↓
one TGS request
 ↓
ticket returned
 ↓
Kali
 ↓
Hashcat
 ↓
candidate 1
candidate 2
candidate 3
candidate 4
...
```

Only the first part necessarily involves the Domain Controller.

---

# 59. Why the Account Does Not Lock Out

The service account is not being repeatedly authenticated to DC01 for each candidate.

Therefore:

```text
candidate 1
candidate 2
candidate 3
...
```

do not produce:

```text
one failed logon per candidate
```

against Active Directory.

Consequently:

```text
Account Lockout Threshold
```

does not protect against the offline candidate-testing loop.

This is a crucial distinction between Kerberoasting and online password guessing.

---

# 60. Why Thousands of 4625 Events Do Not Appear

An online password attack may look like:

```text
candidate
 ↓
DC
 ↓
failure

candidate
 ↓
DC
 ↓
failure
```

producing authentication failures.

Kerberoasting instead looks like:

```text
one successful TGS request
        ↓
ticket leaves DC
        ↓
offline testing
```

Therefore Windows does not receive:

```text
thousands of failed service-account logons
```

during the cracking phase.

---

# 61. The Most Important Visibility Gap

The KDC can observe:

```text
TGS request
```

It cannot observe:

```text
the attacker's intention
```

and after issuing the ticket it cannot observe:

```text
every offline password candidate
```

Therefore:

```text
4769
```

is evidence of:

```text
service-ticket issuance
```

not:

```text
password cracking
```

---

# 62. RC4 Is Not Required for Kerberoasting

It would be incorrect to state:

```text
Kerberoasting requires RC4
```

Kerberoasting can also target service-ticket material protected with:

```text
AES
```

The distinction is:

```text
RC4
 ↓
legacy and particularly attractive

AES
 ↓
stronger password-derived key process
 ↓
offline testing still conceptually possible
```

Therefore:

```text
AES reduces risk
```

but:

```text
AES does not make weak passwords safe
```

---

# 63. AES Service Keys

For AES Kerberos encryption, long-term key generation involves password-based Kerberos string-to-key processing.

Conceptually:

```text
service-account password
        ↓
salt / Kerberos parameters
        ↓
password-based key derivation
        ↓
AES128 or AES256 key
```

The resulting ticket can be encrypted using:

```text
AES128
```

or:

```text
AES256
```

---

# 64. Why AES Is Better

AES-based Kerberos requires more expensive password-derived key computation than the legacy RC4 path.

Therefore:

```text
RC4
 ↓
cheaper password-candidate verification

AES
 ↓
more computationally expensive
candidate verification
```

This increases the attacker's cost.

But the correct security model is:

```text
AES
+
high-entropy service credential
```

not:

```text
AES
+
weak password
=
safe
```

---

# 65. Password Entropy Is a Major Security Boundary

Kerberoasting is an offline password-recovery problem.

Once the ticket is available:

```text
rate limiting
account lockout
network IDS
DC authentication failures
```

do not control the candidate loop.

Therefore the strongest direct protection is:

```text
a secret that is impractical to guess
```

Conceptually:

```text
short human password
      ↓
small/predictable candidate space
      ↓
higher recovery risk
```

versus:

```text
long random secret
      ↓
extremely large candidate space
      ↓
offline recovery becomes impractical
```

---

# 66. Complexity Is Not the Same as Entropy

A password such as:

```text
Summer2026!Service
```

can satisfy traditional complexity requirements.

It still contains:

```text
dictionary words
common capitalization
predictable year
predictable symbol
human pattern
```

Therefore:

```text
looks complex
```

does not necessarily mean:

```text
cryptographically strong
```

Service accounts generally have no usability requirement for a human-memorable password.

---

# 67. Manually Managed Service-Account Passwords

If a traditional user-based service account must be used, the password should be:

```text
long
random
unique
machine-generated
```

MITRE ATT&CK guidance recommends strong service-account passwords and gives:

```text
25+ characters
```

as an ideal minimum-length reference.

The more important principle is:

```text
high entropy
```

rather than merely achieving a particular complexity checklist.

---

# 68. Why Old Service Passwords Are Dangerous

Traditional service accounts are often configured with:

```text
PasswordNeverExpires
```

because administrators fear that credential changes will break:

```text
services
scheduled tasks
applications
database connectors
scripts
application pools
legacy systems
```

This can create accounts whose passwords remain unchanged for years.

Conceptually:

```text
SPN
+
old human-generated password
+
PasswordNeverExpires
      ↓
long-lived Kerberoasting risk
```

---

# 69. Password Rotation

Credential rotation reduces the amount of time for which compromised service-account credentials remain useful.

A controlled lifecycle should look like:

```text
credential created
      ↓
deployed to service
      ↓
monitored
      ↓
rotated
      ↓
new credential deployed
      ↓
old credential retired
```

However, manual rotation alone is not the ideal solution.

Poorly planned rotations can cause service outages.

---

# 70. Why Arbitrary Frequent Manual Rotation Is Not Enough

The correct recommendation is not simply:

```text
change the password constantly
```

If administrators cannot reliably update every dependency, aggressive manual rotation may cause:

```text
service failures
outages
emergency rollback
PasswordNeverExpires
```

A mature environment requires:

```text
service ownership
dependency inventory
credential vaulting
automated deployment
controlled rotation
health validation
rollback planning
```

Where possible, managed service accounts provide a stronger model.

---

# 71. Group Managed Service Accounts

A:

```text
Group Managed Service Account
```

or:

```text
gMSA
```

is a Windows/Active Directory service identity whose password management is performed automatically.

Conceptually:

```text
Active Directory
      ↓
managed service identity
      ↓
high-entropy generated credential
      ↓
authorized hosts retrieve credential
      ↓
Windows manages lifecycle
```

The administrator does not need to manually choose or routinely type the service password.

---

# 72. gMSA Credential Strength

Microsoft documents gMSA credentials as:

```text
240-byte randomly generated passwords
```

Windows manages their lifecycle automatically.

The default password-change interval is:

```text
30 days
```

unless configured differently at account creation.

This makes the credential fundamentally different from a traditional human-created service password.

---

# 73. Why gMSA Strongly Reduces Kerberoasting Risk

A service ticket can still be requested for a gMSA-backed service.

Kerberos itself has not disappeared.

What changes is the usefulness of the ticket as an offline password target.

Conceptually:

```text
traditional service account
        ↓
human-generated password
        ↓
ticket
        ↓
dictionary candidate space
```

versus:

```text
gMSA
 ↓
240-byte random managed secret
 ↓
ticket
 ↓
impractical password-search space
```

Therefore the defensive goal is not:

```text
prevent every ticket from being issued
```

but:

```text
make the ticket a poor password-recovery target
```

---

# 74. Automatic Rotation Reduces Operational Pressure

Traditional service-account management often produces:

```text
password change
      ↓
application failure risk
      ↓
administrator avoids rotation
```

gMSA changes the model:

```text
Windows manages credential
      ↓
authorized systems retrieve it
      ↓
rotation occurs automatically
```

This reduces one of the main reasons that service-account credentials become extremely old.

---

# 75. Prefer Managed Service Identities Where Supported

A good decision hierarchy is:

```text
Can the application use gMSA?
        │
        ├── yes
        │     ↓
        │   use gMSA
        │
        └── no
              ↓
   evaluate sMSA or another
   managed service identity
              ↓
   if manually managed account
   remains necessary:
              ↓
   long random credential
   + managed rotation
```

Application compatibility must be tested before migration.

---

# 76. Least Privilege

Credential strength controls:

```text
probability of password recovery
```

Privilege controls:

```text
impact if recovery occurs
```

Both matter.

Conceptually:

```text
Kerberoasting succeeds
       ↓

low-privileged account
       ↓
limited blast radius
```

versus:

```text
Kerberoasting succeeds
       ↓

Domain Admin service account
       ↓
potential domain compromise
```

---

# 77. Service Accounts Should Not Be Domain Admins Without Strong Justification

Service identities generally should not belong to:

```text
Domain Admins
Enterprise Admins
Schema Admins
```

unless there is an exceptional and documented technical requirement.

A service account should receive:

```text
only the rights needed
for its actual workload
```

This principle reduces the value of a recovered credential.

---

# 78. Restrict Interactive Logon

A service account usually exists for:

```text
background service execution
```

rather than:

```text
human interactive access
```

Where application compatibility permits, service identities should not be allowed to perform unnecessary:

```text
interactive logon
RDP logon
```

If the password is recovered, this removes additional paths of abuse.

---

# 79. Restrict Where the Account Can Be Used

A service account should ideally be usable only where required.

Conceptually:

```text
service identity
      ↓
approved service hosts
```

rather than:

```text
service identity
      ↓
arbitrary hosts across domain
```

This reduces blast radius.

---

# 80. SPN Hygiene

Organizations should maintain an inventory mapping:

```text
SPN
 ↓
service
 ↓
owning account
 ↓
host
 ↓
business owner
 ↓
password-management model
 ↓
encryption support
 ↓
privilege level
```

SPNs should not be allowed to accumulate indefinitely without ownership.

---

# 81. Stale SPNs

An application may be retired while the account and SPN remain.

For example:

```text
service decommissioned
      ↓
SPN remains
      ↓
old service account remains enabled
      ↓
old password remains
      ↓
unnecessary Kerberoasting surface
```

Therefore:

```text
service lifecycle
```

and:

```text
SPN lifecycle
```

should remain aligned.

---

# 82. Password-Age Monitoring

An especially useful risk indicator is:

```text
SPN-bearing account
+
password age
```

Accounts with credentials unchanged for years deserve additional attention.

Risk becomes greater when combined with:

```text
PasswordNeverExpires
RC4
high privilege
interactive logon rights
large system access
```

A mature Active Directory environment should know:

```text

```

Events such as:

Suppose a domain generates:

```text

```

Then:

```text

```

After remediation:

```text

```

```text

      ↓
```

# 85. 2026 RC4 Hardening Context

Current Windows security updates have moved Kerberos service-ticket behavior toward AES and stronger restrictions on RC4.

The July 2026 enforcement phase means administrators should treat remaining RC4 dependencies as:

```text
legacy compatibility issues
```

that should be explicitly identified and remediated.

The laboratory intentionally creates an RC4-compatible service identity for controlled testing.

After the test:

```text
RC4 configuration
```

must be removed or replaced with:

```text

```

where supported.

# 86. Password Rotation Can Also Regenerate AES Keys

Kerberos AES keys are generated when appropriate account password/key material is established.

Legacy accounts that have not had their password updated for a very long time can lack appropriate modern key material in some configurations.

Therefore migration can involve:

```text

      ↓
rotate service credential
      ↓
new Kerberos keys generated
      ↓
verify service
      ↓
remove RC4 dependency
```

This is another reason ancient service credentials should not remain untouched indefinitely.


From the KDC perspective, the two requests may both be:

```text

valid
successful
protocol-compliant
```

The KDC does not know the human intention behind the request.

# 107. Why "User Connected From Outside" Is More Complicated Than It Appears

A remote user may enter the environment through:

```text
VPN
RDP
VDI
jump host
remote-access gateway
```

The IP address recorded by the KDC depends on where the actual Kerberos request originates.

For example:

```text
Internet user
      ↓
VPN
      ↓
internal endpoint
      ↓
Kerberos
      ↓
DC01
```

The KDC may observe the:

```text
VPN-assigned / internal client address
```

rather than the user's original public Internet address.

---

# 108. RDP Example

Consider:

```text
external user
      ↓
VPN
      ↓
RDP
      ↓
WS01
      ↓
access SQL service
```

The Kerberos ticket request can originate from:

```text
WS01
```

because that is where the user's Windows session and Kerberos client exist.

DC01 may therefore observe:

```text
WS01
      ↓
TGS-REQ
```

not:

```text
original external public IP
```

---

# 109. VDI Example

The same problem exists with VDI.

```text
remote employee
      ↓
VDI infrastructure
      ↓
Windows virtual desktop
      ↓
Kerberos request
      ↓
DC01
```

The requesting address visible to the KDC can correspond to the virtual desktop.

Therefore:

```text
Client Address
```

must be interpreted with knowledge of:

```text
remote-access architecture
```

# 110. Why IP Allowlists Are Useful in the Lab but Insufficient in Production

The laboratory contains only a few known systems.

Therefore:

```text

```

provides useful high-confidence context.

In production, however:

```text

```

can itself be compromised.

Likewise:

```text
approved jump host
```

can be used by an attacker with stolen credentials.

Therefore:

```text

```

should be:

```text
one feature
```

not:

```text

```

# 121. Detection Alone Cannot Solve Kerberoasting

This technique demonstrates an important Detection Engineering principle:

```text
not every threat can be solved
by writing a better SIEM rule
```

The KDC must issue legitimate service tickets.

Therefore:

```text
perfectly block all TGS requests
```

is not a viable security strategy.

The stronger security question is:

```text
If an attacker obtains the ticket,
how useful is it?
```

# 122. Prevention and Detection Solve Different Problems

Detection asks:

```text

```

Prevention asks:

```text

realistically be recovered?
```

A mature defense requires both.

# 125. Why MFA Does Not Directly Fix the Service-Ticket Problem

MFA is extremely useful for protecting human interactive authentication.

However, the service ticket itself is protected using:

```text

```

or:


Kerberoasting must therefore also be addressed through service-identity security.

```text
      ├───────────────────────────────┐
      │                               │
      ▼                               ▼
LEGITIMATE USE                  KERBEROASTING
      │                               │
      ▼                               ▼
AP-REQ                         RETAIN TICKET
      │                               │
      ▼                               ▼

      │                        CANDIDATES
      ▼                               │

      │                       DERIVE CANDIDATE
      ▼                         SERVICE KEY

      │                               ▼
      ▼                         TEST AGAINST

AUTHORIZATION                         │
                              ┌───────┴────────┐
                              │                │
                           INVALID           VALID
                              │                │
                              ▼                ▼
                       NEXT CANDIDATE    SERVICE PASSWORD
                                           RECOVERED
```

The central technical conclusion is:

```text
Kerberoasting does not primarily exploit
a malformed Kerberos transaction.

It exploits the fact that a legitimate
authenticated principal can obtain a
legitimate service ticket whose encrypted
ticket portion is protected using long-term
key material associated with the service identity.
```

For that reason:

```text
detecting the TGS request
```

is only one part of the defense.

The stronger model is:

```text
MANAGED HIGH-ENTROPY SERVICE CREDENTIALS
        +
AES
        +
REMOVE RC4
        +
LEAST PRIVILEGE
        +
RESTRICT SERVICE-ACCOUNT USE
        +
SPN HYGIENE
        +
BASELINE NORMAL KERBEROS
        +
DETECT ABNORMAL TICKET COLLECTION
        +
CORRELATE LATER SERVICE-ACCOUNT USE
```

If the service identity uses a high-entropy automatically managed credential and minimum privileges, obtaining its service ticket becomes substantially less valuable even when the original TGS request cannot be reliably distinguished from legitimate Kerberos activity.
