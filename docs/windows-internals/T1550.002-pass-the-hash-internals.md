# T1550.002 — Pass the Hash Internals

## 1. Purpose

This document explains what happens internally during the Pass-the-Hash scenario reproduced in the laboratory.

The objective is not only to state that an NT hash was used instead of a plaintext password.

The objective is to understand why Windows accepts that operation, which cryptographic material is involved, how NTLM authentication works internally, how Windows converts a valid network authentication into a security context, why the operating system cannot directly distinguish password-based NTLM authentication from Pass-the-Hash, and how the authenticated identity is subsequently used to obtain remote execution.

The complete conceptual chain is:

```text
password
   ↓
NT hash
   ↓
NTLM credential material
   ↓
challenge-response authentication
   ↓
Windows validates response
   ↓
network logon
   ↓
access token
   ↓
authorization
   ↓
SMB administrative access
   ↓
Service Control Manager
   ↓
remote execution
   ↓
Windows telemetry
   ↓
Wazuh correlation
```

The Pass-the-Hash variation changes one critical part of this chain:

```text
Normal authentication:

password
   ↓
NT hash calculated
   ↓
NTLM calculations
   ↓
authentication


Pass-the-Hash:

NT hash already possessed
   ↓
NTLM calculations
   ↓
authentication
```

The attacker does not need to recover the original plaintext password.

The NT hash itself provides the secret material required to perform NTLM authentication calculations.

# 3. What Pass-the-Hash Actually Means

Pass-the-Hash does **not** mean that the attacker sends the NT hash directly to the server in place of a password field.

This is one of the most important concepts in the technique.

The network does not simply contain:

```text
Username: usuario.admin
Password: <NT hash>
```

Instead, the NT hash is used locally by the client as cryptographic secret material.

Conceptually:

```text
NT hash
   ↓
cryptographic calculations
   ↓
NTLM authentication response
   ↓
network
   ↓
DC01
```

Therefore:

```text
NT hash
```

and:

```text
NTLM response
```

are not the same thing.

The NT hash remains credential material.

The NTLM response is calculated from that credential material together with data from the authentication exchange.

---

# 4. Three Values That Must Not Be Confused

Pass-the-Hash is easier to understand if three different values are separated.

## Plaintext password

Example conceptually:

```text
password
```

This is the human-readable secret originally chosen by the user.

---

## NT hash

Windows derives credential material from the password.

Conceptually:

```text
password
    ↓
UTF-16LE encoding
    ↓
MD4
    ↓
NT hash
```

The NT hash is a:

```text
128-bit
```

value normally represented as:

```text
32 hexadecimal characters
```

---

## NTLM network response

During network authentication, Windows does not simply transmit the NT hash.

The NT hash is used to derive additional authentication material.

Conceptually:

```text
NT hash
    ↓
NTLM key derivation
    ↓
server challenge
+
client data
    ↓
NTLM challenge response
```

Therefore:

```text
password ≠ NT hash ≠ NTLM response
```

This distinction is fundamental.

---

# 5. How the NT Hash Is Derived

The NT hash is traditionally defined as:

```text
NT_hash = MD4(UTF-16LE(password))
```

The password is converted to its Unicode representation and then processed using MD4.

Conceptually:

```text
User password
      ↓
UTF-16LE
      ↓
MD4
      ↓
128-bit NT hash
```

For example:

```text
password
    ↓
NT hash
```

The NT hash is not salted.

This historical design property is one reason why possession of the hash is security-sensitive.

The hash is not merely a verifier used to compare passwords.

It is also secret material from which NTLM authentication values can be derived.

---

# 6. Why the Hash Is Authentication Material

In some authentication designs, possession of a password hash would not necessarily allow the holder to authenticate directly.

NTLM is different.

The NT hash participates as secret key material in the challenge-response calculations.

Therefore:

```text
Know password
      ↓
derive NT hash
      ↓
perform NTLM calculation
```

and:

```text
Already know NT hash
      ↓
perform same NTLM calculation
```

reach the same cryptographic stage.

This is the structural property abused by Pass-the-Hash.

---

# 7. Normal NTLM Authentication

A normal password-based NTLM authentication can be represented as:

```text
user enters password
        ↓
client derives NT hash
        ↓
client performs NTLM calculations
        ↓
server challenge incorporated
        ↓
authentication response generated
        ↓
response sent to server
        ↓
server validates response
```

The plaintext password is therefore used to obtain the NT hash.

After that point, the protocol calculations operate using derived credential material.

---

# 8. Pass-the-Hash Authentication

Pass-the-Hash starts further down the same chain.

```text
attacker already possesses NT hash
        ↓
no password recovery required
        ↓
NTLM calculations performed
        ↓
authentication response generated
        ↓
response sent to server
        ↓
server validates response
```

Therefore:

```text
Normal:

password
   ↓
NT hash
   ↓
NTLM


Pass-the-Hash:

stolen NT hash
   ↓
NTLM
```

The attacker bypasses the need to know:

```text
plaintext password
```

but does **not** bypass NTLM authentication.

A valid NTLM exchange still takes place.

---

# 9. Pass-the-Hash Is Not an Authentication Bypass

It is important not to describe the technique as:

```text
bypassing Windows authentication
```

Windows authentication still occurs.

The correct interpretation is:

```text
authentication occurs
```

but:

```text
the attacker possesses reusable authentication material
```

Conceptually:

```text
stolen secret
     ↓
valid protocol calculations
     ↓
Windows authentication succeeds
```

Windows behaves according to the protocol design.

---

```text
Kali-ATK01
```


That is not what occurs in this laboratory.

Conceptually, Impacket receives credential material representing:

```text

```

# 12. NTLM Message Architecture

At protocol level, NTLM uses three principal message types:

```text
NEGOTIATE_MESSAGE
CHALLENGE_MESSAGE
AUTHENTICATE_MESSAGE
```

They are commonly described as:

```text
Type 1
Type 2
Type 3
```

Conceptually:

```text
Client
   │
   │ NEGOTIATE_MESSAGE
   ▼
Server
   │
   │ CHALLENGE_MESSAGE
   ▼
Client
   │
   │ AUTHENTICATE_MESSAGE
   ▼
Server
```

These messages perform different functions.

---

# 13. NTLM NEGOTIATE_MESSAGE

The first message is:

```text
NEGOTIATE_MESSAGE
```

The client advertises capabilities relevant to NTLM authentication.

Conceptually:

```text
client
   ↓
supported NTLM capabilities
   ↓
NEGOTIATE_MESSAGE
   ↓
server
```

The message can contain negotiation flags describing functionality supported by the client.

At this point, the server has not yet validated the user's secret.

---

# 14. NTLM CHALLENGE_MESSAGE

The server responds with:

```text
CHALLENGE_MESSAGE
```

One of its critical elements is:

```text
ServerChallenge
```

The server challenge is:

```text
8 bytes
```

of challenge data for the authentication exchange.

Conceptually:

```text
DC01
   ↓
generate challenge
   ↓
CHALLENGE_MESSAGE
   ↓
Kali-ATK01
```

The challenge prevents authentication from consisting of a static password-derived value sent identically every time.

---

# 15. Target Information

The NTLM challenge can also include:

```text
TargetInfo
```

containing Attribute-Value pairs commonly referred to as:

```text
AV_PAIRs
```

These can communicate information relevant to the authentication context.

Conceptually:

```text
CHALLENGE_MESSAGE
      │
      ├── ServerChallenge
      └── TargetInfo
             │
             └── AV_PAIRs
```

This information participates in NTLMv2 response construction.

---

# 16. NTLM AUTHENTICATE_MESSAGE

The client processes the challenge and returns:

```text
AUTHENTICATE_MESSAGE
```

This message can contain information such as:

```text
user
domain
workstation
challenge responses
session-related information
```

The critical security point is:

```text
the response is transmitted
```

not:

```text
the plaintext password
```

and not simply:

```text
the raw NT hash
```

---

# 17. Modern NTLMv2 Calculation

The cryptographic explanation in this document uses NTLMv2.

The exact NTLM variant used in a particular execution should ideally be confirmed through the corresponding Windows fields or packet-level evidence rather than inferred only from:

```text
AuthenticationPackageName = NTLM
```

For NTLMv2, the derivation is more complex than:

```text
HMAC-MD5(NT_hash, server_challenge)
```

That expression is incomplete.

---

# 18. NTOWFv2 / ResponseKeyNT

The NT hash is first used to derive the NTLMv2 response key.

Conceptually:

```text
NT_hash =
MD4(UTF-16LE(password))
```

Then:

```text
ResponseKeyNT =
HMAC-MD5(
    NT_hash,
    Unicode(
        UpperCase(username) + domain
    )
)
```

This value is sometimes described using the NTLM specification terminology:

```text
NTOWFv2
```

Conceptually:

```text
password
   ↓
NT hash
   ↓
username + domain
   ↓
HMAC-MD5
   ↓
ResponseKeyNT
```

Pass-the-Hash becomes possible because the first secret input to this derivation is the NT hash itself.

---

# 19. Client Challenge

NTLMv2 also incorporates a challenge generated by the client.

Conceptually:

```text
ClientChallenge
```

This is different from:

```text
ServerChallenge
```

The authentication response therefore depends on information contributed by both sides.

---

# 20. Timestamp and AV Pairs

The NTLMv2 client data can also contain:

```text
timestamp
client challenge
target information
AV pairs
response-version information
```

Conceptually:

```text
ClientData
   │
   ├── response version
   ├── timestamp
   ├── client challenge
   └── AV_PAIR information
```

This structure forms the variable portion of the NTLMv2 challenge response.

---

# 21. NTProofStr

NTLMv2 calculates:

```text
NTProofStr
```

conceptually as:

```text
NTProofStr =
HMAC-MD5(
    ResponseKeyNT,
    ServerChallenge + ClientData
)
```

The resulting challenge response contains:

```text
NTProofStr
+
ClientData
```

Conceptually:

```text
ResponseKeyNT
        │
        ├───────────────┐
        │               │
        ▼               ▼
ServerChallenge     ClientData
        │               │
        └───────┬───────┘
                ▼
             HMAC-MD5
                ↓
           NTProofStr
                ↓
      NTLMv2 challenge response
```

---

# 22. SessionBaseKey

After calculating the proof value, NTLMv2 can derive:

```text
SessionBaseKey
```

conceptually as:

```text
SessionBaseKey =
HMAC-MD5(
    ResponseKeyNT,
    NTProofStr
)
```

This illustrates that NTLM authentication does more than compare a single hash.

A set of cryptographic keys and response values are derived from the underlying credential material.

---

# 23. Why Possessing the NT Hash Is Enough

The critical observation is:

```text
ResponseKeyNT
```

can be derived when the NT hash is already known.

The attacker therefore does not need:

```text
password
```

to calculate:

```text
ResponseKeyNT
```

because:

```text
NT hash
```

is already available.

Therefore:

```text
Legitimate user:

password
   ↓
NT hash
   ↓
ResponseKeyNT
   ↓
NTProofStr
   ↓
NTLM response


Pass-the-Hash:

NT hash
   ↓
ResponseKeyNT
   ↓
NTProofStr
   ↓
NTLM response
```

Both paths converge before the server receives the authentication response.

---

# 24. What Crosses the Network

This is the key distinction:

```text
plaintext password
```

does not simply cross the network.

Likewise:

```text
raw NT hash
```

is not simply transmitted as the authentication secret.

Instead:

```text
NTLM authentication structures
```

containing calculated response information cross the network.

Conceptually:

```text
Kali
 │
 │ NTLM AUTHENTICATE_MESSAGE
 │
 │ challenge response
 ▼
DC01
```

Therefore a packet capture does not simply reveal:

```text
Password = ...
```

or:

```text
NT_Hash = ...
```

as direct authentication fields.

---

# 25. Why DC01 Can Validate the Response

DC01 needs to determine whether the received NTLM response is cryptographically consistent with the credential material associated with:

```text
LAB\usuario.admin
```

Conceptually:

```text
received user/domain
       ↓
locate account
       ↓
obtain corresponding protected credential material
       ↓
calculate expected NTLM response
       ↓
compare
       │
       ├── mismatch
       │      ↓
       │ authentication failure
       │
       └── match
              ↓
       authentication succeeds
```

The server therefore validates the result of the cryptographic proof.

# 28. LSA and LSASS

Windows centralizes important authentication and security operations around:

```text
Local Security Authority
LSA
```

The associated user-mode process is:

```text
C:\Windows\System32\lsass.exe
```

LSASS participates in:

- authentication;
- interaction with authentication packages;
- creation of logon sessions;
- security-policy enforcement;
- domain authentication functions;
- management of security contexts.

The conceptual path is:

```text

        ↓

        ↓

        ↓

```

# 29. Active Directory on DC01

`DC01` runs:

```text
Active Directory Domain Services
```

Domain security principals such as:

```text
LAB\usuario.admin
```

belong to Active Directory.

The principal Active Directory database is:

```text
NTDS.dit
```

Therefore, the credential material associated with a domain account should not be described as an ordinary workstation-style local SAM account.

Conceptually:

```text
LAB\usuario.admin
      ↓
Active Directory
      ↓
directory account data
      ↓
credential-related material
```

---

# 30. Important SAM vs Active Directory Distinction

On a normal workstation or member server:

```text
local accounts
      ↓
SAM
```

On a Domain Controller:

```text
domain accounts
      ↓
Active Directory
      ↓
NTDS.dit
```

Therefore:

```text
LAB\usuario.admin
```

in this scenario is:

```text
a domain principal
```

not simply an ordinary local SAM user.

This distinction is important when explaining how the credential material was acquired before the Pass-the-Hash phase.

# 31. Authentication Success

When DC01 validates the NTLM response successfully, Windows accepts:

```text

```

as the authenticated identity.

What Windows knows at this point is conceptually:

```text
This client produced valid NTLM authentication
for LAB\usuario.admin
```

Windows does **not** receive evidence describing how the client obtained the underlying secret.

# 32. Windows Does Not Know That a Hash Was "Passed"

This is one of the most important internal concepts in the entire scenario.

Windows does not receive:

```text
PassTheHash = True
```

There is no authentication field equivalent to:

```text
CredentialSource = StolenHash
```

The server sees:

```text
NTLM exchange
      ↓
valid response
      ↓
authenticated identity
```

It does not see:

```text
how the client produced that response
```

# 40. Why This Token Is Crucial

After authentication succeeds, later Windows components do not ask:

```text

```

They evaluate:

```text

What groups does it belong to?
What privileges does it possess?
What object permissions does it have?
```

Therefore:

```text

            │
            └──────────────┐
                           ▼
                    authenticated token
                           ▲
            ┌──────────────┘
NTLM with reused NT hash
```

After this point, the downstream Windows authorization path is essentially the same.

Several parts of the chain can occur legitimately.

For example:

```text

```



- source host;
- source IP;
- account;
- asset criticality;
- whether NTLM use is expected;
- whether administrative shares are normally used;
- service name and path;
- process lineage;
- timing;
- preceding credential-access activity;
- subsequent commands.

# 101. Why NTLM Itself Is Not Malicious

NTLM is still used by legitimate Windows systems and applications in environments where Kerberos cannot be used or is not available.

Therefore:

```text
NTLM = attack
```

is false.

Likewise:

```text
NTLM + administrator = Pass-the-Hash
```

is also false.

The detection becomes meaningful through context.

# 102. Why Pass-the-Hash Is Difficult to Detect Directly

The protocol itself was designed to authenticate possession of the required secret-derived material.

Pass-the-Hash gives the attacker that material.

Therefore, from the protocol's perspective:

```text
proof is valid
```

The protocol does not solve:

```text
how did the client obtain the secret?
```

That is an endpoint and detection problem rather than part of the challenge-response proof itself.

# 107. Detection Engineering Interpretation

The complete cause-and-effect model is:

```text
credential material acquired
        ↓
NT hash becomes available
        ↓
client calculates valid NTLM response
        ↓
Windows validates authentication
        ↓
Windows creates network logon
        ↓
Windows creates authenticated security context
        ↓
Windows authorizes administrative operations
        ↓
SMB provides remote administrative access
        ↓
SCM creates service
        ↓
Windows creates SYSTEM processes
        ↓
Windows generates telemetry
        ↓
Wazuh evaluates rules
        ↓
Wazuh correlates events
        ↓
analyst attributes behavior to T1550.002
```

The central point is:

```text
Windows never directly observes
"the attacker passed a hash"
```

It observes the consequences of a valid authentication performed using credential material that the attacker already possessed.

---

# 108. Why This Matters Defensively

Without understanding the internal protocol, an analyst might memorize:

```text
4624 + NTLM = Pass-the-Hash
```

which is incorrect.

Understanding the protocol produces the correct model:

```text
NT hash
    ↓
client-side cryptographic calculation
    ↓
valid NTLM response
    ↓
Windows authentication succeeds
    ↓
Windows cannot determine secret origin
    ↓
4624
```

The detection challenge is therefore not:

```text
Did NTLM authenticate?
```

but:

```text
Is this NTLM authentication consistent with
legitimate use of the account and source host?
```

and:

```text
What occurred before and after the authentication?
```

The central technical conclusion is:

```text
Pass-the-Hash does not bypass NTLM.

It satisfies NTLM by using an already-obtained
NT hash as the secret material required to
calculate a valid authentication response.
```

Once Windows accepts that response, it creates an ordinary authenticated security context.

From that point forward:

```text
SMB
authorization
administrative shares
SCM
service creation
process execution
```

operate on that authenticated identity in essentially the same way they would after another successful NTLM authentication.

This is why the attack is difficult to identify from one isolated Windows event and why correlation between credential access, authentication, privilege assignment, administrative access, service creation, and process execution is essential.
