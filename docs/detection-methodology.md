# Detection Methodology

The project applies the same detection-engineering workflow to five controlled Active Directory scenarios:

1. Define the behavior to detect.
2. Identify the required Windows or Sysmon telemetry.
3. Execute the documented scenario in the isolated laboratory.
4. preserve the relevant timestamps and events.
5. Build or adapt the Wazuh rules.
6. Validate the generated alerts.
7. Map the observable behavior to MITRE ATT&CK.
8. Document confidence, false positives and detection boundaries.
9. Sanitize the evidence before publication.

---

## Telemetry Sources

| Source | Purpose |
|---|---|
| Windows Security Event Log | Authentication, privileges, process creation, object access and Kerberos activity |
| Windows System Event Log | Service Control Manager and service-creation telemetry |
| Sysmon | Optional process and network context |
| Wazuh Agent | Event collection and forwarding |
| Wazuh Manager | Decoding, rule evaluation, correlation and alert generation |
| Wazuh Dashboard | Search, validation and CSV export |

| Kerberoasting | `4769`, optional Sysmon Event ID `3` |
| AS-REP Roasting | `4768` |

## Detection Philosophy

The detections focus on observable behavior rather than relying only on tool names.

Relevant behaviors include:

- remote logons;
- NTLM authentication;
- special privileges;
- administrative share access;
- service creation;
- directory replication access;
- post-access process execution;
- RC4 Kerberos service-ticket requests;
- successful TGT requests without pre-authentication;
- repeated requests from one source.

A single event may be weak or ambiguous. Confidence increases when fields, identities, systems and timestamps can be correlated.

---

## Event, Alert and Attribution

| Layer | Meaning |
|---|---|
| Event | Native telemetry generated by Windows or Sysmon |
| Alert | Wazuh output after applying one rule or a correlation |
| Attribution | Analyst conclusion connecting the evidence to MITRE ATT&CK |

The repository does not claim that Wazuh observes hidden credential material directly.

For AS-REP Roasting, Wazuh observes the TGT request and its fields. It does not observe every offline password candidate or prove that password recovery succeeded.

---

## Evidence Handling

Public evidence must:

- preserve timestamps, Event IDs, rule IDs and relevant detection fields;
- remove complete SIDs and backend document identifiers;
- remove `full_log`, duplicated messages and unnecessary raw data;
- exclude passwords, tickets, hashes, potfiles and dictionaries;
- distinguish separate validation sessions;
- avoid manufacturing a one-to-one relationship that the timestamps do not demonstrate.

---

## Validation Criteria

A rule is considered validated when a supplied alert document contains:

- the expected rule ID;
- the expected event;
- the required field values;
- the expected MITRE mapping;
- a timestamp that can be traced to the relevant validation session.

Rule-ID validation coverage is different from per-execution detection coverage.

The AS-REP evidence validates all three custom rule IDs, but it does not support a detection percentage for the six visible command executions because they cannot all be mapped one-to-one to Windows events and alerts.
