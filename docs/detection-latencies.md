# Detection Latencies

This document summarizes the detection latency measurements observed during the controlled laboratory executions.

The goal is to show how long it took Wazuh to generate relevant alerts after each simulated attack started.

These metrics represent the behavior of this laboratory only. They are not production SOC metrics. The lab did not include concurrent legitimate user activity, real administrative noise or long-term traffic baselining.

## 1. Measurement Model

The project separates three concepts:

| Concept | Meaning |
|---|---|
| Attack start | Timestamp when the controlled scenario execution began |
| First observable signal | Earliest useful alert or event that indicates the chain has started |
| Highest-severity alert | Most severe alert generated by the scenario |
| Detection latency | Difference between attack start and the selected Wazuh alert timestamp |

## 2. Important Interpretation Note

A fast alert is not always the strongest alert.

For example, in the Pass-the-Hash scenario, rule `100011` can appear early because it detects NTLM network authentication. However, the strongest alert is rule `100033`, because it requires correlation with DCSync-like activity and privileged access.

Therefore, this document distinguishes between:

```text
first observable signal
```

and:

```text
highest-severity or highest-confidence alert
```

### Analyst interpretation

The RDP scenario is useful because it shows remote interactive access followed by post-access activity.

However, the analyst should avoid treating an RDP logon alone as malicious. RDP can be legitimate. The detection becomes more meaningful when it is combined with process execution such as:

```text
whoami.exe
hostname.exe
ipconfig.exe
cmd.exe
```

```text
rule.id:100011
```


| Execution | Attack Start (CEST) | Wazuh Alert `100011` (CEST) | Detection Latency | First Observable Signal | Highest-Severity Alert in Scenario |

| 02 | Jun 2, 2026 00:10:48 | Jun 2, 2026 00:10:58.051 | 10.051 s | `100011` NTLM network logon | `100033` / level 15 after correlation |
| 03 | Jun 2, 2026 00:10:56 | Jun 2, 2026 00:11:08.002 | 12.002 s | `100011` NTLM network logon | `100033` / level 15 after correlation |
| 04 | Jun 2, 2026 00:11:04 | Jun 2, 2026 00:11:15.101 | 11.101 s | `100011` NTLM network logon | `100033` / level 15 after correlation |

Average detection latency:

```text
11.056 s
```

### Important note about Pass-the-Hash timing

The table above measures the first useful NTLM network authentication signal, represented by rule `100011`.

The strongest Pass-the-Hash-related alert is not `100011`. The strongest alert is:

```text
rule.id:100033
```

Rule `100033` is slower by design because it depends on correlation. It requires DCSync-like activity detected by `100030` and privileged access detected by `100021` inside the configured timeframe.

Therefore:

```text
100011 = early signal
100033 = stronger correlated alert
```

### Analyst interpretation

A fast NTLM alert does not prove Pass-the-Hash. Windows does not tell Wazuh that a hash was used instead of a password.

The attribution is built from the chain:

```text
DCSync-like activity → NTLM network authentication → privileged session → remote activity
```

## 7. Why Latency Alone Is Not Enough

The fastest alert is not necessarily the best alert.

A low-level or medium-confidence alert may appear earlier than a high-confidence correlation alert. For detection engineering, both are useful:

| Alert Type | Value |
|---|---|
| Early signal | Helps begin investigation quickly |
| High-confidence correlation | Helps prioritize severity and response |
| Supporting telemetry | Helps explain what happened and reduce ambiguity |

## 8. Operational Use

A SOC analyst could use these measurements as follows:

1. Use early signals such as `100011` to start triage quickly.
2. Wait for correlated or higher-severity alerts such as `100033` before escalating as critical.
3. Review supporting evidence such as administrative shares, service creation and process execution.
4. Avoid over-attribution from a single event.

## 9. Key Takeaway

The laboratory showed detection latencies under 25 seconds in all measured scenarios.

The strongest operational conclusion is not only that Wazuh generated alerts quickly, but that the alert chains were explainable:

```text
RDP:
remote access + post-access commands

SMB / PsExec-like:
NTLM + privileges + service creation

Pass-the-Hash:
NTLM + privileges + DCSync-like evidence + correlation
```
