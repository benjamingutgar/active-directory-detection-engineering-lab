# T1558.003 — Kerberoasting Detection

This write-up explains the detection logic for the controlled Kerberoasting scenario.

It covers three detection hypotheses:

| Hypothesis | Meaning |
|---|---|
| `H8` | Detect a Kerberos TGS using RC4 from a source outside the approved laboratory list |
| `H9` | Detect three suspicious RC4 service-ticket requests from the same source in 120 seconds |
| `H10` | Detect a process other than `lsass.exe` connecting from `WS01` to the Kerberos service on `DC01` |

The global hypothesis model is documented in [detection-hypotheses.md](detection-hypotheses.md), but this file is designed to be readable on its own.

---

## 1. Technique Overview

Kerberoasting is a credential-access technique that targets Active Directory accounts associated with Service Principal Names.

A domain-authenticated user can normally request a Kerberos service ticket for an available SPN.

Part of that ticket is protected using key material associated with the service account.

An attacker can export the encrypted ticket material and test password candidates offline.

The attack does not require the password candidates to be sent back to the Domain Controller.

The main defensive problem is therefore:

```text
The suspicious action is visible when the ticket is requested.

The password guessing phase may happen completely offline.
```

MITRE ATT&CK classifies this behavior as:

```text
T1558.003 — Steal or Forge Kerberos Tickets: Kerberoasting
```

---

## 2. Kerberos Context

Kerberos authentication relies on a Key Distribution Center operating on the Domain Controller.

Conceptually, the KDC provides:

- the Authentication Service;
- the Ticket Granting Service.

A normal flow is:

```text
User authenticates
        ↓
KDC issues a Ticket Granting Ticket
        ↓
User requests access to a service identified by an SPN
        ↓
KDC issues a Ticket Granting Service ticket
        ↓
User presents the service ticket to the service
```

Kerberoasting abuses the service-ticket request stage.

The attacker does not need to break the KDC.

The attacker requests a legitimate ticket and attacks the encrypted material offline.

---

## 3. Detection Objective

The objective is to identify behavior compatible with Kerberoasting through several layers:

```text
H8 — suspicious RC4 TGS request
            ↓
H9 — repeated requests from the same source
            ↓
H10 — optional endpoint process context
```

The primary detection relies on Windows Security Event ID `4769`.

The supporting endpoint detection relies on Sysmon Event ID `3`.

## 5. Execution Summary

The controlled scenario follows this sequence:

```text
Create non-privileged service account
        ↓
Register a controlled SPN
        ↓
Temporarily enable RC4
        ↓
Enumerate accounts with SPNs
        ↓
Request one or more TGS tickets
        ↓
Collect Event ID 4769
        ↓
Generate Wazuh alerts
        ↓
Perform a controlled offline password test
        ↓
Rotate the password and restore AES
```

# 7. H8 — RC4 TGS Request from an Unapproved Source

## 7.1 What H8 Tries to Prove

H8 attempts to prove that the Domain Controller issued a Kerberos service ticket using RC4 to a source outside the approved laboratory list.

In natural language:

> If DC01 records Event ID 4769 with ticket encryption type 0x17 and the client address is not an approved Kerberos source, the SIEM has an initial signal compatible with Kerberoasting.

## 7.2 Expected Indicators

| Field | Expected value |
|---|---|
| `agent.name` | `DC01` |
| `data.win.system.eventID` | `4769` |
| `data.win.eventdata.ticketEncryptionType` | `0x17` |
| `data.win.eventdata.ipAddress` | Controlled attacker source |
| `data.win.eventdata.serviceName` | Controlled service identity |
| `rule.id` | `100040` |
| `rule.mitre.id` | `T1558.003` |

The address may appear as:

```text
<ATTACKER_IP>
```

or as an IPv4-mapped IPv6 address:

```text
::ffff:<ATTACKER_IP>
```

## 7.3 Detection Value

H8 combines:

```text
ticket request
+
weak encryption
+
unapproved source
```

This is more useful than alerting on every Event ID `4769`.

Service-ticket requests occur normally in Active Directory.

The contextual value comes from the source and encryption type.

## 7.4 Limitation

H8 is not proof of Kerberoasting.

A legitimate application can:

- request a service ticket;
- use RC4 because of legacy configuration;
- run from a system not yet included in an allowlist.

An attacker can also request an AES ticket and avoid an RC4-only rule.

# 8. H9 — Repeated RC4 Requests from the Same Source

## 8.1 What H9 Tries to Prove

H9 attempts to identify repeated suspicious service-ticket requests.

In natural language:

> If the same source generates three H8 alerts in 120 seconds, the activity has greater relevance as possible automated ticket collection.

## 8.2 Expected Indicators

| Field | Expected value |
|---|---|
| Base matched rule | `100040` |
| Number of matches | `3` |
| Time window | `120` seconds |
| Correlation field | `data.win.eventdata.ipAddress` |
| Correlated rule | `100041` |
| Severity | Critical laboratory alert |
| MITRE mapping | `T1558.003` |

## 8.3 Detection Value

A single service-ticket request may be routine.

Several similar requests in a short period can indicate:

- automated SPN targeting;
- scripted ticket collection;
- enumeration followed by roasting;
- repeated validation of a vulnerable account.

The rule is deliberately simple to make correlation observable in a small laboratory.

## 8.4 Limitation

A fixed threshold can be bypassed.

An attacker may:

- request only one high-value ticket;
- introduce delays;
- distribute the requests across multiple systems;
- request AES tickets;
- use a source already included in the allowlist.

Production thresholds must be based on normal Kerberos activity.

# 9. H10 — Unusual Process Connection to Kerberos

## 9.1 What H10 Tries to Prove

H10 adds endpoint context when ticket-related activity is executed from `WS01`.

In natural language:

> If a process other than lsass.exe connects from WS01 to the Kerberos service on DC01, the SIEM should flag the unusual process context for review.

## 9.2 Expected Indicators

| Field | Expected value |
|---|---|
| Source host | `WS01` |
| Sysmon Event ID | `3` |
| Destination | `DC01` |
| Destination port | `88` |
| Expected normal process | `lsass.exe` |
| Suspicious condition | Process image does not end in `lsass.exe` |
| Wazuh rule | `100042` |
| MITRE mapping | `T1558.003` |

## 9.3 Detection Value

H10 can add process-level context such as:

- image path;
- source host;
- destination address;
- destination port;
- process identity.

This can help distinguish normal Windows Kerberos processing from direct connections created by an unusual tool or script.

## 9.4 Limitation

This rule is supporting evidence only.

Some applications interact with Kerberos through LSASS.

In those cases, Sysmon may show `lsass.exe` even when the original request was triggered by a different application.

The rule also does not apply to the attack executed directly from Linux because Linux does not generate Windows Sysmon telemetry.

## 10. Detection Logic

### 10.1 Layer 1 — KDC Event

The Domain Controller records:

```text
Event ID 4769
```

This establishes that the KDC processed a service-ticket request.

### 10.2 Layer 2 — Encryption Type

The detection checks:

```text
ticketEncryptionType = 0x17
```

This identifies RC4-HMAC.

RC4 is relevant because it is legacy encryption and generally provides a less resistant offline password-testing target than modern AES Kerberos formats.

### 10.3 Layer 3 — Source Context

The rule excludes explicitly approved laboratory sources.

A request from the controlled attacker address generates:

```text
rule 100040
```

### 10.4 Layer 4 — Frequency Correlation

Wazuh counts three alerts from the same source in 120 seconds.

The correlation generates:

```text
rule 100041
```

### 10.5 Layer 5 — Optional Process Context

When equivalent activity is initiated from `WS01`, Sysmon can provide a process and network connection relationship.

An unusual process connecting to `DC01:88` may generate:

```text
rule 100042
```

## 11. Wazuh Rules

### Rule 100040

Purpose:

```text
Detect Event ID 4769 with RC4 from a source outside the approved list.
```

Primary conditions:

```text
Windows Security event
Event ID 4769
ticketEncryptionType 0x17
source address not approved
```

### Rule 100041

Purpose:

```text
Correlate three rule 100040 matches from the same source in 120 seconds.
```

Primary conditions:

```text
if_matched_sid = 100040
frequency = 3
timeframe = 120
same source address
```

### Rule 100042

Purpose:

```text
Detect a process other than lsass.exe connecting from WS01 to DC01 on port 88.
```

Primary conditions:

```text
Sysmon Event ID 3
source host WS01
destination DC01
destination port 88
process image not lsass.exe
```

## 13. Analyst Interpretation

An analyst should not interpret every Event ID `4769` as malicious.

The correct interpretation is:

> The Domain Controller issued an RC4 Kerberos service ticket to a source outside the approved laboratory list. Repeated requests from the same source triggered a correlation alert. This behavior is compatible with Kerberoasting in the controlled scenario, although no isolated event proves offline password recovery.

The analyst should review:

1. requesting account;
2. source address;
3. requested service;
4. associated service account;
5. encryption type;
6. number of distinct SPNs requested;
7. request frequency;
8. source-host baseline;
9. privileges assigned to the service account;
10. password age;
11. whether RC4 is still operationally required;
12. activity performed with the service account after the request.

---

## 14. False-Positive Considerations

Possible legitimate causes include:

| Source | Why it can look similar |
|---|---|
| Legacy applications | May still request RC4 tickets |
| Monitoring platforms | May access several services rapidly |
| Management systems | Can request tickets from fixed administration hosts |
| Application servers | May generate repeated service-ticket requests |
| Account migrations | Can temporarily produce unusual encryption patterns |
| Misconfigured SPNs | Can create repeated ticket activity |

Recommended tuning:

- build a baseline of normal Event ID `4769` activity;
- identify all systems that still require RC4;
- maintain an allowlist of expected service-ticket requesters;
- monitor requests for privileged service accounts separately;
- count distinct SPNs per requester;
- identify users requesting unusually many service tickets;
- review requests outside normal operating hours;
- use honey SPNs for high-confidence detection;
- correlate ticket requests with later authentication using the service identity.

---

## 15. Mitigation

Recommended controls include:

- replace weak service-account passwords with long random values;
- rotate service credentials;
- use Group Managed Service Accounts where supported;
- remove `PasswordNeverExpires` where unnecessary;
- enable AES128 and AES256;
- remove RC4 after validating compatibility;
- apply minimum privilege;
- deny interactive and RDP logon to service identities where possible;
- restrict where each service identity can authenticate;
- remove unused or duplicate SPNs;
- monitor password age and account-group membership;
- investigate RC4 use through Events `4768` and `4769`.

AES reduces the efficiency of offline password testing but does not make a weak password safe.

Password strength and credential lifecycle remain essential.

## 17. Limitations

The scenario was validated in a controlled laboratory.

The laboratory does not include:

- normal enterprise Kerberos volume;
- many legitimate service accounts;
- multiple application servers;
- long-term false-positive measurement;
- realistic password-rotation workflows;
- production identity governance;
- full LDAP telemetry;
- endpoint telemetry from Linux.

The detection should therefore be considered:

```text
validated laboratory logic, not production-ready detection without tuning
```

---

## 18. Key Takeaway

Kerberoasting demonstrates the difference between:

```text
detecting a password attack
```

and:

```text
detecting the activity that makes an offline password attack possible
```

Wazuh can detect the ticket request and its context.

It cannot directly observe every password candidate tested offline.

The strongest defensive approach combines:

```text
Kerberos telemetry
+
encryption type
+
source baseline
+
request volume
+
service-account risk
+
post-request authentication activity
```
