# T1021.001 — RDP Detection

This write-up explains the detection logic for the **RDP lateral movement scenario**.

It covers two detection hypotheses:

| Hypothesis | Meaning |
|---|---|
| **H1** | RDP access from the controlled attacker host to `WS01` |
| **H2** | Post-access process execution after the RDP session |

The global hypothesis model is documented in [`detection-hypotheses.md`](detection-hypotheses.md), but this file is designed to be readable on its own.

---

## 1. Technique Overview

**Remote Desktop Protocol**, or **RDP**, is a legitimate Windows remote administration protocol.

In real environments, RDP is used by:

- administrators;
- helpdesk teams;
- remote support teams;
- users connecting to workstations or servers;
- jump servers;
- maintenance workflows.

From an attacker perspective, RDP can be abused for lateral movement when the attacker has valid credentials and the target system allows remote desktop access.

The defensive problem is that RDP is not suspicious by default.

The relevant question is not only:

```text
Was there an RDP logon?
```

The relevant question is:

```text
Who authenticated?
From where?
Against which host?
With which account?
Was the source expected?
What happened after the session was established?
```

---

## 2. Detection Objective

The objective is to detect behavior compatible with **RDP-based lateral movement** in the controlled Active Directory laboratory.

The detection is based on a two-step chain:

```text
H1 — RDP access
        ↓
H2 — post-access activity
```

The RDP logon gives the initial signal. The post-access process execution gives context.

This is important because an RDP logon alone can be legitimate. An RDP logon followed by command execution is more useful for analyst triage.

## 3. Lab Scenario

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Source IP | `192.168.56.40` |
| Target host | `WS01` |
| Target IP | `192.168.56.30` |
| Domain | `lab.local` |
| Account type | Standard domain user with RDP permission |
| Main technique | `T1021.001 — Remote Services: Remote Desktop Protocol` |
| Main hypotheses | `H1`, `H2` |

The scenario simulates RDP access from the Kali host to the Windows workstation.

The purpose is not to simulate a complete intrusion. The purpose is to generate observable telemetry that allows the analyst to reconstruct this sequence:

```text
remote access → interactive session → post-access commands
```

## 4. Execution Summary

The RDP session was executed from Kali using FreeRDP.

Example command structure:

```bash
xfreerdp /u:<standard_user> /p:'<PASSWORD>' /d:LAB /v:192.168.56.30 /sec:tls /cert:ignore
```

After the session was established, basic post-access commands were executed:

```cmd
whoami
hostname
ipconfig
```

All credentials in the public repository are placeholders.

# 6. H1 — RDP Access from Known Attack Origin

## 6.1 What H1 Tries to Prove

**H1** tries to prove that `WS01` received a remote RDP-related logon from the controlled attacker host.

In natural language:

> **If `WS01` records a successful remote logon from `192.168.56.40`, then the SIEM has an initial signal compatible with RDP-based lateral movement.**

## 6.2 Expected Indicators

| Field | Expected Value |
|---|---|
| `agent.name` | `WS01` |
| `data.win.system.eventID` | `4624` |
| `data.win.eventdata.ipAddress` | `192.168.56.40` |
| `data.win.eventdata.targetUserName` | `<standard_user>` |
| `rule.id` | `92653` or `100001` |
| `rule.mitre.id` | `T1021.001` |

## 6.3 Detection Value

H1 gives the analyst the first important fact:

```text
A remote session was established from Kali-ATK01 to WS01.
```

This is useful because `Kali-ATK01` is the controlled attack simulation host in the laboratory.

## 6.4 Limitation

H1 is not enough by itself.

RDP is a legitimate protocol. A similar event could be caused by:

- helpdesk support;
- remote administration;
- a jump server;
- VPN access;
- a scheduled maintenance task;
- an authorized user working remotely.

Therefore, H1 should be treated as an **initial signal**, not as final attribution.

---

# 7. H2 — Post-access Activity After RDP Session

## 7.1 What H2 Tries to Prove

**H2** tries to prove that the RDP session was followed by activity on the target host.

In natural language:

> **If command execution appears on `WS01` after the RDP logon, then the RDP access becomes more relevant as potential lateral movement.**

## 7.2 Expected Indicators

| Field | Expected Value |
|---|---|
| `agent.name` | `WS01` |
| `data.win.system.eventID` | `4688` |
| `data.win.eventdata.newProcessName` | `whoami.exe`, `hostname.exe`, `ipconfig.exe`, `cmd.exe` |
| `rule.id` | `67027`, `92052` or `100001` |
| Sysmon Event ID | `1`, if Sysmon is available |

## 7.3 Detection Value

H2 gives context to H1.

The chain becomes:

```text
RDP logon → interactive session → command execution
```

This is stronger than an isolated RDP logon because it shows that the remote session was used.

## 7.4 Limitation

The commands themselves are not malicious.

For example:

```cmd
whoami
hostname
ipconfig
```

are normal diagnostic commands.

They become relevant because of the surrounding context:

```text
source host + target host + account + RDP session + command execution
```

## 8. Detection Logic

The RDP detection should be read as a chain.

## 8.1 Layer 1 — Remote Authentication

The first layer identifies that remote authentication occurred.

Relevant evidence:

```text
Windows Event ID 4624
source IP 192.168.56.40
target host WS01
RDP-related context
```

## 8.2 Layer 2 — RDP Contextual Alert

Wazuh native and custom rules provide RDP context.

Relevant rules:

```text
92653
100001
```

Rule `100001` is used as the project-specific contextual rule. In the public repository, this rule is tied to the controlled lab context and should be tuned before reuse.

## 8.3 Layer 3 — Post-access Process Execution

Post-access commands are observed through process telemetry.

Relevant rules:

```text
67027
92052
```

This layer is important because it helps answer:

```text
What did the user do after the RDP session started?
```

---

## 9. Evidence Observed

The RDP scenario generated evidence on `WS01`.

Observed evidence includes:

- remote authentication;
- source IP `192.168.56.40`;
- target host `WS01`;
- domain user context;
- process execution after access;
- Wazuh mapping to `T1021.001`.

Expected alert chain:

```text
92653 / 100001 → 67027 / 92052
```

---

## 10. Analyst Interpretation

An analyst should not treat the RDP logon alone as malicious.

The correct interpretation is:

> **The SIEM observed RDP access from the controlled attacker host followed by post-access activity on the workstation. This is compatible with RDP-based lateral movement in the laboratory context.**

The analyst should review:

1. source IP address;
2. target host;
3. authenticated user;
4. logon type;
5. logon time;
6. post-access processes;
7. whether the source is an approved RDP origin;
8. whether the user normally accesses the host remotely;
9. whether additional lateral movement occurred after the RDP session.

---

## 11. False-Positive Considerations

Possible legitimate sources of similar telemetry:

| Source | Why it can look similar |
|---|---|
| Helpdesk activity | Remote support often uses RDP |
| System administrators | Administrators may access workstations remotely |
| Jump servers | Controlled administrative access may originate from fixed hosts |
| VPN users | Remote users may connect from unusual IPs |
| Remote support platforms | May create interactive remote activity patterns |

Recommended tuning:

- define approved RDP source hosts;
- baseline normal RDP users;
- monitor RDP from unusual IP ranges;
- increase severity when RDP is followed by reconnaissance commands;
- correlate RDP logons with process execution;
- review RDP to sensitive hosts separately from RDP to normal workstations.

## 14. Limitations

This detection was validated in a controlled laboratory environment.

The lab does not include:

- real helpdesk activity;
- normal user traffic;
- multiple administrators;
- VPN baselines;
- remote support platforms;
- long-term production false-positive measurement.

Therefore, the detection should be considered:

```text
validated laboratory logic, not production-ready detection without tuning
```

---

## 15. Key Takeaway

The RDP scenario is useful because it shows the difference between:

```text
RDP logon as an isolated event
```

and:

```text
RDP logon followed by post-access activity
```

The second chain is more useful for Blue Team analysis because it allows the analyst to reconstruct behavior, not only observe authentication.
