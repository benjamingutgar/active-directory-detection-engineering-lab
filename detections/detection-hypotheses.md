# Detection Hypotheses

This document defines the **thirteen detection hypotheses** used in the Wazuh Active Directory security laboratory.

A detection hypothesis is the analytical bridge between a MITRE ATT&CK technique and the SIEM rule that tries to detect it.

In other words, this file answers:

> **What behavior should be observable in Windows, Sysmon and Wazuh telemetry if the controlled technique was executed?**

The Wazuh rules are not the starting point of the project. The starting point is the hypothesis. The rules are the implementation layer.

---

## 1. Why Detection Hypotheses Matter

A SIEM does not directly see an attack technique.

A SIEM sees:

- Windows events;
- Sysmon events;
- fields inside those events;
- timestamps;
- source and destination systems;
- user accounts;
- Wazuh rule matches;
- correlations between alerts.

The analyst interprets those signals and maps the resulting behavior to MITRE ATT&CK.

For that reason, this repository separates three levels:

| Level | Meaning | Examples |
|---|---|---|
| **Event** | Raw telemetry generated by Windows, Sysmon or another source | `4624`, `4662`, `4672`, `4688`, `4768`, `4769`, `5145`, `7045`, Sysmon Event IDs `1` and `3` |
| **Alert** | Wazuh output after applying a rule to an event or sequence of events | `100001`, `100011`, `100030`, `100033`, `100040`, `100041`, `100050`, `100051`, `100052` |
| **Attribution** | Analyst interpretation that maps the observed evidence to MITRE ATT&CK | `T1021.001`, `T1021.002`, `T1569.002`, `T1550.002`, `T1003.006`, `T1558.003`, `T1558.004` |

This distinction is especially important for Pass-the-Hash, Kerberoasting and AS-REP Roasting.

### Pass-the-Hash

Wazuh does not observe the NTLM hash directly. It observes authentication and the activity surrounding the authenticated session.

The correct conclusion is:

```text
Wazuh detected a chain of behavior compatible with Pass-the-Hash in the controlled laboratory context.
```

It is not:

```text
Wazuh directly detected the NTLM hash.
```

### Kerberoasting

Wazuh can observe the Kerberos service-ticket request and its context, but it does not observe every password candidate tested offline.

The correct conclusion is:

```text
Wazuh detected repeated RC4 Kerberos service-ticket requests compatible with Kerberoasting.
```

It is not:

```text
Wazuh observed the service-account password being recovered.
```

### AS-REP Roasting

Wazuh can observe a Kerberos TGT request without pre-authentication, its result, encryption type, source and frequency.

The correct conclusion is:

```text
Wazuh detected successful Kerberos TGT requests without pre-authentication, including RC4-HMAC and frequency context, compatible with AS-REP Roasting.
```

It is not:

```text
Wazuh observed the target-account password being recovered.
```

## 3. Scenario-to-Hypothesis Relationship

The thirteen hypotheses are grouped into five controlled scenarios:

```text
RDP:
H1 + H2

SMB / PsExec-like:
H3 + H4 + H5

Pass-the-Hash / DCSync:
H6 + H7

Kerberoasting:
H8 + H9 + H10

AS-REP Roasting:
H11 + H12 + H13
```

The project reconstructs behavior chains from several related signals instead of treating every Windows event or Wazuh alert as a separate incident.

# 4. H1 — RDP Access from Known Attack Origin

## 4.1 Purpose

H1 detects the first relevant signal of the RDP scenario: a remote logon from the controlled attacker host to the workstation.

The hypothesis is:

> **If `WS01` records a successful remote RDP logon from `192.168.56.40`, then there is an initial signal compatible with RDP-based lateral movement.**

## 4.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Source IP | `192.168.56.40` |
| Target host | `WS01` |
| Target IP | `192.168.56.30` |
| Technique | `T1021.001 — Remote Services: Remote Desktop Protocol` |
| Main rule | `92653` |
| Main event | `4624` |

## 4.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `WS01` |
| `data.win.system.eventID` | `4624` |
| `data.win.eventdata.ipAddress` | `192.168.56.40` |
| `data.win.eventdata.targetUserName` | `<standard_user>` |
| RDP context | Logon Type `10` or equivalent RDP-session telemetry |
| `rule.id` | `92653` |
| `rule.mitre.id` | `T1021.001` |

## 4.4 What H1 Proves

H1 proves that a remote RDP access event occurred from the controlled source to the Windows workstation.

It gives the analyst the following relationship:

```text
Kali-ATK01 → RDP authentication → WS01
```

## 4.5 What H1 Does Not Prove

H1 does not prove malicious intent by itself.

RDP can be generated legitimately by:

- helpdesk personnel;
- system administrators;
- jump servers;
- VPN users;
- remote-support teams;
- authorized maintenance sessions.

## 4.6 Analyst Interpretation

The analyst should determine:

1. Is the source IP expected?
2. Is the account authorized to use RDP?
3. Is the target normally accessed remotely?
4. Did the activity occur during an expected period?
5. Was the logon followed by process execution?

The final question leads to H2.

# 5. H2 — Post-Access Activity After an RDP Session

## 5.1 Purpose

H2 adds process context to H1.

The hypothesis is:

> **If process execution is recorded on `WS01` after the RDP session, then the remote-access event gains additional lateral-movement context.**

## 5.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Target host | `WS01` |
| Technique | `T1021.001 — Remote Services: Remote Desktop Protocol` |
| Main rules | `67027`, `92052`, `100001` |
| Main event | `4688` |
| Optional event | Sysmon Event ID `1` |

## 5.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `WS01` |
| `data.win.system.eventID` | `4688` or Sysmon Event ID `1` |
| Process names | `whoami.exe`, `hostname.exe`, `ipconfig.exe`, `cmd.exe` |
| `rule.id` | `67027`, `92052` or `100001` |

Rule `100001` is a post-access process rule in the current public ruleset. It is not the initial RDP-logon rule.

## 5.4 What H2 Proves

H2 proves that activity occurred after the remote session was established.

The relevant chain becomes:

```text
RDP logon
    ↓
interactive session
    ↓
process execution
```

## 5.5 What H2 Does Not Prove

Commands such as the following can be legitimate administrative or diagnostic activity:

```text
whoami
hostname
ipconfig
```

They become more relevant because of their surrounding context:

```text
controlled source
+
RDP access
+
target workstation
+
post-access process execution
```

## 5.6 Analyst Interpretation

H2 increases the confidence of the RDP scenario by connecting access with later activity.

Full scenario explanation:

- [`T1021.001-rdp.md`](T1021.001-rdp.md)

# 6. H3 — SMB Authentication from Kali to DC01

## 6.1 Purpose

H3 detects the first relevant signal of the SMB / PsExec-like scenario.

The hypothesis is:

> **If `DC01` records a network logon from `192.168.56.40` using NTLM and Logon Type 3, then there is an initial signal compatible with SMB-based lateral movement.**

## 6.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Source IP | `192.168.56.40` |
| Target host | `DC01` |
| Target IP | `192.168.56.20` |
| Technique | `T1021.002 — SMB/Windows Admin Shares` |
| Main rule | `100011` |
| Main event | `4624` |

## 6.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `DC01` |
| `data.win.system.eventID` | `4624` |
| `data.win.eventdata.logonType` | `3` |
| `data.win.eventdata.authenticationPackageName` | `NTLM` |
| `data.win.eventdata.ipAddress` | `192.168.56.40` |
| `data.win.eventdata.targetUserName` | `<privileged_user>` |
| `rule.id` | `100011` |
| `rule.mitre.id` | `T1021.002`, `T1550.002` |

## 6.4 What H3 Proves

H3 proves that `DC01` received network authentication using NTLM from the controlled source.

This is an initial component of the SMB / PsExec-like activity chain.

## 6.5 What H3 Does Not Prove

A Logon Type 3 event can also be produced by:

- file-share access;
- administrative scripts;
- backup software;
- endpoint-management tools;
- software deployment;
- legacy applications;
- printers or scanners;
- remote inventory systems.

## 6.6 Analyst Interpretation

H3 is an early indicator.

It becomes stronger when combined with administrative-share access and remote service creation.

Full scenario explanation:

- [`T1021.002-smb-psexec-like.md`](T1021.002-smb-psexec-like.md)

# 7. H4 — Access to Administrative Shares

## 7.1 Purpose

H4 strengthens the SMB / PsExec-like hypothesis by identifying access to administrative shares.

The hypothesis is:

> **If, after NTLM network authentication, `DC01` records access to administrative shares such as `ADMIN$`, `C$` or `IPC$`, then the SMB lateral-movement chain becomes stronger.**

## 7.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Source IP | `192.168.56.40` |
| Target host | `DC01` |
| Technique | `T1021.002 — SMB/Windows Admin Shares` |
| Main rule | `92218` |
| Main event | `5145` |

## 7.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `DC01` |
| `data.win.system.eventID` | `5145` |
| `data.win.eventdata.shareName` | `ADMIN$`, `C$` or `IPC$` |
| `data.win.eventdata.ipAddress` | `192.168.56.40` |
| `rule.id` | `92218` or another applicable native Wazuh rule |

## 7.4 What H4 Proves

H4 proves that the authenticated remote session interacted with administrative SMB resources.

The chain becomes:

```text
NTLM network logon
        ↓
administrative-share access
```

## 7.5 What H4 Does Not Prove

Administrative-share access can be generated by:

- administrators;
- software-deployment systems;
- remote-management tools;
- backup products;
- monitoring systems;
- authorized Windows administration.

## 7.6 Analyst Interpretation

H4 should be interpreted together with H3 and H5.

Administrative-share activity is more useful than authentication alone, but service-creation or execution evidence provides a stronger conclusion.

# 8. H5 — Remote Service Creation Compatible with PsExec-Like Execution

## 8.1 Purpose

H5 is the strongest hypothesis in the SMB / PsExec-like scenario.

The hypothesis is:

> **If, after NTLM authentication and administrative-share access, `DC01` records a new service, then the chain is compatible with PsExec-like remote execution.**

## 8.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Target host | `DC01` |
| Techniques | `T1021.002`, `T1569.002` |
| Main rules | `100010`, `92307`, `92650` |
| Main event | `7045` |

## 8.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `DC01` |
| `data.win.system.eventID` | `7045` |
| `data.win.system.providerName` | `Service Control Manager` |
| `data.win.eventdata.accountName` | `LocalSystem` |
| `data.win.eventdata.serviceName` | Random or tool-generated service name |
| `data.win.eventdata.imagePath` | Remote command or executable path |
| `rule.id` | `100010`, `92307` or `92650` |

## 8.4 What H5 Proves

H5 confirms that a service was created on the target.

Combined with the preceding telemetry, the chain becomes:

```text
NTLM network logon
        ↓
privileged session
        ↓
administrative-share access
        ↓
service creation
        ↓
process execution
```

## 8.5 What H5 Does Not Prove

Remote service creation can also be produced by:

- endpoint-management agents;
- software-deployment tools;
- EDR installation;
- backup software;
- authorized maintenance;
- remote troubleshooting.

## 8.6 Analyst Interpretation

The analyst should review:

1. service name;
2. service path;
3. account used;
4. source IP;
5. parent process when available;
6. whether the service is expected;
7. whether the activity matches an authorized maintenance period.

Full scenario explanation:

## 9.1 Purpose

H6 detects the authentication effect of the controlled Pass-the-Hash scenario.

The hypothesis is:

> **If `DC01` records NTLM network authentication from the controlled source and the account receives special privileges, then there is a signal compatible with credential-based lateral movement.**

| Target host | `DC01` |

|---|---|

| Field | Expected Value |

## 9.4 What H6 Proves

## 9.5 What H6 Does Not Prove

H6 does not prove that a hash was used.

A normal NTLM authentication using a password can produce similar Windows telemetry.

```text
privileged NTLM network authentication compatible with credential reuse
```

It is not:

```text
direct proof of Pass-the-Hash
```

## 9.6 Analyst Interpretation

H6 is an early signal.

It becomes more meaningful when correlated with DCSync-like activity in H7.

## 10.1 Purpose

H7 is the strongest hypothesis in the Pass-the-Hash / DCSync scenario.

The hypothesis is:

> **If DCSync-like activity by a non-machine account is correlated with privileged access by the same account inside the configured timeframe, then the chain is compatible with credential-access behavior.**

## 10.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Target host | `DC01` |
| Techniques | `T1550.002`, `T1003.006` |
| Main rules | `100030`, `100033` |
| Main event | `4662` |
| Correlation window | `300` seconds |
| Correlation field | `win.eventdata.subjectUserName` |

## 10.3 Expected DCSync Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `DC01` |
| `data.win.system.eventID` | `4662` |
| `data.win.eventdata.accessMask` | `0x100` |
| `data.win.eventdata.properties` | Replication-related GUIDs or permissions |
| `data.win.eventdata.subjectUserName` | Non-machine account |
| `rule.id` | `100030` |

## 10.4 Expected Correlation Telemetry

| Field | Expected Value |
|---|---|
| Previous alert | `100030` |
| Current alert | `100021` |
| Same field | `win.eventdata.subjectUserName` |
| Correlation rule | `100033` |
| Severity | Level `15` |
| MITRE mapping | `T1550.002`, `T1003.006` |

## 10.5 What H7 Proves

H7 proves that two high-value signals appeared as part of the same controlled behavior chain:

```text
DCSync-like activity
        ↓
privileged access by the same account
```

This is the strongest basis in the repository for attributing the observed behavior to the controlled Pass-the-Hash / DCSync scenario.

## 10.6 What H7 Does Not Prove

H7 does not mean Wazuh directly observed the NTLM hash.

It means Wazuh observed a sequence technically compatible with credential reuse and Active Directory credential access.

## 10.7 Analyst Interpretation

The correct wording is:

```text
Wazuh detected behavior compatible with Pass-the-Hash by correlating DCSync-like activity and privileged access on DC01.
```

# 11. H8 — RC4 Kerberos Service Ticket from an Unexpected Source

## 11.1 Purpose

H8 detects the principal observable signal of the Kerberoasting scenario.

The hypothesis is:

> **If `DC01` records a Kerberos service-ticket request using RC4-HMAC from a source outside the approved laboratory list, then there is an initial signal compatible with Kerberoasting.**

## 11.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Source IP | `192.168.56.40` |
| Target host | `DC01` |
| Target IP | `192.168.56.20` |
| Technique | `T1558.003 — Kerberoasting` |
| Main rule | `100040` |
| Main event | `4769` |
| Ticket encryption type | `0x17 — RC4-HMAC` |

## 11.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `DC01` |
| `data.win.system.eventID` | `4769` |
| `data.win.eventdata.ticketEncryptionType` | `0x17` |
| `data.win.eventdata.ipAddress` | `192.168.56.40` or `::ffff:192.168.56.40` |
| `data.win.eventdata.targetUserName` | Requesting domain account |
| `data.win.eventdata.serviceName` | `<service_account>` |
| `rule.id` | `100040` |
| `rule.level` | `12` |
| `rule.mitre.id` | `T1558.003` |

## 11.4 Detection Logic

```text
Event ID 4769
+
ticketEncryptionType = 0x17
+
source address outside the approved list
=
rule 100040
```

Windows can represent the client address as:

```text
192.168.56.40
```

or:

```text
::ffff:192.168.56.40
```

The detection logic must account for both representations.

## 11.5 What H8 Proves

H8 proves that the Domain Controller processed an RC4 Kerberos service-ticket request from the controlled source.

The observable sequence is:

```text
TGS request
    ↓
Event ID 4769
    ↓
RC4-HMAC
    ↓
unexpected source
```

## 11.6 What H8 Does Not Prove

H8 does not prove that:

- the complete service ticket was exported;
- offline password testing occurred;
- the service-account password was recovered;
- the requesting account had malicious intent;
- a recovered credential was reused.

## 11.7 False-Positive Considerations

Possible legitimate causes include:

- legacy applications that require RC4;
- monitoring or management systems;
- application servers;
- administration hosts missing from the allowlist;
- migration activity;
- older service accounts without suitable AES configuration.

## 11.8 Analyst Interpretation

The analyst should determine:

1. Is the source expected to request the service ticket?
2. Which account requested it?
3. Which service identity owns the SPN?
4. Is RC4 expected for the service?
5. Is the service account privileged?
6. Were other service tickets requested from the same source?
7. Was the service identity used afterward?

Repeated requests lead to H9.

Full scenario explanation:

- [`T1558.003-kerberoasting.md`](T1558.003-kerberoasting.md)

# 12. H9 — Repeated RC4 Service-Ticket Requests

## 12.1 Purpose

H9 adds frequency correlation to H8.

The hypothesis is:

> **If the same source produces three rule `100040` matches within 120 seconds, then Wazuh should generate the higher-level correlation rule `100041`.**

## 12.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Source IP | `192.168.56.40` |
| Target host | `DC01` |
| Technique | `T1558.003 — Kerberoasting` |
| Base rule | `100040` |
| Correlation rule | `100041` |
| Frequency | `3` |
| Timeframe | `120` seconds |
| Correlation field | `win.eventdata.ipAddress` |

## 12.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| Previous rule | `100040` |
| Matching source | `192.168.56.40` or IPv4-mapped IPv6 equivalent |
| Required matches | `3` |
| Maximum interval | `120` seconds |
| `rule.id` | `100041` |
| `rule.level` | `15` |
| `rule.mitre.id` | `T1558.003` |

## 12.4 Detection Logic

```text
three matches of rule 100040
+
same source address
+
within 120 seconds
=
rule 100041
```

The validated alert sequence is:

```text
first request  → 100040
second request → 100040
third request  → 100041
```

Wazuh may display the higher-level correlation rule for the third event instead of another visible `100040`.

## 12.5 What H9 Proves

H9 proves that several suspicious RC4 service-ticket requests originated from the same source inside the configured window.

This provides stronger behavioral context than one Event ID `4769`.

## 12.6 What H9 Does Not Prove

H9 does not prove that offline password recovery occurred or succeeded.

The correlation rule also does not cover activity that does not meet its configured frequency and timeframe conditions.

Legitimate applications can produce several service-ticket requests in a short period, so production use requires a Kerberos baseline.

## 12.7 Analyst Interpretation

The analyst should review:

1. number of requested service identities;
2. requesting account;
3. source host;
4. expected RC4 usage;
5. request timing;
6. service-account privileges;
7. subsequent use of the service identity.

Full scenario explanation:

- [`T1558.003-kerberoasting.md`](T1558.003-kerberoasting.md)

| Source host | `WS01` |
| Source IP | `192.168.56.30` |
| Target host | `DC01` |

# 20. Key Takeaway

The project does not claim that every individual event is malicious.

It shows how a SIEM can turn several observable signals into stronger detection chains:

```text
telemetry
    ↓
detection hypothesis
    ↓
Wazuh rule
    ↓
alert or correlation
    ↓
analyst interpretation
    ↓
MITRE ATT&CK attribution
```

The five controlled scenarios demonstrate different levels of visibility:

```text
RDP:
remote access and post-access processes are observable

SMB / PsExec-like:
authentication, administrative shares and service creation are observable

Pass-the-Hash:
the hash is not directly visible, but surrounding behavior can be correlated

Kerberoasting:
the service-ticket request is visible, but offline password testing is not

AS-REP Roasting:
the no-pre-authentication TGT request is visible, but offline password recovery is not
```

That distinction between event, alert, correlation and attribution is the main detection-engineering value of the laboratory.
