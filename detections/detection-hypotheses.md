# Detection Hypotheses

This document defines the **seven detection hypotheses** used in the Wazuh lateral movement laboratory.

A detection hypothesis is the analytical bridge between a MITRE ATT&CK technique and the SIEM rule that tries to detect it.

In other words, this file answers:

> **What behavior should be observable in Windows and Wazuh telemetry if the simulated technique was executed?**

The Wazuh rules are not the starting point of the project. The starting point is the hypothesis. The rules are only the implementation layer.

---

## 1. Why Detection Hypotheses Matter

A SIEM does not directly see an attack technique.

A SIEM sees:

- Windows events;
- Sysmon events;
- fields inside those events;
- timestamps;
- source and destination systems;
- user accounts;
- Wazuh rule matches;
- correlations between alerts.

The analyst is the one who interprets those signals and maps them to a MITRE ATT&CK technique.

For that reason, this repository separates three levels:

| Level | Meaning | Example |
|---|---|---|
| **Event** | Raw telemetry generated by Windows, Sysmon or another source | `4624`, `4672`, `4688`, `5145`, `7045`, `4662` |
| **Alert** | Wazuh output after applying a rule to an event or sequence of events | `100011`, `100021`, `100030`, `100033` |
| **Attribution** | Analyst interpretation that maps the evidence to MITRE ATT&CK | `T1021.001`, `T1021.002`, `T1550.002`, `T1003.006` |

This distinction is especially important for **Pass-the-Hash**.

Wazuh does not observe the NTLM hash directly. It observes the effects of authentication and activity around it. Therefore, the correct conclusion is not:

```text
Wazuh directly detected the hash.
```

The correct conclusion is:

```text
Wazuh detected a chain of behavior compatible with Pass-the-Hash in the controlled laboratory context.
```

This is the same idea defended in the thesis: the most sustainable Pass-the-Hash detection is not a single NTLM event, but a correlated chain involving DCSync-like activity and privileged access. The thesis maps H1-H7 to the main rules and evidence, including H7 as the correlation between `100030` and `100033`.

## 3. Scenario-to-Hypothesis Relationship

The seven hypotheses are grouped by scenario:

```text
RDP:
H1 + H2

SMB / PsExec-like:
H3 + H4 + H5

Pass-the-Hash / DCSync:
H6 + H7
```

This matters because the project does not try to detect each event as a separate incident. It tries to reconstruct attack chains.

# 4. H1 — RDP Access from Known Attack Origin

## 4.1 Purpose

**H1** detects the first relevant signal of the RDP scenario: a remote logon from the controlled attacker host to the workstation.

The hypothesis is:

> **If `WS01` records a successful remote logon from `192.168.56.40`, then there is an initial signal compatible with RDP-based lateral movement.**

## 4.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Source IP | `192.168.56.40` |
| Target host | `WS01` |
| Target IP | `192.168.56.30` |
| Technique | `T1021.001 — Remote Services: Remote Desktop Protocol` |
| Main rules | `92653`, `100001` |
| Main event | `4624` |

## 4.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `WS01` |
| `data.win.system.eventID` | `4624` |
| `data.win.eventdata.ipAddress` | `192.168.56.40` |
| `data.win.eventdata.targetUserName` | `<standard_user>` |
| `rule.id` | `92653` or `100001` |
| `rule.mitre.id` | `T1021.001` |

## 4.4 What H1 Proves

H1 proves that a remote access event occurred from the attacker-controlled machine to the Windows workstation.

It gives the analyst this information:

```text
Kali-ATK01 authenticated remotely to WS01.
```

## 4.5 What H1 Does Not Prove

H1 does **not** prove malicious activity by itself.

RDP can be legitimate. The same type of telemetry can be generated by:

- helpdesk access;
- a system administrator;
- a jump server;
- a VPN user;
- remote support tooling;
- an authorized maintenance session.

## 4.6 Analyst Interpretation

H1 should be interpreted as an **initial signal**.

The analyst should check:

1. Is the source IP expected?
2. Is the account allowed to use RDP?
3. Is the target workstation normally accessed remotely?
4. Did the activity happen during normal working hours?
5. Did anything happen after the RDP session?

The last question leads to **H2**.

# 5. H2 — Post-access Activity After RDP Session

## 5.1 Purpose

**H2** gives context to H1.

The hypothesis is:

> **If command execution appears on `WS01` after the RDP session, then the RDP access becomes more relevant as potential lateral movement.**

## 5.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Target host | `WS01` |
| Technique | `T1021.001 — Remote Services: Remote Desktop Protocol` |
| Main rules | `67027`, `92052`, `100001` |
| Main event | `4688` |
| Optional event | Sysmon Event ID `1` |

## 5.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `WS01` |
| `data.win.system.eventID` | `4688` |
| `data.win.eventdata.newProcessName` | `whoami.exe`, `hostname.exe`, `ipconfig.exe`, `cmd.exe` |
| `rule.id` | `67027`, `92052` or `100001` |

## 5.4 What H2 Proves

H2 proves that the session was not just a logon event. It was followed by activity.

The relevant chain becomes:

```text
RDP logon → interactive session → command execution
```

## 5.5 What H2 Does Not Prove

H2 does not prove malicious intent by itself.

Commands such as the following are normal administrative or diagnostic commands:

```text
whoami
hostname
ipconfig
```

They become suspicious because of the surrounding context:

```text
unusual source + RDP access + domain user + target workstation + post-access commands
```

## 5.6 Analyst Interpretation

H2 increases the confidence of the RDP scenario.

A single RDP logon can be weak. RDP followed by command execution is more useful because it gives the analyst behavior to investigate.

Full scenario explanation:

- [`T1021.001-rdp.md`](T1021.001-rdp.md)

# 6. H3 — SMB Authentication from Kali to DC01

## 6.1 Purpose

**H3** detects the first relevant signal of the SMB/PsExec-like scenario.

The hypothesis is:

> **If `DC01` records a network logon from `192.168.56.40` using NTLM and Logon Type 3, then there is an initial signal compatible with SMB-based lateral movement.**

## 6.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Source IP | `192.168.56.40` |
| Target host | `DC01` |
| Target IP | `192.168.56.20` |
| Technique | `T1021.002 — SMB/Windows Admin Shares` |
| Main rule | `100011` |
| Main event | `4624` |

## 6.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `DC01` |
| `data.win.system.eventID` | `4624` |
| `data.win.eventdata.logonType` | `3` |
| `data.win.eventdata.authenticationPackageName` | `NTLM` |
| `data.win.eventdata.ipAddress` | `192.168.56.40` |
| `data.win.eventdata.targetUserName` | `<privileged_user>` |
| `rule.id` | `100011` |
| `rule.mitre.id` | `T1021.002`, `T1550.002` |

## 6.4 What H3 Proves

H3 proves that the target received a network authentication using NTLM.

This is important because SMB/PsExec-like execution normally begins with remote network authentication.

## 6.5 What H3 Does Not Prove

H3 does not prove malicious activity by itself.

A Logon Type 3 event can appear in many legitimate cases:

- file share access;
- administrative scripts;
- backup software;
- endpoint management tools;
- software deployment;
- legacy applications;
- printers or scanners;
- remote inventory tools.

## 6.6 Analyst Interpretation

H3 is an early indicator. It becomes stronger only when combined with H4 and H5.

Full scenario explanation:

- [`T1021.002-smb-psexec-like.md`](T1021.002-smb-psexec-like.md)

# 7. H4 — Access to Administrative Shares

## 7.1 Purpose

**H4** strengthens the SMB/PsExec-like hypothesis by looking for access to administrative shares.

The hypothesis is:

> **If, after NTLM network authentication, `DC01` records access to administrative shares such as `ADMIN$`, `C$` or `IPC$`, then the SMB lateral movement chain becomes stronger.**

## 7.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Target host | `DC01` |
| Technique | `T1021.002 — SMB/Windows Admin Shares` |
| Main rule | `92218` |
| Main event | `5145` |

## 7.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `DC01` |
| `data.win.system.eventID` | `5145` |
| `data.win.eventdata.shareName` | `ADMIN$`, `C$`, `IPC$` |
| `data.win.eventdata.ipAddress` | `192.168.56.40` |
| `rule.id` | `92218` or related Wazuh rule |

## 7.4 What H4 Proves

H4 proves that the authenticated remote session interacted with administrative SMB resources.

This is relevant because PsExec-like techniques commonly rely on:

```text
ADMIN$ / C$ / IPC$ → named pipes → service control interaction
```

## 7.5 What H4 Does Not Prove

Administrative share access is not always malicious.

It may be generated by:

- administrators;
- software deployment systems;
- remote management tools;
- backup products;
- monitoring products;
- legitimate Windows administration.

## 7.6 Analyst Interpretation

H4 should be interpreted together with H3 and H5.

The chain becomes:

```text
NTLM network logon → administrative share access
```

This is stronger than H3 alone, but still not enough without service creation or execution context.

# 8. H5 — Remote Service Creation Compatible with PsExec-like Execution

## 8.1 Purpose

**H5** is the strongest hypothesis in the SMB/PsExec-like scenario.

The hypothesis is:

> **If, after NTLM authentication and administrative share access, `DC01` records the creation of a new service, then the chain is compatible with PsExec-like remote execution.**

## 8.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Target host | `DC01` |
| Techniques | `T1021.002`, `T1569.002` |
| Main rules | `100010`, `92307`, `92650` |
| Main event | `7045` |

## 8.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `DC01` |
| `data.win.system.eventID` | `7045` |
| `data.win.system.providerName` | `Service Control Manager` |
| `data.win.eventdata.accountName` | `LocalSystem` |
| `data.win.eventdata.serviceName` | Random or tool-generated service name |
| `data.win.eventdata.imagePath` | Suspicious command or payload path |
| `rule.id` | `100010`, `92307` or `92650` |

## 8.4 What H5 Proves

H5 proves that a remote execution mechanism was probably used.

The complete SMB/PsExec-like chain becomes:

```text
NTLM network logon → privileged session → administrative share access → service creation → process execution
```

## 8.5 What H5 Does Not Prove

Remote service creation can also be legitimate.

Examples:

- endpoint management agents;
- software deployment tools;
- EDR installation;
- backup software;
- administrator maintenance;
- remote troubleshooting.

## 8.6 Analyst Interpretation

H5 is high-value because service creation on a domain controller is sensitive.

The analyst should review:

1. service name;
2. service path;
3. account used;
4. source IP;
5. parent process if available;
6. whether the service is expected;
7. whether the activity matches a maintenance window.

Full scenario explanation:

- [`T1021.002-smb-psexec-like.md`](T1021.002-smb-psexec-like.md)

# 9. H6 — NTLM Network Authentication Compatible with Pass-the-Hash

## 9.1 Purpose

**H6** detects the authentication effect of the Pass-the-Hash scenario.

The hypothesis is:

> **If `DC01` records NTLM network authentication from the attacker host and the account receives special privileges, then there is a signal compatible with credential-based lateral movement and possible Pass-the-Hash activity.**

## 9.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Source IP | `192.168.56.40` |
| Target host | `DC01` |
| Technique | `T1550.002 — Pass the Hash` |
| Main rules | `100011`, `100021` |
| Main events | `4624`, `4672` |

## 9.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `DC01` |
| `data.win.system.eventID` | `4624` |
| `data.win.eventdata.logonType` | `3` |
| `data.win.eventdata.authenticationPackageName` | `NTLM` |
| `data.win.eventdata.ipAddress` | `192.168.56.40` |
| `data.win.eventdata.targetUserName` | `<privileged_user>` |
| `rule.id` | `100011` |

For privileges:

| Field | Expected Value |
|---|---|
| `data.win.system.eventID` | `4672` |
| `data.win.eventdata.subjectUserName` | `<privileged_user>` |
| `rule.id` | `100021` |

## 9.4 What H6 Proves

H6 proves that a privileged account authenticated to `DC01` over the network using NTLM.

This is compatible with the effect of Pass-the-Hash.

## 9.5 What H6 Does Not Prove

H6 does not prove that a hash was used.

A normal NTLM authentication using a password can look similar from the point of view of Windows logs.

Therefore, H6 should be described as:

```text
privileged NTLM network authentication compatible with credential reuse
```

not as:

```text
direct proof of Pass-the-Hash
```

## 9.6 Analyst Interpretation

H6 is an early signal.

It becomes much stronger when correlated with H7.

Full scenario explanation:

- [`T1550.002-pass-the-hash.md`](T1550.002-pass-the-hash.md)

# 10. H7 — Pass-the-Hash / DCSync Correlation

## 10.1 Purpose

**H7** is the strongest hypothesis in the Pass-the-Hash scenario.

The hypothesis is:

> **If DCSync-like activity by a non-machine account is correlated with privileged access inside a defined timeframe, then the chain is compatible with Pass-the-Hash / credential access behavior.**

## 10.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Target host | `DC01` |
| Techniques | `T1550.002`, `T1003.006` |
| Main rules | `100030`, `100033` |
| Main event | `4662` |
| Correlation window | `300` seconds |

## 10.3 Expected DCSync Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `DC01` |
| `data.win.system.eventID` | `4662` |
| `data.win.eventdata.accessMask` | `0x100` |
| `data.win.eventdata.properties` | Replication-related GUIDs or permissions |
| `data.win.eventdata.subjectUserName` | Non-machine account |
| `rule.id` | `100030` |
| `rule.mitre.id` | `T1003.006` |

## 10.4 Expected Correlation Telemetry

| Field | Expected Value |
|---|---|
| Previous alert | `100030` |
| Current alert | `100021` |
| Correlation rule | `100033` |
| Severity | Level `15` |
| MITRE mapping | `T1550.002`, `T1003.006` |

## 10.5 What H7 Proves

H7 proves that two high-value signals appeared as part of the same attack chain:

```text
DCSync-like activity → privileged access
```

This is the strongest basis for attributing the behavior to the controlled Pass-the-Hash scenario.

## 10.6 What H7 Does Not Prove

Even H7 does not mean Wazuh saw the hash.

It means Wazuh saw a sequence that is technically compatible with hash reuse and credential access.

## 10.7 Analyst Interpretation

H7 should be treated as a critical correlation in the laboratory.

The correct wording is:

```text
Wazuh detected behavior compatible with Pass-the-Hash by correlating DCSync-like activity, privileged NTLM access and remote activity on DC01.
```

Full scenario explanation:

- [`T1550.002-pass-the-hash.md`](T1550.002-pass-the-hash.md)

# 11. Final Detection Chains

## 11.1 RDP Chain

```text
H1: RDP logon from Kali to WS01
        ↓
H2: post-access process execution on WS01
```

## 11.2 SMB / PsExec-like Chain

```text
H3: NTLM network logon to DC01
        ↓
H4: administrative share access
        ↓
H5: remote service creation and process execution
```

## 11.3 Pass-the-Hash / DCSync Chain

```text
H6: privileged NTLM network authentication
        ↓
H7: DCSync-like activity correlated with privileged access
```

---

# 12. Key Takeaway

The project does not claim that every individual event is malicious.

The project shows how a SIEM can turn multiple weak or medium signals into stronger detection chains:

```text
telemetry → hypothesis → Wazuh rule → alert → analyst interpretation → MITRE mapping
```

That is the detection engineering value of the laboratory.
