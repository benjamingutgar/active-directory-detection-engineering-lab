# Detection Hypotheses

This document defines the **thirteen detection hypotheses** used in the Wazuh Active Directory security laboratory.

A detection hypothesis is the analytical bridge between a MITRE ATT&CK technique and the SIEM rule that tries to detect it.

In other words, this file answers:

> **What behavior should be observable in Windows, Sysmon and Wazuh telemetry if the simulated technique was executed?**

The Wazuh rules are not the starting point of the project. The starting point is the hypothesis. The rules are only the implementation layer.

---

## 1. Why Detection Hypotheses Matter

A SIEM does not directly see an attack technique.

A SIEM sees:

- Windows events;
- Sysmon events;
- fields inside those events;
- timestamps;
- source and destination systems;
- user accounts;
- Wazuh rule matches;
- correlations between alerts.

The analyst is the one who interprets those signals and maps them to a MITRE ATT&CK technique.

For that reason, this repository separates three levels:

| Level | Meaning | Example |
|---|---|---|
| **Event** | Raw telemetry generated by Windows, Sysmon or another source | `4624`, `4662`, `4672`, `4688`, `4768`, `4769`, `5145`, `7045` |
| **Alert** | Wazuh output after applying a rule to an event or sequence of events | `100011`, `100030`, `100033`, `100040`, `100041`, `100050`, `100051`, `100052` |
| **Attribution** | Analyst interpretation that maps the evidence to MITRE ATT&CK | `T1021.001`, `T1021.002`, `T1550.002`, `T1003.006`, `T1558.003`, `T1558.004` |

This distinction is especially important for **Pass-the-Hash**, **Kerberoasting** and **AS-REP Roasting**.

Wazuh does not observe the NTLM hash directly during Pass-the-Hash. It observes the effects of authentication and activity around it. Therefore, the correct conclusion is not:

```text
Wazuh directly detected the hash.
```

The correct conclusion is:

```text
Wazuh detected a chain of behavior compatible with Pass-the-Hash in the controlled laboratory context.
```

The same principle applies to Kerberoasting.

Wazuh can observe the Kerberos service-ticket request and its context, but it does not observe every password candidate tested offline.

The correct conclusion is:

```text
Wazuh detected repeated RC4 Kerberos service-ticket requests compatible with Kerberoasting.
```

It is not:

```text
Wazuh observed the service-account password being cracked.
```

The same detection boundary applies to AS-REP Roasting. Wazuh can observe a TGT request processed without Kerberos pre-authentication and the fields associated with that request, but it does not observe offline password recovery.

The correct conclusion is:

```text
Wazuh detected TGT requests without Kerberos pre-authentication compatible with AS-REP Roasting.
```

It is not:

```text
Wazuh observed the AS-REP account password being recovered offline.
```

## 3. Scenario-to-Hypothesis Relationship

The thirteen hypotheses are grouped by scenario:

```text
RDP:
H1 + H2

SMB / PsExec-like:
H3 + H4 + H5

Pass-the-Hash / DCSync:
H6 + H7

Kerberoasting:
H8 + H9 + H10

AS-REP Roasting:
H11 + H12 + H13
```

The project reconstructs behavior chains from related signals instead of treating every event as a separate incident.

# 4. H1 — RDP Access from Known Attack Origin

## 4.1 Purpose

**H1** detects the first relevant signal of the RDP scenario: a remote logon from the controlled attacker host to the workstation.

The hypothesis is:

> **If `WS01` records a successful remote logon from `192.168.56.40`, then there is an initial signal compatible with RDP-based lateral movement.**

## 4.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Source IP | `192.168.56.40` |
| Target host | `WS01` |
| Target IP | `192.168.56.30` |
| Technique | `T1021.001 — Remote Services: Remote Desktop Protocol` |
| Main rule | `92653` |
| Main event | `4624` |

## 4.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `WS01` |
| `data.win.system.eventID` | `4624` |
| `data.win.eventdata.ipAddress` | `192.168.56.40` |
| `data.win.eventdata.targetUserName` | `<standard_user>` |
| `rule.id` | `92653` |
| `rule.mitre.id` | `T1021.001` |

## 4.4 What H1 Proves

H1 proves that a remote access event occurred from the attacker-controlled machine to the Windows workstation.

It gives the analyst this information:

```text
Kali-ATK01 authenticated remotely to WS01.
```

## 4.5 What H1 Does Not Prove

H1 does not prove malicious activity by itself.

RDP can be legitimate. The same type of telemetry can be generated by:

- helpdesk access;
- a system administrator;
- a jump server;
- a VPN user;
- remote support tooling;
- an authorized maintenance session.

## 4.6 Analyst Interpretation

H1 should be interpreted as an initial signal.

The analyst should check:

1. Is the source IP expected?
2. Is the account allowed to use RDP?
3. Is the target workstation normally accessed remotely?
4. Did the activity happen during normal working hours?
5. Did anything happen after the RDP session?

The last question leads to **H2**.

# 5. H2 — Post-access Activity After RDP Session

## 5.1 Purpose

**H2** gives context to H1.

The hypothesis is:

> **If command execution appears on `WS01` after the RDP session, then the RDP access becomes more relevant as potential lateral movement.**

## 5.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Target host | `WS01` |
| Technique | `T1021.001 — Remote Services: Remote Desktop Protocol` |
| Main rules | `67027`, `92052`, `100001` |
| Main event | `4688` |
| Optional event | Sysmon Event ID `1` |

## 5.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `WS01` |
| `data.win.system.eventID` | `4688` |
| `data.win.eventdata.newProcessName` | `whoami.exe`, `hostname.exe`, `ipconfig.exe`, `cmd.exe` |
| `rule.id` | `67027`, `92052` or `100001` |

## 5.4 What H2 Proves

H2 proves that the session was not just a logon event. It was followed by activity.

The relevant chain becomes:

```text
RDP logon → interactive session → command execution
```

## 5.5 What H2 Does Not Prove

H2 does not prove malicious intent by itself.

Commands such as the following are normal administrative or diagnostic commands:

```text
whoami
hostname
ipconfig
```

They become suspicious because of the surrounding context:

```text
unusual source + RDP access + domain user + target workstation + post-access commands
```

## 5.6 Analyst Interpretation

H2 increases the confidence of the RDP scenario.

A single RDP logon can be weak. RDP followed by command execution is more useful because it gives the analyst behavior to investigate.

Full scenario explanation:

- [`T1021.001-rdp.md`](T1021.001-rdp.md)

# 6. H3 — SMB Authentication from Kali to DC01

## 6.1 Purpose

**H3** detects the first relevant signal of the SMB/PsExec-like scenario.

The hypothesis is:

> **If `DC01` records a network logon from `192.168.56.40` using NTLM and Logon Type 3, then there is an initial signal compatible with SMB-based lateral movement.**

## 6.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Source IP | `192.168.56.40` |
| Target host | `DC01` |
| Target IP | `192.168.56.20` |
| Technique | `T1021.002 — SMB/Windows Admin Shares` |
| Main rule | `100011` |
| Main event | `4624` |

## 6.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `DC01` |
| `data.win.system.eventID` | `4624` |
| `data.win.eventdata.logonType` | `3` |
| `data.win.eventdata.authenticationPackageName` | `NTLM` |
| `data.win.eventdata.ipAddress` | `192.168.56.40` |
| `data.win.eventdata.targetUserName` | `<privileged_user>` |
| `rule.id` | `100011` |
| `rule.mitre.id` | `T1021.002`, `T1550.002` |

## 6.4 What H3 Proves

H3 proves that the target received a network authentication using NTLM.

This is important because SMB/PsExec-like execution normally begins with remote network authentication.

## 6.5 What H3 Does Not Prove

H3 does not prove malicious activity by itself.

A Logon Type 3 event can appear in many legitimate cases:

- file share access;
- administrative scripts;
- backup software;
- endpoint management tools;
- software deployment;
- legacy applications;
- printers or scanners;
- remote inventory tools.

## 6.6 Analyst Interpretation

H3 is an early indicator. It becomes stronger only when combined with H4 and H5.

Full scenario explanation:

- [`T1021.002-smb-psexec-like.md`](T1021.002-smb-psexec-like.md)

# 7. H4 — Access to Administrative Shares

## 7.1 Purpose

**H4** strengthens the SMB/PsExec-like hypothesis by looking for access to administrative shares.

The hypothesis is:

> **If, after NTLM network authentication, `DC01` records access to administrative shares such as `ADMIN$`, `C$` or `IPC$`, then the SMB lateral movement chain becomes stronger.**

## 7.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Target host | `DC01` |
| Technique | `T1021.002 — SMB/Windows Admin Shares` |
| Main rule | `92218` |
| Main event | `5145` |

## 7.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `DC01` |
| `data.win.system.eventID` | `5145` |
| `data.win.eventdata.shareName` | `ADMIN$`, `C$`, `IPC$` |
| `data.win.eventdata.ipAddress` | `192.168.56.40` |
| `rule.id` | `92218` or related Wazuh rule |

## 7.4 What H4 Proves

H4 proves that the authenticated remote session interacted with administrative SMB resources.

This is relevant because PsExec-like techniques commonly rely on:

```text
ADMIN$ / C$ / IPC$ → named pipes → service control interaction
```

## 7.5 What H4 Does Not Prove

Administrative share access is not always malicious.

It may be generated by:

- administrators;
- software deployment systems;
- remote management tools;
- backup products;
- monitoring products;
- legitimate Windows administration.

## 7.6 Analyst Interpretation

H4 should be interpreted together with H3 and H5.

The chain becomes:

```text
NTLM network logon → administrative share access
```

This is stronger than H3 alone, but still not enough without service creation or execution context.

# 8. H5 — Remote Service Creation Compatible with PsExec-like Execution

## 8.1 Purpose

**H5** is the strongest hypothesis in the SMB/PsExec-like scenario.

The hypothesis is:

> **If, after NTLM authentication and administrative share access, `DC01` records the creation of a new service, then the chain is compatible with PsExec-like remote execution.**

## 8.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Target host | `DC01` |
| Techniques | `T1021.002`, `T1569.002` |
| Main rules | `100010`, `92307`, `92650` |
| Main event | `7045` |

## 8.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `DC01` |
| `data.win.system.eventID` | `7045` |
| `data.win.system.providerName` | `Service Control Manager` |
| `data.win.eventdata.accountName` | `LocalSystem` |
| `data.win.eventdata.serviceName` | Random or tool-generated service name |
| `data.win.eventdata.imagePath` | Suspicious command or payload path |
| `rule.id` | `100010`, `92307` or `92650` |

## 8.4 What H5 Proves

H5 proves that a remote execution mechanism was probably used.

The complete SMB/PsExec-like chain becomes:

```text
NTLM network logon → privileged session → administrative share access → service creation → process execution
```

## 8.5 What H5 Does Not Prove

Remote service creation can also be legitimate.

Examples:

- endpoint management agents;
- software deployment tools;
- EDR installation;
- backup software;
- administrator maintenance;
- remote troubleshooting.

## 8.6 Analyst Interpretation

H5 is high-value because service creation on a domain controller is sensitive.

The analyst should review:

1. service name;
2. service path;
3. account used;
4. source IP;
5. parent process if available;
6. whether the service is expected;
7. whether the activity matches a maintenance window.

Full scenario explanation:

- [`T1021.002-smb-psexec-like.md`](T1021.002-smb-psexec-like.md)

# 9. H6 — NTLM Network Authentication Compatible with Pass-the-Hash

## 9.1 Purpose

**H6** detects the authentication effect of the Pass-the-Hash scenario.

The hypothesis is:

> **If `DC01` records NTLM network authentication from the attacker host and the account receives special privileges, then there is a signal compatible with credential-based lateral movement and possible Pass-the-Hash activity.**

## 9.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Source IP | `192.168.56.40` |
| Target host | `DC01` |
| Technique | `T1550.002 — Pass the Hash` |

## 9.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `DC01` |
| `data.win.system.eventID` | `4624` |
| `data.win.eventdata.logonType` | `3` |

## 9.4 What H6 Proves

H6 proves that a privileged account authenticated to `DC01` over the network using NTLM.

This is compatible with the effect of Pass-the-Hash.

## 9.5 What H6 Does Not Prove

H6 does not prove that a hash was used.

A normal NTLM authentication using a password can look similar from the point of view of Windows logs.

Therefore, H6 should be described as:

```text
privileged NTLM network authentication compatible with credential reuse
```

not as:

```text
direct proof of Pass-the-Hash
```

## 9.6 Analyst Interpretation

H6 is an early signal.

It becomes much stronger when correlated with H7.

## 10.1 Purpose

**H7** is the strongest hypothesis in the Pass-the-Hash scenario.

> **If DCSync-like activity by a non-machine account is correlated with privileged access inside a defined timeframe, then the chain is compatible with Pass-the-Hash / credential access behavior.**

```text
Wazuh detected behavior compatible with Pass-the-Hash by correlating DCSync-like activity, privileged NTLM access and remote activity on DC01.
```

# 11. H8 — RC4 Kerberos Service Ticket from an Unexpected Source

## 11.1 Purpose

**H8** detects the principal observable signal of the Kerberoasting scenario.

The hypothesis is:

> **If `DC01` records a Kerberos service-ticket request using RC4-HMAC from the controlled attacker host, then there is an initial signal compatible with Kerberoasting.**

## 11.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Source IP | `192.168.56.40` |
| Target host | `DC01` |
| Target IP | `192.168.56.20` |
| Technique | `T1558.003 — Kerberoasting` |
| Main rule | `100040` |
| Main event | `4769` |
| Ticket encryption type | `0x17 — RC4-HMAC` |

## 11.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| `agent.name` | `DC01` |
| `data.win.system.eventID` | `4769` |
| `data.win.eventdata.ticketEncryptionType` | `0x17` |
| `data.win.eventdata.ipAddress` | `192.168.56.40` or `::ffff:192.168.56.40` |
| `data.win.eventdata.targetUserName` | Requesting domain account |
| `data.win.eventdata.serviceName` | `<service_account>` |
| `rule.id` | `100040` |
| `rule.level` | `12` |
| `rule.mitre.id` | `T1558.003` |

## 11.4 Detection Logic

The main condition is:

```text
Event ID 4769
+
ticketEncryptionType = 0x17
+
source address outside the approved list
=
rule 100040
```

The request may contain an IPv4 address in either of these forms:

```text
192.168.56.40
::ffff:192.168.56.40
```

The detection logic must account for both representations.

## 11.5 What H8 Proves

H8 proves that the Domain Controller processed an RC4 Kerberos service-ticket request from the controlled attacker source.

The relevant sequence is:

```text
TGS request → Event ID 4769 → RC4-HMAC → unexpected source
```

This is the part of Kerberoasting that is observable from the Domain Controller.

## 11.6 What H8 Does Not Prove

H8 does not prove that:

- the complete ticket was exported;
- the ticket was tested with Hashcat;
- the service-account password was recovered;
- the requesting account had malicious intent;
- the recovered credential was reused.

Kerberos service-ticket requests are part of normal Active Directory activity.

The event becomes more relevant because of the combination:

```text
RC4 encryption
+
unexpected request source
+
service account associated with an SPN
```

## 11.7 False-Positive Considerations

Possible legitimate causes include:

- legacy applications that still require RC4;
- monitoring or management systems;
- application servers;
- administration hosts not included in the allowlist;
- migration activity;
- old service accounts without AES keys;
- incomplete RC4 remediation.

## 11.8 Analyst Interpretation

The analyst should check:

1. Is the source expected to request this service ticket?
2. Which account requested it?
3. Which service identity owns the SPN?
4. Does the service still require RC4?
5. Is the service account privileged?
6. How old is its password?
7. Were other SPNs requested by the same source?
8. Was the service account used after the request?

Repeated suspicious requests lead to **H9**.

Full scenario explanation:

- [`T1558.003-kerberoasting.md`](T1558.003-kerberoasting.md)

# 12. H9 — Repeated RC4 Service-Ticket Requests

## 12.1 Purpose

**H9** adds frequency correlation to H8.

The hypothesis is:

> **If the same source generates three H8 alerts within 120 seconds, then the activity becomes more relevant as possible automated Kerberos ticket collection.**

## 12.2 Scenario Context

| Field | Value |
|---|---|
| Source host | `Kali-ATK01` |
| Source IP | `192.168.56.40` |
| Target host | `DC01` |
| Technique | `T1558.003 — Kerberoasting` |
| Base rule | `100040` |
| Correlation rule | `100041` |
| Frequency | `3` |
| Timeframe | `120` seconds |
| Correlation field | Source IP address |

## 12.3 Expected Telemetry

| Field | Expected Value |
|---|---|
| Previous rule | `100040` |
| Matching source | `192.168.56.40` or IPv4-mapped IPv6 equivalent |
| Number of matches | `3` |
| Maximum interval | `120` seconds |
| `rule.id` | `100041` |
| `rule.level` | `15` |
| `rule.mitre.id` | `T1558.003` |

## 12.4 Detection Logic

The correlation condition is:

```text
three matches of rule 100040
+
same source address
+
within 120 seconds
=
rule 100041
```

The validated sequence is:

```text
first request  → 100040
second request → 100040
third request  → 100041
```

Wazuh may display the higher-level correlation rule for the third event rather than another visible `100040`.

That does not mean the third event stopped satisfying the initial conditions.

## 12.5 What H9 Proves

H9 proves that several suspicious RC4 service-ticket requests originated from the same source within the configured correlation window.

The chain becomes:

```text
100040
   ↓
100040
   ↓
third matching request
   ↓
100041
```

This provides stronger behavioral context than a single Event ID `4769`.

## 12.6 What H9 Does Not Prove

H9 still does not prove that offline password recovery succeeded.

The correlation can be avoided by an attacker who:

- requests only one high-value ticket;
- introduces delays between requests;
- distributes requests across several systems;
- uses a source already included in the allowlist;
- requests tickets using AES instead of RC4.

Legitimate applications may also request several tickets in a short period.

## 12.7 Analyst Interpretation

The analyst should compare the request pattern with the normal Kerberos baseline.

Relevant questions include:

1. How many different SPNs were requested?
2. Were the requests generated by the same account?
3. Is the source normally used for service access?
4. Is RC4 expected in the domain?
5. Were requests made outside normal operating hours?
6. Did the service identity authenticate elsewhere afterward?
7. Does the requested account have elevated privileges?

Full scenario explanation:

# 13. H10 — Unusual Process Connecting to Kerberos

## 13.1 Purpose

**H10** provides optional endpoint context when Kerberos activity originates from a monitored Windows workstation.

The hypothesis is:

> **If a process other than `lsass.exe` connects from `WS01` to the Kerberos service on `DC01`, then the process should be reviewed as unusual Kerberos activity.**

## 13.3 Expected Telemetry

| `rule.level` | `13` |
| `rule.mitre.id` | `T1558.003` |

## 13.4 Detection Logic

The supporting condition is:

```text
Sysmon Event ID 3
+
source host = WS01
+
destination = DC01
+
destination port = 88
+
process image is not lsass.exe
=
rule 100042
```

## 13.5 What H10 Proves

H10 proves that an unusual process established a network connection from the monitored workstation to the Kerberos service.

It can provide:

- process image;
- source workstation;
- destination address;
- destination port;
- network context.

## 13.6 What H10 Does Not Prove

H10 does not prove Kerberoasting by itself.

Some Windows applications request Kerberos tickets through LSASS.

In those cases, Sysmon can show:

```text
C:\Windows\System32\lsass.exe
```

even when another application triggered the operation.

The rule also does not detect the main laboratory execution from Kali because Linux does not generate Windows Sysmon events.

## 13.7 Analyst Interpretation

H10 is complementary evidence.

It can strengthen a Kerberos investigation when the activity originates from a Windows endpoint and the process context is available.

The main validated Kali-based detection chain remains:

```text
Event ID 4769
        ↓
rule 100040
        ↓
rule 100041
```

Rule `100042` should therefore be treated as supporting, environment-dependent coverage.

# 17. Final Detection Chains

## 17.1 RDP

```text
H1: remote RDP logon
        ↓
H2: post-access process execution
```

The custom rule `100001` belongs to H2 because it is chained from process-creation rule `67027`; it is not the rule that establishes the initial RDP logon.

## 17.2 SMB / PsExec-like

```text
H3: NTLM network logon
        ↓
H4: administrative share access
        ↓
H5: service creation and process execution
```

## 17.3 Pass-the-Hash / DCSync

```text
H6: privileged NTLM network authentication
        ↓
H7: DCSync-like activity correlated with privileged access
```

## 17.4 Kerberoasting

```text
H8: RC4 service-ticket request from an unexpected source
        ↓
H9: request-frequency correlation
        ↓
H10: optional Windows process context
```

## 17.5 AS-REP Roasting

```text
H11: successful Event ID 4768 with preAuthType 0
        ↓
H12: RC4-HMAC context
        ↓
H13: three qualifying requests from one source in 60 seconds
```

The AS-REP validations were collected on two different dates. The repository validates the three rule IDs but does not present them as one continuous execution timeline.

# 18. Key Takeaway

The repository distinguishes between event, alert and attribution:

```text
telemetry
    ↓
detection hypothesis
    ↓
Wazuh rule
    ↓
correlation
    ↓
analyst interpretation
    ↓
MITRE ATT&CK attribution
```

The five scenarios provide different visibility:

```text
RDP:
remote access and post-access execution are observable

SMB / PsExec-like:
authentication, shares, services and execution are observable

Pass-the-Hash:
the hash is not directly visible, but related behavior can be correlated

Kerberoasting:
the TGS request is visible, but offline password testing is not

AS-REP Roasting:
the no-pre-authentication TGT request is visible, but password recovery is not
```

That distinction between event, alert and attribution is the main detection-engineering value of the laboratory.
