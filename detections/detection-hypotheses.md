# Detection Hypotheses

This document defines the detection hypotheses used in the Wazuh lateral movement laboratory.

A detection hypothesis is not the same as a rule. A hypothesis describes the behavior that should be observable in logs when a technique is executed. Rules are only the implementation layer that turns part of that behavior into alerts.

The purpose of this file is to make the reasoning behind the detections explicit.

## 1. Analytical Model

The project separates three levels of analysis:

| Level | Meaning | Example |
|---|---|---|
| Event | Raw record generated by Windows, Sysmon or another telemetry source | `4624`, `4672`, `4688`, `5145`, `7045`, `4662` |
| Alert | Result of applying a Wazuh rule to one or more events | `92653`, `100001`, `100010`, `100011`, `100021`, `100030`, `100033` |
| Technical Attribution | Analyst interpretation that maps events and alerts to a MITRE ATT&CK technique | `T1021.001`, `T1021.002`, `T1550.002`, `T1003.006` |

This distinction is important because a SIEM does not directly detect a technique. It detects events and patterns. The mapping to MITRE ATT&CK is an analyst interpretation built from telemetry, sequence, context and correlation.

For example, observing an NTLM network logon does not prove Pass-the-Hash. It becomes more relevant when it appears together with privileged access, administrative share access, service creation or DCSync-like activity.

## 3. H1 — RDP Access from Known Attack Origin

| Field | Value |
|---|---|
| Hypothesis ID | H1 |
| Associated Technique | `T1021.001 — Remote Services: Remote Desktop Protocol` |
| Scenario | RDP lateral movement |
| Source Host | `Kali-ATK01` |
| Source IP | `192.168.56.40` |
| Target Host | `WS01` |
| Target IP | `192.168.56.30` |
| Main Rules | `92653`, `100001` |
| Main Windows Event | `4624` |

### Natural-language condition

If `WS01` records a successful remote interactive logon from `192.168.56.40` using a domain user, then there is an initial signal compatible with RDP-based lateral movement.

### Expected fields

| Field | Expected Value |
|---|---|
| `data.win.system.eventID` | `4624` |
| `data.win.eventdata.logonType` | `10` |
| `data.win.eventdata.ipAddress` | `192.168.56.40` |
| `data.win.eventdata.targetUserName` | `<standard_user>` |
| `agent.name` | `WS01` |
| `rule.id` | `92653` or `100001` |
| `rule.mitre.id` | `T1021.001` |

### Analyst interpretation

An RDP logon is not automatically malicious. RDP is a legitimate administration protocol.

The hypothesis becomes relevant because the logon comes from the controlled attack simulation host and targets a domain-joined workstation. In a production environment, the analyst should check whether the source IP belongs to an approved administrative jump host, VPN range or remote support platform.

### Why this is not enough by itself

This is an initial access signal inside the lateral movement scenario, but it is not enough to prove malicious behavior. It needs to be interpreted together with H2, which covers post-access activity after the session is established.

## 4. H2 — Post-access Activity After RDP Session

| Field | Value |
|---|---|
| Hypothesis ID | H2 |
| Associated Technique | `T1021.001 — Remote Services: Remote Desktop Protocol` |
| Scenario | RDP lateral movement |
| Source Host | `Kali-ATK01` |
| Target Host | `WS01` |
| Main Rules | `67027`, `92052`, `100001` |
| Main Windows Event | `4688` |
| Main Sysmon Event | Sysmon Event ID `1`, if available |

### Natural-language condition

If command execution or local reconnaissance appears on `WS01` after an RDP session from `Kali-ATK01`, then the RDP access should be interpreted as post-access activity compatible with lateral movement.

### Expected fields

| Field | Expected Value |
|---|---|
| `data.win.system.eventID` | `4688` |
| `data.win.eventdata.newProcessName` | `whoami.exe`, `hostname.exe`, `ipconfig.exe`, `cmd.exe` |
| `data.win.eventdata.parentProcessName` | `cmd.exe` or another shell/process launcher |
| `data.win.eventdata.subjectUserName` | `<standard_user>` |
| `agent.name` | `WS01` |
| `rule.id` | `67027`, `92052`, `100001` |
| `rule.mitre.id` | `T1021.001` |

### Analyst interpretation

This hypothesis gives context to H1. A login without activity may be normal or may represent a test connection. A login followed by reconnaissance commands is more suspicious because it shows that the session was used interactively.

Typical post-access commands in the lab were:

```text
whoami
hostname
ipconfig
```

### Why this matters

The RDP scenario is weaker than the SMB/PsExec-like and Pass-the-Hash scenarios if only the logon is considered. It becomes stronger when the analyst can reconstruct the sequence:

```text
Remote logon → interactive session → command execution → process creation evidence
```

## 5. H3 — SMB Authentication from Kali to DC01

| Field | Value |
|---|---|
| Hypothesis ID | H3 |
| Associated Technique | `T1021.002 — Remote Services: SMB/Windows Admin Shares` |
| Scenario | SMB/PsExec-like execution |
| Source Host | `Kali-ATK01` |
| Source IP | `192.168.56.40` |
| Target Host | `DC01` |
| Target IP | `192.168.56.20` |
| Main Rule | `100011` |
| Main Windows Event | `4624` |

### Natural-language condition

If `DC01` records a network logon from `192.168.56.40` using NTLM and Logon Type 3, then there is an initial signal compatible with SMB-based lateral movement.

### Expected fields

| Field | Expected Value |
|---|---|
| `data.win.system.eventID` | `4624` |
| `data.win.eventdata.logonType` | `3` |
| `data.win.eventdata.authenticationPackageName` | `NTLM` |
| `data.win.eventdata.ipAddress` | `192.168.56.40` |
| `data.win.eventdata.targetUserName` | `<privileged_user>` |
| `agent.name` | `DC01` |
| `rule.id` | `100011` |
| `rule.mitre.id` | `T1021.002`, `T1550.002` |

### Analyst interpretation

This event is useful but ambiguous. Logon Type 3 is common in Windows environments. NTLM is also common in legacy environments or where Kerberos is not used for a specific access path.

The value of this hypothesis is that it opens the chain. It should not be treated as final attribution by itself.

### Why this is not enough by itself

A single NTLM network logon can be caused by:

- legitimate administration,
- backup software,
- endpoint management tools,
- remote inventory,
- file access,
- legacy applications,
- printer or scanner workflows.

It becomes meaningful when combined with H4 and H5.

## 6. H4 — Access to Administrative Shares

| Field | Value |
|---|---|
| Hypothesis ID | H4 |
| Associated Technique | `T1021.002 — Remote Services: SMB/Windows Admin Shares` |
| Scenario | SMB/PsExec-like execution |
| Source Host | `Kali-ATK01` |
| Target Host | `DC01` |
| Main Rules | `92218`, native Windows event `5145` |
| Main Windows Event | `5145` |

### Natural-language condition

If, after an SMB authentication, `DC01` records access to administrative shares such as `ADMIN$`, `C$` or `IPC$` from the same source, then the SMB lateral movement hypothesis becomes stronger.

### Expected fields

| Field | Expected Value |
|---|---|
| `data.win.system.eventID` | `5145` |
| `data.win.eventdata.shareName` | `ADMIN$`, `C$`, `IPC$` |
| `data.win.eventdata.ipAddress` | `192.168.56.40` |
| `agent.name` | `DC01` |
| `rule.id` | `92218` or related administrative share rule |

### Analyst interpretation

Administrative share access is not malicious by itself. `ADMIN$` and `IPC$` are normal Windows administrative mechanisms.

However, when this activity appears after NTLM network authentication from an unusual source and before remote service creation, it becomes a relevant lateral movement indicator.

### Why this matters

PsExec-like behavior typically needs administrative share access and Service Control Manager interaction. Access to `IPC$` and named pipes such as `\pipe\svcctl` is especially relevant because it can indicate interaction with remote service control mechanisms.

## 7. H5 — Remote Service Creation Compatible with PsExec-like Execution

| Field | Value |
|---|---|
| Hypothesis ID | H5 |
| Associated Techniques | `T1021.002 — SMB/Windows Admin Shares`, `T1569.002 — Service Execution` |
| Scenario | SMB/PsExec-like execution |
| Source Host | `Kali-ATK01` |
| Target Host | `DC01` |
| Main Rules | `100010`, `92307`, `92650` |
| Main Windows Event | `7045` |

### Natural-language condition

If, after NTLM network authentication and administrative share access, `DC01` records the creation of a new service with suspicious command or payload execution characteristics, then the chain is compatible with PsExec-like remote execution.

### Expected fields

| Field | Expected Value |
|---|---|
| `data.win.system.eventID` | `7045` |
| `data.win.system.providerName` | `Service Control Manager` |
| `data.win.eventdata.serviceName` | Random or tool-generated service name |
| `data.win.eventdata.imagePath` | Command or payload path used for remote execution |
| `data.win.eventdata.accountName` | `LocalSystem` |
| `agent.name` | `DC01` |
| `rule.id` | `100010`, `92307`, `92650` |
| `rule.mitre.id` | `T1021.002`, `T1569.002` |

### Analyst interpretation

This is the strongest signal in the SMB/PsExec-like scenario. A service creation event on a domain controller is high-value telemetry, especially when it appears after NTLM authentication and administrative share access.

The analyst should review:

- service name,
- service path,
- parent process if available,
- account used,
- source IP,
- command output behavior,
- whether the activity matches approved administration.

### Why this has higher confidence

The chain is no longer only:

```text
network logon
```

It becomes:

```text
NTLM network logon → privileged session → administrative share access → service creation → process execution
```

That sequence is much more consistent with lateral movement and remote execution.

## 8. H6 — NTLM Network Authentication Compatible with Pass-the-Hash

| Field | Value |
|---|---|
| Hypothesis ID | H6 |
| Associated Technique | `T1550.002 — Use Alternate Authentication Material: Pass the Hash` |
| Scenario | Pass-the-Hash |
| Source Host | `Kali-ATK01` |
| Target Host | `DC01` |
| Main Rules | `100011`, `100021` |
| Main Windows Events | `4624`, `4672` |

### Natural-language condition

If `DC01` records NTLM network authentication from `Kali-ATK01` and the authenticated account receives special privileges, then there is a signal compatible with credential-based lateral movement and possible Pass-the-Hash activity.

### Expected fields

| Field | Expected Value |
|---|---|
| `data.win.system.eventID` | `4624`, `4672` |
| `data.win.eventdata.logonType` | `3` |
| `data.win.eventdata.authenticationPackageName` | `NTLM` |
| `data.win.eventdata.ipAddress` | `192.168.56.40` |
| `data.win.eventdata.subjectUserName` | `<privileged_user>` |
| `data.win.eventdata.privilegeList` | Administrative privileges such as `SeDebugPrivilege`, `SeBackupPrivilege`, `SeRestorePrivilege` |
| `agent.name` | `DC01` |
| `rule.id` | `100011`, `100021` |
| `rule.mitre.id` | `T1550.002`, `T1078` |

### Analyst interpretation

Wazuh does not observe the NTLM hash directly. It observes the effects of authentication:

```text
NTLM network logon → privileged session → remote activity
```

This means that attribution to Pass-the-Hash must be careful. The same Windows events may also appear when a privileged user authenticates normally over NTLM.

### Why this is not enough by itself

This hypothesis is compatible with Pass-the-Hash but not definitive. It needs correlation with the rest of the chain, especially H7.

## 9. H7 — Pass-the-Hash and DCSync Correlation

| Field | Value |
|---|---|
| Hypothesis ID | H7 |
| Associated Techniques | `T1550.002 — Pass the Hash`, `T1003.006 — DCSync` |
| Scenario | Pass-the-Hash / DCSync correlation |
| Source Host | `Kali-ATK01` |
| Target Host | `DC01` |
| Main Rules | `100030`, `100033` |
| Main Windows Events | `4662`, `4672`, `4624` |

### Natural-language condition

If `DC01` records DCSync-like activity by a non-machine account and this is followed within a defined timeframe by privileged NTLM access, then the chain is compatible with a controlled Pass-the-Hash / credential access scenario.

### Expected fields

| Field | Expected Value |
|---|---|
| `data.win.system.eventID` | `4662` |
| `data.win.eventdata.accessMask` | `0x100` |
| `data.win.eventdata.properties` | Replication-related GUIDs or replication permissions |
| `data.win.eventdata.subjectUserName` | Non-machine account |
| `rule.id` | `100030`, `100033` |
| `rule.level` | `13`, `15` |
| `rule.mitre.id` | `T1003.006`, `T1550.002` |

### Analyst interpretation

This is the strongest correlation in the laboratory because it links credential access evidence with privileged remote authentication.

Rule `100030` detects DCSync-like behavior by observing Active Directory replication rights used by a non-machine account. Rule `100033` raises the severity by correlating DCSync-like evidence with privileged access in the same attack chain.

### Why this has high confidence

A single NTLM logon is weak. A single privileged session is also not enough. But the combination of:

```text
DCSync-like activity → privileged NTLM authentication → remote execution evidence
```

is a much stronger basis for analyst triage.

## 11. Key Takeaway

The detections in this repository are not based only on individual events.

Their value comes from chaining weak or medium signals into stronger analytical sequences:

```text
RDP:
remote logon → post-access process execution

SMB / PsExec-like:
NTLM network logon → privileges → admin shares → service creation → process execution

Pass-the-Hash / DCSync:
DCSync-like activity → NTLM privileged access → correlation alert
```

This is the core detection logic of the project.
