# T1558.004 — AS-REP Roasting Detection

## Overview

This document describes the detection of controlled AS-REP Roasting activity in the Active Directory laboratory.

The scenario is mapped to:

```text
MITRE ATT&CK T1558.004 — Steal or Forge Kerberos Tickets: AS-REP Roasting
Tactic: Credential Access
```

The detection is based on successful Kerberos TGT requests for an account that does not require Kerberos pre-authentication.

The main observable chain is:

```text
TGT request
      ↓
Windows Security Event ID 4768
      ↓
Pre-Authentication Type 0
      ↓
RC4-HMAC encryption context
      ↓
Wazuh base and correlation rules
```

The experiment was performed in a private, isolated and authorized laboratory.

## Detection Objective

The objective is to determine whether Wazuh can detect three levels of AS-REP Roasting-compatible activity:

1. A successful TGT request without Kerberos pre-authentication.
2. The same request using RC4-HMAC encryption.
3. Repeated qualifying requests from the same source within a short period.

These detection levels correspond to hypotheses `H11`, `H12` and `H13`.

The evidence confirms that:

- `svc_asrep_lab` existed in `lab.local`;
- the account accepted a TGT request without Kerberos pre-authentication;
- `Kali-ATK01` could communicate with `DC01`;

- Kerberos auditing generated Event ID `4768`;

The supplied evidence does not preserve:

## Signal Confidence

| Signal | Confidence | Interpretation |
| ------ | ---------- | -------------- |
| Event ID `4768` alone | Low | A TGT request occurred |
| `status=0x0` alone | Low | The request completed successfully |
| `ticketEncryptionType=0x17` alone | Low to medium | RC4-HMAC was used |
| `preAuthType=0` for a named account | Medium to high | No Kerberos pre-authentication was recorded |
| `4768 + preAuthType=0 + status=0x0` | High | Successful no-pre-authentication TGT request |
| Previous combination + `0x17` | High | Adds RC4-HMAC context |
| Three qualifying requests from the same source | Very high in this laboratory | Adds behavioral repetition |

---

## False Positives

Possible legitimate or authorized causes include:

- a legacy account intentionally configured without Kerberos pre-authentication;
- an authorized Active Directory security assessment;
- an account-configuration audit;
- a legacy application repeatedly requesting tickets;
- different clients sharing one translated source address;
- multiple accounts requested from the same source IP.

The correlation rule groups events by source IP. It does not require every event to target the same username.

## Limitations

- The three rules were validated across two different dates.
- The exact XML revision active on each date was not preserved.
- The stored `100052` description differs from the current XML.
- The six screenshot executions cannot be mapped one-to-one to six Windows events.
- No Sysmon evidence was supplied.
- No benign baseline or negative control was supplied.
- Only one target account, one Domain Controller and one source host were used.
- All preserved events use RC4-HMAC.
- Account preparation, restoration and cleanup evidence was not supplied.
- The experiment does not demonstrate password recovery or later use of the account.

---

## Defensive Conclusion

The experiment validates the following detection chain:

```text
successful Event ID 4768
        ↓
preAuthType = 0
        ↓
non-machine account
        ↓
rule 100050
        ↓
ticketEncryptionType = 0x17
        ↓
rule 100051
        ↓
three qualifying requests from the same source
        ↓
rule 100052
```

The alert evidence validates rules `100050`, `100051` and `100052`.

The correct analyst conclusion is:

> Wazuh detected successful Kerberos TGT requests without pre-authentication, including RC4-HMAC context and repeated activity from the same source, compatible with AS-REP Roasting in the controlled laboratory.

The evidence does not demonstrate that the account password was recovered.
